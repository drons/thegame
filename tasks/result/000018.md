# 000018: вариант контролов, оптимизированных для тачскрина

Статус: выполнено. Тесты: 222 → 230 pass (новых 8, tests/controls.test.js).

## Что сделано

* **src/controls.js** (чистое ядро, UMD — как и клавишный маппинг 000028):
  * `isTouchDevice(env)` — детект тач-устройства по СНИМКУ окружения
    `{maxTouchPoints, touchEvents, coarsePointer}`; чистая функция —
    navigator/document не трогает, значения подставляет вызывающий.
    Строгая валидация (строка/-1/NaN → false).
  * `chooseControlsScheme(env, forced)` — выбор схемы `'touch'` |
    `'keyboard'`: по детекту либо явное переопределение (`forced`).
  * `layoutTouchControls(width, height, {bottomInset})` — раскладка:
    D-pad (квадрат внизу слева, 96…220 px) и кнопка действия (внизу
    справа, 56…96 px); `bottomInset` поднимает только кнопку (под
    полноэкранную кнопку). Невалидные размеры → нулевые прямоугольники.
  * `touchActionAt(x, y, layout)` — хит-тест: направление D-pad по
    доминирующей оси от центра (диагональ 45° → горизонталь), в центре
    мёртвая зона (`TOUCH_DEADZONE`), кнопка → `'interact'`, мусор → null.
  * `touchMoveKeyForAction(action)` — виртуальная клавиша `'touch:<dir>'`
    (для `'interact'` — null).
  * `deltaForMoveKey` расширен: понимает `touch:<dir>` → дельта;
    `touch:interact` → null. Поведение для прежних id не изменено.
* **src/main.js** (сборка):
  * `touchEnvSnapshot()` — собирает снимок (navigator + matchMedia) для
    ядра; `?controls=touch|keyboard` из URL — явное переопределение
    схемы (тест на десктопе и наоборот).
  * при схеме `'touch'`: `G.touchControls.init({onHold, onRelease,
    onInteract}) + .show()`. onHold/onRelease кладут `touch:<dir>` в
    ТОТ ЖЕ Set `keys`, что и настоящие клавиши — цикл кадра и `tryMove()`
    не тронуты (одна дорожка движения). onInteract → `toggleNpcDialog()`.
  * Обработчик [E] вынесен в `toggleNpcDialog()` — общий для клавиатуры
    и тач-кнопки.
  * `blur` — очищает и тач-состояние (`touchControls.releaseAll()`).
  * `__game.state.controls` — текущая схема (отладка/смoke).
* **src/ui.js** — `Game.touchControls` (DOM-привязка):
  * D-pad (внизу слева): удержание — движение, скольжение пальца —
    смена направления, мёртвая зона — текущее направление. Pointer
    Events + `setPointerCapture` (pointerup доедет под оверлеем —
    «залипший» палец не останется). Второй палец игнорируется.
  * Кнопка «E» (внизу справа) — действие (диалог NPC/подземелье);
    `blur()` после нажатия (гибридные устройства).
  * `bottomInset()` меряет высоту кнопки полноэкранного режима —
    раскладка поднимает кнопку действия, чтобы не пересекаться.
  * `show/hide/isActive/releaseAll`, пересчёт на resize, отпускание на
    `visibilitychange`.
* **index.html** — CSS on-screen-контролов (z-index 5, под оверлеями;
  контейнер `pointer-events: none`) и `user-scalable=no` в viewport
  (браузерный pinch-zoom ломает контролы; зум в игре — свой).

## Ключевые решения

* Одна дорожка движения: тач даёт виртуальные id в тот же Set удержанных
  клавиш, `deltaForMoveKey` их понимает — клавиатура и палец идут через
  один и тот же код перемещения (ничего не дублируется).
* D-pad по доминирующей оси + мёртвая зона — проще и надёжнее
  квадрантов/сетки (см. memory).
* Чистое ядро получает СНИМОК окружения, а не navigator — ядро
  тестируется в node без DOM.
