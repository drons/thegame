# 000031: сохранение состояния мира и игрока — версионирование и миграции

Статус: выполнено. Тесты: 196 → 212 pass (новых 16, tests/save.test.js).

## Что сделано

* **Новый чистый UMD-модуль `src/save.js`** (без DOM, без зависимостей;
  браузер — `Game.*`, node — require; в index.html подключён перед
  main.js). Хранилище подставляется вызывающим (в браузере —
  window.localStorage), модуль хранилище не знает — в тестах мок.
  * Оболочка сейва: `{ version, savedAt, data }` — версия СТРУКТУР
    ДАННЫХ (data) записывается в хранилище вместе с данными.
  * `CURRENT_VERSION = 1`; правило: «ломающее» изменение структур —
    поднять версию + добавить миграцию N→N+1 в `MIGRATIONS`.
  * `migrate(data, from, to)` — ПОСЛЕДОВАТЕЛЬНОЕ применение цепочки
    1→2→…→to; чистая функция, бросает при неудаче.
  * `load(storage)` → `{status}`: `empty` | `ok` (с миграцией до версии
    кода, помечается `migrated`) | `corrupt` (битый JSON/оболочка —
    восстановить нечего) | `migration_failed` (включая сейв «из
    будущего»: версия данных > версии кода). При неудачах запись в
    хранилище НЕ трогается — обнуляет UI, только после согласия.
  * `save(storage, data)` / `clear(storage)` — с защитой от исключений
    хранилища (квота, приватный режим) → false.
* **src/main.js** (UI-часть):
  * при старте — `G.load(localStorage)`; `migration_failed` →
    `console.warn` + `confirm()` «данные восстановить невозможно,
    обнулить?» — `G.clear` ТОЛЬКО после согласия; `corrupt` → тихий
    сброс с `console.warn` (принцип задачи 000029);
  * `collectSaveData()` — структура v1: `{ day, steps, position, hero }`
    (день мира, прогресс шагов, позиция, персонаж);
  * `saveNow()` вызывается: после успешного шага по миру, при смене дня,
    после боя (мир и подземелье), при выходе из подземелья, на
    `beforeunload`;
  * `restoreFromSave()` — после загрузки карты: день доводится часами
    (`rest()`/`addStep`, флаг `restoring` подавляет перезапись сейва),
    персонаж восстанавливается при валидной форме (иначе console.warn,
    игра не роняется), позиция — если тайл проходим (иначе спавн).
  * `__game.state.save` — отладочная информация о загруженном сейве.
* **tests/save.test.js** (16 тестов): roundtrip сериализации; битый
  JSON и некорректные оболочки → corrupt; цепочка миграций 1→2→3
  (последовательность и результат); миграция с ошибкой →
  migration_failed; отсутствующая миграция в цепочке; сейв «из
  будущего»; при неудаче хранилище не меняется; квота → false без
  исключений; clear; getItem, бросаящий; setCurrentVersion;
  «браузерный» путь UMD через vm-песочницу.

## Ключевые решения

* Два режима неудачи — по разным правилам: `migration_failed`
  (данные старые/чужие, миграция упала) — согласие пользователя;
  `corrupt` (читаться нечего) — тихий сброс. Так совмещены требования
  000031 (согласие) и 000029 (тихий сброс невалидного сейва).
* Payload v1 намеренно минимален (день/позиция/персонаж): квесты и сток
  NPC добавит задача 000029 ДОП. полями без повышения версии (неломкое
  расширение).
* Восстановление дня (ПРАВИЛЬНО, после ревью) — `fastForward` +
  `addStep(steps)`: слушатели onDay при восстановлении НЕ должны
  срабатывать — сейв это снимок, все эффекты прошедших дней уже в
  данных; флаг `restoring` убран (saveNow при восстановлении и так
  не вызывается). См. memory/000031-save-versioning.md.

## Ограничения

* Не сохраняются: dungeonMemory, содержимое активного подземелья —
  не входили в задачу; при необходимости добавятся полями (версия не
  меняется) или миграцией.
* UI-часть в main.js (confirm, восстановление) — браузерный клей, не
  покрыт node-тестами (паттерн проекта: чистое ядро тестируется,
  DOM-клей — нет).

## Правки по итогам ревью (коммит «Правки по итогам ревью: …»)

* **defeatedAt теперь СОХРАНЯЕТСЯ** (выше было ограничение): поле
  `defeatedAt: {'x,y': день}` в payload (неломкое расширение, версия
  не меняется) + `serializeDefeatedAt`/`restoreDefeatedAt` (day.js,
  с валидацией). После перезагрузки побеждённая группа оживает не
  мгновенно, а через respawn_days — как требует SPEC «Игровое время»
  (раньше награду той же группы можно было забрать повторно в тот же
  день).
* **Восстановление дня без заморозки:** `clock.fastForward(n)` (day.js)
  вместо `rest()` (day-1) раз — O(1), без оповещения слушателей (сейв
  — снимок, эффекты прошедших дней уже в данных; раньше day=100000 →
  ~99999 перерисовок панели). Граница дня — MAX_SAVED_DAY = 1e9,
  день > границы КЛАМПится (раньше day > 100000 молча сбрасывался на 1,
  и pruneQuestBookByDay(qb, 1) терял ВСЕ активные квесты).
* **Шаги первого дня** восстанавливаются (раньше блок был вложен в
  `d.day > clock.day`, и {day:1, steps:35} восставал со steps=0).
* **Персонаж сейва чистится** до применения: `sanitizeSavedHero`
  (player.js) + `sanitizeInventory`/`sanitizeEquipment` (items.js) —
  битый/устаревший сейв (призрак-предметы, нечисловые уровни, null-
  записи) больше не роняет старт (требование 000029). См.
  memory/000031-save-versioning.md и memory/000029-….
