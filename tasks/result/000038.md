## Что сделано

* **src/sprites.js** (чистая функция, тестируется в node):
  * `HP_BAR_COLORS = { high: '#6fdc6f', mid: '#e0b13c', low: '#d9483b' }`
    — цвета из существующей палитры игры, новых не введено:
    #6fdc6f — полоса HP мобов на canvas (combat-ui.js), #e0b13c —
    ROLE_COLORS.swarm (combat-ui.js) и отмётки подземелья
    (dungeon-ui.js), #d9483b — ROLE_COLORS.melee (combat-ui.js) и
    dungeon-ui.js.
  * `hpBarColor(frac)` — чистая функция цвета полосы HP:
    `frac >= 0.5 → зелёный; frac >= 0.2 → жёлтый; иначе → красный`.
    Зафиксированное решение по границам: границы «включены сверху» —
    ровно 0.5 — зелёный, ровно 0.2 — жёлтый (ТЗ «>50%» и «20–50%»
    читаем как включительные диапазоны 50–100 и 20–50). Логика
    закреплена комментарием в коде и тестом.
  * Clamp: frac вне [0,1] приводится в [0,1] (±Infinity → 1/0);
    NaN/нечисла → 0 (красный) — рендер не падает ни при каких
    аргументах.
  * Экспорт `HP_BAR_COLORS, hpBarColor` добавлен в UMD-блок
    (в браузере — `Game.hpBarColor`).
* **src/combat-ui.js**:
  * `build()`: `.combat-hpbar` (контейнер + `.combat-hpbar-fill` +
    `.combat-hpbar-text`) — ВТОРОЙ элемент `.combat-side`: ПОСЛЕ
    `.combat-turnorder` (000036), ПЕРЕД `.combat-state` (ТЗ п. 1).
  * `render()`: ОДИН блок расчёта `p = c.player; d = G.derived(p);
    hpFrac = d.maxHP > 0 ? p.hp / d.maxHP : 0; hpColor = hpBarColor
    (hpFrac)` — вынесен ПЕРЕД ромбом героя; один вызов G.derived на
    render (как раньше) и один вызов hpBarColor на троих
    потребителей:
    1. canvas-миниполоса 4px над ромбом (паттерн мобов: дорожка
       #3a0d0d + заполнение); ширина = ширина ромба (2·s), позиция —
       8px над верхней вершиной («над головой»); рисуется ПОСЛЕ
       отрисовки героя → «поверх любого вида героя» (000047 —
       спрайт, координаты — те же (c.px, c.py));
    2. текст stateEl — без изменений (`HP ${p.hp}/${d.maxHP}`,
       источник maxHP тот же);
    3. DOM-полоса: `width = clamp(hpFrac)·100%`, `background =
       hpColor`, `textContent = HP ${p.hp}/${d.maxHP}` (числа всегда

  * Обновление — ТОЛЬКО в render() (единственный путь, как строка

    (const G = globalThis.Game) — функция из скрипта, загружающегося

## Исправления по ревью (major — порядок загрузки, подтверждён)

Замечание ревью (major): в исходной версии index.html
`src/sprites.js` стоял ПОСЛЕ `src/combat-ui.js`, а вывод «ленивый
вызов в render() разрешится после загрузки всех скриптов» — НЕВЕРЕН:
каждый UMD-модуль ЗАМЕНЯЕТ объект Game
(`root.Game = Object.assign({}, root.Game, factory(...))`), а
combat-ui.js снимает его один раз при загрузке
(`const G = globalThis.Game`). `hpBarColor` попадал только в НОВЫЙ
объект — `G.hpBarColor` оставался undefined НАВСЕГДА, и полоса героя
(DOM-бар и canvas-миниполоса) всегда рисовалась фолбэком `'#6fdc6f'`;
пороговые цвета (жёлтый 20–50%, красный <20%) не срабатывали никогда.
Независимо воспроизведено vm-симуляцией цепочки index.html: герой
HP 1/25 (frac 0.04) → `fill.style.background = '#6fdc6f'` вместо
`'#d9483b'`. Node-тесты были зелёные: tests/sprites.test.js проверял
только чистую функцию, а tests/combat-ui.test.js грузил combat-ui.js
без sprites.js — фиксировал как раз фолбэк.

Фикс (паттерн задачи 000018 — порядок скриптов + регрессия):
* **index.html**: `<script src="src/sprites.js">` переставлен ПЕРЕД
  `<script src="src/combat-ui.js">` (sprites.js требует только
  map.js, который грузится раньше; остальные потребители API
  спрайтов — main.js — грузится последним, не пострадал). В
  HTML-комментарии о порядке добавлено объяснение пары.
* **tests/index-order.test.js**: новый тест фиксирует пару
  «sprites.js ДО combat-ui.js»; sprites.js добавлен в список

* **tests/combat-ui.test.js**: цепочка loadCombatUi() теперь
  включает map.js + sprites.js ДО combat-ui.js (порядок

  `fill.style.background` = `#d9483b` (из hpBarColor, не фолбэк) и
  ширина = доля HP; (2) цепочка без sprites.js — фолбэк

* **memory/000038-combat-hpbar.md и этот отчёт**: раздел о порядке
