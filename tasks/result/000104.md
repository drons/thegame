## Решения (зафиксированы, см. memory)

1. **Внутренний размер = footprint × 2 — УНИФОРМНО** (пример из
   задачи). Альтернатива max(3, 2×footprint) ОТКЛОНЕНА: ломает
   униформность формулы; вырожденный хутор 2x2 (внутренности нет —
   000102: мин_постройки=0) задокументирован и покрыт тестом.
2. **Сид — от ПОЗИЦИИ** (hash2(cityX, cityY, CITY_LAYOUT_CONST)): город
   статичен, НЕ сидится totalXp (в отличие от
   generateDungeonContents). Новая соль 0x4c41594f с golden-пином —
   прецедент CITY_SEED_CONST 000103.
3. **Вход/выход — юг/север** (не «сторона захода героя»): layout —
   статичная функция позиции, направление захода — state 000105.
   Порядок вызовов rng (сначала entrance.x, затем exit.x) закреплён
   golden-пином.
4. **Город — НЕ тип подземелья**: DUNGEON_TYPES/DUNGEON_SIZE/
   dungeonShapeSeed/assets-dungeons/COMBAT_BG_DUNGEON не тронуты;
   layout — ровно 7 полей без type/rooms/wallObjs, маркер
   `kind: 'city'` для 000105.
5. **Открытое пространство** (не лабиринт, без улиц/кварталов) —
   решение по умолчанию; 000106 кладёт постройки на FLOOR.
6. **Чистый UMD-модуль** (единственный require — perlin.js; браузер —
   неймспейс Game.Cities; гард-throw) — взаимных require в момент
   загрузки нет (прецедент 000064), vm-цепочки не ломает.
7. **Не персистится**: layout перегенерируется из позиции; сейв не
   трогать (data.cities — 000109, без повышения версии — 000031).
