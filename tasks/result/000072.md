# Отчёт: задача 000072 — «раз в день» по эффекту, благословения и состояние построек в сейве

Статус: выполнено. Тесты: 567 → 587 pass, 0 fail.
Коммиты: dc8b2c2 (красные тесты), f2882db (реализация).
Память: memory/000072-building-effect-state.md.
Родитель: 000064 (план — memory/000064-building-effects-plan.md);
параллельная подзадача — 000071 (основание buildingUI).

## Суть

000064 зафиксировала механику «раз в день» (`canUseToday`) и
благословения храмов, но состояние эффектов никуда не записывалось и
не попадало в сейв: `canUseToday` не имела потребителей, флаг
`особые_параметры.раз_в_день` каталога кодом не читался, а прецедент
`_lastUnkillDay` (src/combat.js, «Несокрушимость») показал дефект —
состояние на объекте hero не переживает перезагрузку (после restore
эффект повторно доступен в тот же день). Задача: общий слой состояния
(«раз в день» + временные благословения на 1 день), который используют
ВСЕ последующие подзадачи эффектов (ни одна не хранит состояние сама);
состояние живёт в main.js и обязательных разделах сейва.

## Что сделано

1. **src/day.js** (+146; UMD-обёртка не ломается — функции добавлены в
   возврат factory). Функции размещены в day.js рядом с
   canUseToday/serializeDefeatedAt, а НЕ в src/building-effects.js —
   эти файлы принадлежат 000071 (он создаёт их как новые), создание их
   000072 гарантировало бы add/add-конфликт:
   * `serializeDayMap`/`restoreDayMap` — обобщение
     serializeDefeatedAt/restoreDefeatedAt на ключи 'x,y[:effectId]':
     целые координаты (могут быть отрицательными) + опциональный
     суффикс ':effectId' (без пробелов, ':' и ','), день — целое ≥ 1;
     прочее тихо отбрасывается (принцип 000029).
   * `grantBuff(buffs, source, day, kind)` — ЧИСТАЯ (новый массив,
     вход не мутируется); повтор того же (source, kind) — обновление
     дня (дублей нет), разные (source, kind) сосуществуют;
     невалидные записи отбрасываются.
   * `activeBuffs(buffs, day)` — активен, пока `buff.day >= day`
     (АБСОЛЮТНЫЕ дни — сейв снимок, fastForward без слушателей, 000031).
   * `buffMods(buffs, day)` → `{ damageMult, armor }`: активный
     'damage' → 1.05 (солнце, константа SUN_DAMAGE_MULT), активный
     'armor' → +1 (гора, MOUNTAIN_ARMOR). Множители ФИКСИРОВАНЫ на
     ВИД: два храма солнца → 1.05, а НЕ 1.05×1.05; две горы → +1, а
     не +2. Неизвестный kind игнорируется. Применение к формулам боя —
     000076; здесь — только чистые функции.
   * `restoreBuffs(saved, day)` — whitelist kind {'damage','armor'},
     source — 'x,y'; отбрасывает и «будущие» (day > clock.day —
     подделка), и «истёкшие» (day < clock.day): onDay-очистка при
     восстановлении НЕ пройдёт (fastForward не оповещает слушателей,
     000031). `serializeBuffs` — массив копий.
2. **src/main.js** (+71; diff ТОЛЬКО в state/save-секции по паттерну
   defeatedAt — осознанно, чтобы не конфликтовать с параллельными
   ветками, правящими drawSprites/HUD):
   * состояние: `buildingOncePerDay` (Map 'x,y:effectId' → день
     применения) + `buffs` (массив) — рядом с `defeatedAt`;
   * `collectSaveData`: два новых раздела data — `buildingOncePerDay`
     (через serializeDayMap) и `buffs` (через serializeBuffs);
   * `restoreFromSave`: каждый раздел — СВОЙ try/catch + явная
     проверка формы раздела (объект-не-массив / массив) с
     `console.warn` по имени раздела (restore-функции тихие — без
     этой проверки warn не был бы гарантирован) + кламп «будущих»
     дней (запись day > clock.day отброшена);
   * `clock.onDay`: очистка истёкших благословений (buff.day < day) —
     в начале колбэка, рядом с dueForRespawn.
   * «Сброс» «раз в день» ничего не сбрасывает — проверка
     `canUseToday(last, clock.day)` (без изменений, уже верна).
3. Версию сейва НЕ подняли (save.js не трогали): неломкое расширение
   v1, CURRENT_VERSION = 1, MIGRATIONS пустые, старый v1-сейв
   восстанавливается как есть без миграций (правило 000031,
   прецедент 000029 — quests/npcStocks).

## Решения и подводные камни (см. memory/000072-…)

1. **Функции в src/day.js, НЕ building-effects.js** — файлы
   building-effects.js/test.js принадлежат 000071 (создаёт их как
   новые); 000072 их НЕ создаёт (иначе гарантированный add/add-
   конфликт при старте 000071).
2. **Счёт по ЭФФЕКТУ, не по постройке**: ключ 'x,y:effectId'. Фонтан
   — исцеление с лимитом, монета — без (у неё флага `раз_в_день` в
   каталоге нет). Конвенция effectId: латиница, БЕЗ ':'/','/пробелов;
   каталог эффектов (000073+) обязан ей следовать — id с ':' или ','
   тихо отбрасывается (fail-open: эффект снова доступен, игра не
   ломается).
3. **Агрегация buffMods фиксирована на ВИД** (стак не умножает и не
   складывает): 000076 потребляет buffMods как есть.
4. **Дни — абсолютные** (сейв — СНИМОК): «будущие» записи
   buildingOncePerDay при restore отброшены (иначе canUseToday(99, 7)
   === true — эффект заблокирован на N дней); истёкшие баффы
   отброшены при restore (onDay-очистка не пройдёт — fastForward без
   слушателей). «Прошлые» записи dayMap держим — вредно не могут.
5. **Битые разделы**: restoreDayMap/restoreBuffs тихие (000029),
   поэтому warn на некорректную ФОРМУ раздела сделан явной проверкой
   в restoreFromSave (тесты требуют warn с именем раздела именно на
   'junk' строку).
6. **Момент «использовано» для потребителей (000071+)**: запись
   `buildingOncePerDay.set('x,y:effectId', clock.day)` + `saveNow()`
   СРАЗУ после действия (паттерн onChange → saveNow из 000029) —
   лимит не должен жить до beforeunload (краш между действием и
   закрытием — потеря лимита). Хелпер markDayUsed НЕ вводится:
   000071 работает со снимком `save.buildingOncePerDay` (интерфейс
   buildingActions { day, tile, hero, save }) напрямую.
