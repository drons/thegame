## Почему так разложено

* Каждое направление 000030 = ровно одна самодостаточная подзадача:
  своя область файлов, свой набор тестов, независимый коммит.
* Каждая подзадача содержит: текущее состояние (с фактами из кода),
  проектное решение «по умолчанию» (там, где есть выбор), список файлов,
  требования к тестам, ограничения и зависимости.
* Граница «ядро/UI» выдержана по стилю проекта: игровая логика —
  в тестируемом ядре (combat.js, sprites.js, новый combat-keys.js,
  global-settings.js), отрисовка — в browser-модуле combat-ui.js.

## Ключевые проектные решения, зафиксированные в подзадачах

* 000047: спрайты — те же ассеты (phlogiston + 6 базовых видов мобов),
  новая чистая функция mobSpriteKind(mobId) для всех 36 типов мобов;
  фолбэк на цветные маркеры обязателен; rAF-цикл только в UI-слое;
  спрайт моба — на весь его прямоугольник (000040, до 3×3).
* 000048: реальный конфликт — KeyA в бою = «Удар» (в мире KeyA =
  влево), т.е. на русской раскладке физический Ф не двигает влево.
  Аудит по правильной модели e.code/e.key (src/controls.js, 000028):
  кириллических code не существует (записи KeyЦ/Ы/Ф/В — мёртвый код),
  русские «дубли» — те же физические клавиши; новые ключи только
  Л=KeyK и Г=KeyU. Решение: WASD/ЦФЫВ в бою = движение как в мире,
  «Удар» → KeyJ; единая таблица в новом UMD-модуле src/combat-keys.js
  + тесты.
* 000049: 11 фонов — 5 проходимых террейнов мира (бой начинается только
  на проходимых тайлах: SAND/GRASS/FOREST/HILL/SWAMP) + 5 типов
  подземелий (dungeon-бой тоже через combatUI) + fallback; фон
  выбирается чистой функцией, пути — в allAssetPaths().
* 000050: формулировка «препятствия на фоновом SVG» истолкована как
  отдельный SVG-спрайт поверх общего фона (детерминированная генерация
  через c._rng, параметры в global-settings.js, BFS-достижимость
  мобов, запрет на клетках старта; с учётом 000040 — препятствия
  обходят стартовые прямоугольники мобов до 3×3). Вариант «уникальный
  SVG на каждый бой» зафиксирован как fallback-вариант, если вид
  будет хуже.
* 000036: игровая семантика НЕ меняется (игрок первым, затем мобы в
  порядке units) — ядро лишь делает порядок наблюдаемым
  (buildTurnOrder, turnOrder, turnIndex) + DOM-строка токенов.
* 000037: canDoAction(c, action) — чистая «зеркальная» проверка без
  побочных эффектов; tooltip с причиной; по клавише — reason в лог.
* 000038: DOM-полоса в .combat-side + миниполоса на поле; чистая
  функция hpBarColor(frac) в sprites.js.

## Зависимости и рекомендуемый порядок выполнения подзадач

* Независимы (можно параллельно, в т.ч. в разных git worktree):
  000048, 000036, 000037, 000038 — у каждой свои файлы и тесты.
* 000049 — фундамент визуального стека; 000047 и 000050 рисуются
  поверх фона (без 000049 работают в фолбэке, но лучше после).
* 000048 ↔ 000037 — пересечение (обратная связь по «мёртвым» клавишам):
  сначала 000037 (canDoAction), затем 000048 использует её.
* Рекомендуемый порядок: 000037 → 000036 → 000048 → 000038 →
  000049 → 000047 → 000050.

## Побочные находки (включены в подзадачи)

* Бад лога исцеления: playerSpell('heal') логирует ОБЩЕЕ HP
  (P.heal возвращает c.hp), а не восстановленное количество —
  фикс закреплён в 000037.
* Кнопка «Предмет [T]» сейчас не может сработать: c.invItem() без
  itemId всегда «выберите предмет из инвентаря» (нет UI выбора) —
  в 000037 только корректный дизейбл, меню выбора — отдельная
  потенциальная задача.
* Мобы stepToward/stepAway и playerMove не знают о препятствиях —
  учтено в 000050.
