## Что сделано

### 1. Продажа по типу (src/items.js)

`sellAccepts(shop, itemId)` — приоритеты P1 не-магазин (null-виды,
в т.ч. барахолка 47) → false; P2 богатство 3 (универсам) → true;
P3 floor (kind ∈ «видов» лавки) → true; P4 таблица `SELLABLE_BY_KIND`
(kind → магазины сверх «видов»: shield/tool→0, ring→1, spell_scroll/
resurrection_scroll/craft_scroll/artifact→3). Таблица — только
ДОБАВКА: прежние отказы бит-в-бит, причина «магазин не скупает такие
предметы» не менялась. `sellItem` — гейт sellAccepts; фильтр строк
скупки вкладки «Магазин» — `src/ui-tab-shop.js` (тот же sellAccepts).

Цена вне ассортимента — прежняя формула sellPrice; страховочная база
по типу `SELL_BASE_VALUE` для нечисленного `value` (дыра валидатора
NaN достижима — пин T5 divergedBoot-пробами, на диске таких нет).

### 2. Выкуп следующего обновления (src/items.js + src/main.js)

Модульный магазин предзаказов `shopPreOrders` (ключ `'C:x,y'`),
поставщик следующего цикла регистрирует main.js (стоик лагеря:
`makeCampShop(x, y, day + respawn_days, …)` — ТЕМ ЖЕ детерминированным
вызовом, 0 новых RNG). `buyItem`: нет в текущем стоке → если позиция
есть в net-стоке следующего цикла — покупка по обычной цене,
{ ok, ahead, message: «Забронировано к следующему обновлению: … » },
в текущем сток предмет НЕ фигурирует; нет и там — каноничный
«нет в наличии». `campShopFor` при refresh вызывает
`consumeShopAhead` (max(0,…) clamp, полное гашение ключа).
Сейв v1 без миграции: верхнеуровневый раздел `shopPreOrders`
(serialize/restore с санацией, absent → {}), MIGRATIONS == [] цел.
