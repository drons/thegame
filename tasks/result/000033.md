# Отчёт: задача 000033 — плавное передвижение персонажа

Статус: выполнено (красные тесты → реализация → адверсариальное ревью).
Полный набор тестов: **465 pass / 0 fail** (красная стадия по коммиту
5993968: 438 pass / 4 fail — все 4 падения только по новым
требованиям: модуль и подключение ещё не существовали). Игровая логика
(tryMove, бой, сейвы) НЕ меняется: player.x/y по-прежнему меняется
целым тайлом, изменились РЕНДЕР (глейд) и камера (dt-сглаживание) +
интервал шага теперь учитывает «Ловкий шаг» (закрыт SPEC-пробел
«Ловкость → Скорость перемещения по карте», SPEC.md строки 325/367).

## Что сделано

1. **src/motion.js (новый, чистый UMD-модуль, без зависимостей,
   паттерн controls.js — тестируется в node)**:
   * примитивы: `clamp01` (NaN → 0 = начало глейда, ±∞ → 0/1),
     `lerp`, `lerpPos` (t клампится в [0,1] — не вылетает за
     отрезок), `easeInOut(t) = t²(3−2t)` (smoothstep — плавный
     старт/финиш);
   * `stepProgress(now, start, interval)` — прогресс глейда
     p ∈ [0,1]: кламп за концом (без отката), interval<=0 — мгновенно,
     NaN-время → 0;
   * `cameraStep(cur, target, dt, tau) = cur + (t−cur)·(1−e^(−dt/tau))`
     — экспоненциальное сглаживание, НЕЗАВИСИМОЕ от fps (безпамятность
     экспоненты: 2 кадра по 8 мс ≡ 1 кадр 16 мс; перелёта через
     цель нет по построению, k ∈ (0,1)); `CAM_TAU_MS =
     1000/60/−ln(0.8) ≈ 74.7 мс` подобрано так, что при 60 fps
     коэффициент ≈ 0.2/кадр — старое ощущение камеры сохраняется, а
     при 144 Гц то же движение за то же РЕАЛЬНОЕ время (раньше 0.2
     на КАДР: при 144 Гц камера ловила цель в ~2.4 раза быстрее);
   * `moveIntervalMs(base, mult)` — «Ловкий шаг»
     (derived().moveSpeedMult = 1 + pct('step'), src/player.js:223):
     mult > 1 — интервал короче (base/mult), кламп
     `MIN_MOVE_INTERVAL_MS = 60 мс` СНИЗУ, и кламп НИКОГДА не
     удлиняет шаг сверх базы (moveIntervalMs(30, 1e6) = 30);
     mult < 1 / нечисло → база (навык только ускоряет);
   * `createMover({x, y, intervalMs})` → `{position, step, teleport}`:
     глейд from→to за интервал (с easing'ом), `position(now)` —
     ДРОБНАЯ тайловая позиция (до шага — старт, в глейде —
     lerp(easeInOut(p)), после — цель без отката), interval передаётся
     НА ШАГ (динамическая скорость), `teleport(x,y)` — мгновенный
     снап с отменой текущего глейда.
2. **src/main.js (клей)**:
   * `mover` создаётся при загрузке (guard `G.createMover` — без
     motion.js игра деградирует в старое поведение); после успешного
     tryMove() — `mover.step(prevPos → player, now, stepMs)`;
   * **одна дробная точка рендера на кадр**: `rp = renderPos(now)`,
     оба слоя (WebGL-ромб `buildFrame(rp)` и спрайт
     `drawSprites(now, rp)`) рисуют rp + 0.5 — фолбэк-слой и спрайт
     не расходятся (раньше ромб «прыгал» из центра тайла в центр);
   * камера: `updateCamera(now)` — dt из разницы rAF-таймстампов
     (первый кадр dt=0), G.cameraStep + CAM_TAU_MS; fallback на старый
     коэффициент 0.2/кадр, если motion.js не загрузился;
   * **телепорт-снапы (4 места)**: старт после findSpawn/
     restoreFromSave (иначе «скользит» от точки создания мувера до
     спавна), restoreFromSave (позиция сейва), бой onEnd при
     outcome !== 'victory' (побег/смерть — назад на prevPos, иначе
     спрайт скользит обратно через поле боя);
   * интервал шага `stepMs = G.moveIntervalMs(140,
     derived(hero).moveSpeedMult)` — одновременно гейт шага и
     длительность глейда; без навыка (mult = 1) ровно 140 мс, как
     раньше;
   * `__game.state.playerRender` — дробная позиция рендера для
     ручной/смоук-проверки.
3. **index.html**: `<script src="src/motion.js"></script>` между
   save.js и main.js — ОБЯЗАТЕЛЬНО до main.js (UMD-ловушка, паттерн
   000018/000038: main.js снимает G = globalThis.Game один раз при
   загрузке); порядок зафиксирован в tests/index-order.test.js.
4. **Окно walk/idle 260 мс НЕ трогалось** (косметика): при базовых
   140 мс герой всегда в walk-анимации (норма); при динамических
   60–140 мс окно по-прежнему всегда в walk — визуально корректно.
