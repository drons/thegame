## Что сделано

1. **Ядро (src/combat.js)**:
   * `c.obstacles` — Set строк 'x,y' непроходимых клеток; создаётся в
     createCombat и заполняется `generateObstacles` РОВНО между placeUnits
     (нужны стартовые прямоугольники мобов — reserved) и refillPools;
   * генерация ТОЛЬКО через c._rng: target = min + floor(rng × (max−min+1))
     — один бросок; кандидат — два броска (x, y); последовательность
     бросков закреплена (детерминизм алгоритма); при max_frac ≤ 0 бросков
     НЕТ — поток RNG совпадает с боем без генерации (критично для
     снэпшотов);
   * min/max = round(frac × area), live-чтение SETTINGS (паттерн
     level_delta_max), guard max<min;
   * reserved: старт игрока + ВСЕ клетки стартовых прямоугольников всех
     мобов (включая 2×2/3×3 — не только якорь);
   * достижимость: BFS из старта игрока по не-препятствиям (мобы
     игнорируя) обязан достигать ≥1 клетки стартового прямоугольника
     КАЖДОГО моба; нарушение — только что добавленная клетка удаляется;
     лимит MAX_OBSTACLE_TRIES = 500 — при исчерпании меньше препятствий
     (разрешённый фолбэк п. 3 задачи: поле играбельно, плотность < min);
   * `reachableCells(c)` — чистая BFS-функция, экспорт для тестов;
   * блокируется ТОЛЬКО движение: playerMove → { ok: false, reason:
     'препятствие' } (порядок reason: «стена» → «препятствие» → «тут стоит
     моб»); stepToward/stepAway — через rectFree (одна точка проверки для
     обоих: мобы не проходят сквозь камни и не встают на них);
   * атаки и заклинания (в т.ч. дальние) летают ПОВЕРХ камней — линий
     видимости в модели нет (unitDist — Манхэттен); зафиксировано в
     заголовке модуля.
2. **Настройки (src/global-settings.js)**: combat_obstacle_min_frac = 0.10,
   combat_obstacle_max_frac = 0.20 — доля клеток поля (для 7×7: 5..10
   клеток); единый источник, live-чтение.
3. **Спрайты (src/sprites.js)**: OBSTACLE_DIR/OBSTACLE_SPRITES (3 файла),
   чистая функция `obstacleSprite(x, y)` = (x*3 + y*5) % 3 (тот же приём,
   что фазы кадров: соседи — разные виды; все 3 вида на 3×3);
   нецелое/отрицательное → null (рендерер — фолбэк-квадрат); пути — в
   allAssetPaths() (main.js сам кьюит их в spriteLoader). Литерал без
   зависимости от combat.js (паттерн MOB_SPRITE_KINDS).
4. **Слой UI (src/combat-ui.js)**: препятствия рисуются строго ПОСЛЕ сетки
   и ДО юнитов; картинка — из spriteLoader КАЖДЫЙ render (паттерн фона
   000049: поздняя загрузка подхватывается без рестарта); G.obstacleSprite
   — guard (УМД-ловушка «G снимается один раз», паттерн hpBarColor);
   фолбэк — тёмный квадрат #3a4150 (CELL-6, отступ 3 px): непроходимость —
   правило ядра, поэтому без ассетов клетка остаётся читаемой; итерация по
   Set (порядок вставки — детерминирован).
5. **Ассеты (assets/combat/obstacles/)**: rock.svg, boulder.svg,
   bush.svg — 3 универсальных спрайта 48×48 (viewBox), нейтральная
   палитра (серые + приглушённая зелень) — читаются на всех 11 фонах
   000049; перенесены готовые из старой ветки задачи (решение
   пользователя, побайтовая идентичность проверена).
6. **SVG-гейт (tests/svg.test.js)**: EXPECTED_SVG_BY_DIR + 'combat/
   obstacles': 3 (итого 275 файлов после объединения с chest.svg из
   000067).

## Ревью (адверсариальное)

Найденный при анализе нюанс закреплён тестами/комментариями: жадный ИИ
мобов (stepToward) не умеет обходить препятствия — моб за камнем стоит
(это зафиксированное поведение задачи: «если некуда — стоят»); deadlock
возможен только для тестового autoPlay, поэтому баланс-сценарии снимают
препятствия явно. Атаки поверх камней — осознанное упрощение модели
(задокументировано в заголовке combat.js и в memory).

## Решения (детали в memory)

* Решение (б) 000030 подтверждено: отдельный спрайт-слой поверх общего
  фона, не процедурный «запечённый» фон на бой.
* Препятствия блокируют только движение; атаки/заклинания — поверх.
* Неопроходимость — правило ядра, визуал — отдельный слой с фолбэком.
* Порядок бросков c._rng закреплён: генерация строго между placeUnits и
  refillPools; при frac 0/0 поток RNG совпадает с боем без генерации.
* Фолбэк при лимите попыток (500) — меньше препятствий (допустимая
  плотность < min), поле всегда играбельно.
* По решению пользователя ребейз старой ветки не делался: ветка удалена,
  работа выполнена заново напрямую с нового мастера ae0b26d (конфликтов
  по построению не возникло); SVG-спрайты перенесены готовые; красная
  фаза проверена (15 падающих → 917/917 после реализации).
