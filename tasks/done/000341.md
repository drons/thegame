Оптимизация рендера C: cap tileCache под размер вьюпорта против FIFO-trэш (RENDER-OPTIMIZE §5C)

## Цель

Движение персонажа = miss-кадр на каждом пересечении тайла; при худшем вьюпорте
(z=4, 1920×1080 — N≈131k тайлов) cap `tileCache` 65536 трэшится FIFO и каждая
miss-пересборка содержит ~65k синхронных регенераций `tileAt` (fbm/noise) на
main thread — главный анти-jank ходьбы на низком зуме. Поднять (или сделать
адативным) cap так, чтобы pan/movement-кадры стали чистыми lookup'ами.

## Знания (вынесены из RENDER-OPTIMIZE.md, анализ 2026-11-08)

* `tileCache` — кэш тайлов мира в src/map.js (JSDoc `@param {number}
  [maxSize=65536]` ~:1208 — пересчитать символом `maxSize`/класса кэша;
  в документе был якорь map.js:1203, номера дрейфуют).
* `tileAt` детерминирован (чистая процедурная генерация fbm/noise) → при смене
  FIFO-порядка вытеснения содержимое бит-в-бит идентично; меняется только
  порядок evict.
* Пинов tileCache-в-`frame()` в тестах НЕТ (проверено анализом 000276 §7);
  изолированные tileCache-тесты — tests/map.test.js (проверить в анализе, пинит
  ли maxSize — тогда честный ре-пин по новому значению, не ослабление).
* НЕ путать с `fpCache`/`nmCache` (тоже 65536, map.js ~:944/:1017 — отдельные
  кэши fp/nm, не трогать).
* Память: 131k тайл-объектов ≈ несколько MB — приемлемо (§5C).
* Оценки (§5.1): Эффект 6, Простота 8, Риск 3; ДВИЖЕНИЕ (§5.2): 10 — наравне
  с A; steady-кадры не трогает (hit-ветка frameTiles не ходит в tileCache).
* Решение анализа: константа (напр. 163840/262144 — под worst-case зум) vs
  адаптивный cap от размера вьюпорта; довод адаптивности — не платить памятью
  на малых окнах; довод константы — детерминизм поведения/тестов.

## Что сделать

1. src/map.js: cap tileCache под worst-case вьюпорт (решение «константа vs
   адаптивный» — в анализе, с обоснованием и памятью).
2. Красные тесты (tests/map-tilecache-cap-000341.test.js, kind=node):
   T1 cap >= N худшего вьюпорта (пересчёт N для фиксированного окна/z — пин);
   T2 симуляция ходьбы/pan через > 65536 уникальных тайлов: количество
   генераций tileAt ограничено первым заполнением (spy-счётчик генераций;
   до правки — красный: генераций ≈ числу запросов, после — только miss на
   новых координатах);

   (бит-в-бит сравнение двух прогонов different order);
   T4 evict при превышении cap работает (размер кэша не растёт бесконечно);
   T5 регресс: tests/map.test.js tileCache-секции зелёные (+re-pin если пинует).
