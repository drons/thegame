Ассортимент магазинов: единый источник (дизайн + реализация)
(подзадача 000053)

Родительская: 000053 (аудит дублирования данных; принцип — JSON в
assets/ первичный источник)

Цель: убрать третью копию контента магазинов. Сейчас «что продаёт
магазин» задано в двух местах с РАЗНЫМИ семантиками: в assets/buildings
— поле `ассортимент` (decorative проза: «мечи», «луки», «посохи»,
«щиты» — кодом НЕ читается), а в src/items.js — shopKindsFor
(~строка 476) — таблица map.js BUILDING_TYPES (int 0..12) →
ITEM_KINDS (weapon/armor/potion/food/reagent/skill_book) — её кодом
ЧИТАЕТ makeShop (детерминированный сток). Привести к одному источнику.

Состояние сейчас (сверено с кодом master)
* src/items.js: shopKindsFor(buildingType): WEAPONS_SHOP→['weapon'],
  ARMOR_SHOP→['armor'], APOTHECARY→['potion','food'],
  MAGIC_SHOP→['reagent','skill_book'], TAVERN→['food','potion'],
  остальное → null (не магазин).
* assets/buildings: у 5 магазинов (map_index 0..4) `ассортимент` —
  список русских слов-категорий (проза), не совпадающий с ITEM_KINDS
  и не читаемый кодом.
* UI: «магазин, богатство N/3» (ui.js ~240) — от богатства, не от
  ассортимента — менять НЕ нужно.

Ключевое проектное решение (сначала дизайн, затем реализация)
Сопоставить прозу `ассортимент` каталога с ITEM_KINDS shopKindsFor и
выбрать ОДИН источник. Варианты:
* (а) ПREFERRED: в каталог — функциональное поле (особые_параметры —
  свободный объект): `особые_параметры.виды` = [id из ITEM_KINDS]
  (weapon/armor/potion/food/reagent/skill_book) у 5 магазинов;
  проза `ассортимент` остаётся описательной (или убирается дубль —
  решение в задаче). shopKindsFor читает `виды` из каталога (лениво,
  паттерн 000055: items.js грузится ПОСЛЕ map.js, 297, ДО buildings.js,
  298 — каталог бери лениво через root.Game, как map.js; vm-тесты —
  гарды).
* (б) Оставить функциональную таблицу в коде (items.js), а каталог
  сделать не дублирующим: `ассортимент` — либо убрать, либо
  тест-связь «проза ↔ виды» (слабее — проза не функциональна).
Выбрать (а) по умолчанию; аргументировать в SPEC/memory.

Работа
1. Дизайн: таблица соответствия (проза `ассортимент` ↔ виды
   shopKindsFor) по 5 магазинам; решение (а)/(б); зафиксировать.
2. Реализация выбранного варианта: assets/buildings (5 записей
   магазинов — `особые_параметры.виды`, если (а)); src/items.js —
   shopKindsFor из каталога (гарды: без каталога/в vm — текущая
   таблица как фолбэк, чтобы бой/торговля работали в песочницах).
3. SPEC.md: «Постройки → Магазины» (и/или «Предметы → Торговля») —
   единый источник ассортимента; проза `ассортимент` — статус.
4. Проверить UI-тексты: «магазин, богатство N/3» (ui.js) и строки
   «Здесь: …» (main.js) — значения БЕЗ ИЗМЕНЕНИЙ (ассортимент в них
   не участвует; имена — зона 000055, здесь не трогать).

Тесты
* RED (до правки): нет связи `ассортимент`/`виды` каталога с
  shopKindsFor (после — есть).
* shopKindsFor(5 магазинов) ≡ `особые_параметры.виды` каталога
  (все 5 int-индексов); не-магазины → null (без изменений).
* makeShop: сток на фиксированных (x, y, buildingType, wealth) —
  golden БЕЗ ИЗМЕНЕНИЙ (детерминизм торговли; seed — hash2, 000009-паттерн).
* vm-песочницы (items.test.js): без каталога — фолбэк-таблица,
  поведение идентично.
* Регрессия: npm test — все зелёные.

Файлы: assets/buildings (5 записей магазинов, если вариант (а)),
src/items.js, tests (items, buildings), SPEC.md, memory/.

Ограничения
* Делать ПОСЛЕ 000055 (те же assets/buildings «картовые» записи;
  000055 вводит генерацию buildings.js и `название_карты` — не
  конфликтовать, ре-база).
* Торговля (цены, богатство, сток, seed) — БЕЗ ИЗМЕНЕНИЙ; только
  источник видов товаров.
* Перенумерации id построек/предметов НЕТ (сейв-совместимость,
  memory/000031-save-versioning.md).
* UI-текст «магазин, богатство N/3» (ui.js ~240) не меняется.
