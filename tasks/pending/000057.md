Стационарные группы мобов: каталог assets/mob_groups (JSON) + схема
(подзадача 000053)

Родительская: 000053 (аудит дублирования данных; принцип — JSON в
assets/ первичный источник)

Цель: данные о 7 стационарных группах мобов сейчас разложены по трём
модулям (map.js + combat.js + sprites.js) без единого источника —
вынести в каталог assets/mob_groups (JSON + schema.json) по устоявшему
паттерну «каталог в assets + JS-фолбэк + синхронизация + тесты».

Состояние сейчас (сверено с кодом master)
* src/map.js: MOB_GROUP_TYPES (7 id + NONE), MOB_GROUP_COUNT=7,
  MOB_GROUP_NAMES (строки: «орочий лагерь», «орочий набеги», …).
  Генерация: hash2(x,y,seed) % MOB_GROUP_COUNT.
* src/combat.js: GROUP_RECIPES (по каждому типу — состав группы:
  список mob-ид и/или count:[min,max], например 3 wolf_pack —
  {count:[3,6], mobs:['wolf']}).
* src/sprites.js: MOB_KINDS (groupType → базовый спрайт-вид MOB_FRAMES,
  ~строка 91) — третья таблица на те же 7 типов.
* assets/ — каталога мобов-групп НЕТ; данные только в коде.

Ключевое проектное решение
* Каталог assets/mob_groups: 000001..000007.json + schema.json
  (валидатор — tests/json-schema.js, ограниченный набор ключей,
  паттерн assets/npc/schema.json; имена полей русские, стиль
  assets/buildings):
  * `id` — целое 1..7, совпадает с номером файла;
  * `название` — имя группы (из MOB_GROUP_NAMES map.js);
  * `состав` — рецепт из GROUP_RECIPES combat.js: `{мобы: [id, …]}`
    и/или `{число: [min, max]}` (id мобов — из assets/mobs, проверяется
    тестом);
  * `спрайт` — базовый вид из MOB_FRAMES (из MOB_KINDS sprites.js);
  * (опц.) `особые_параметры` — свободный объект (лидер/агрессивность,
    если понадобится).
* JS-фолбэк-модуль (src/mob-groups-data.js или аналог — решение в
  задаче) — генерируемая/ручная копия каталога под file:// (JSON не
  fetch'ится, ограничение SPEC). ВАЖНО: фолбэк-модуль БЕЗ взаимных
  require (паттерн COMBAT_BG_DUNGEON из 000049: sprites.js НЕ тянет
  dungeon.js намеренно — vm-песочницы combat-ui/sprites не грузят
  dungeon.js/map.js-зависимости). Потребители (map.js, combat.js,
  sprites.js) читают данные ЛЕНИВО/через гарды, как в 000055.
* Синхронизация: по образцу sync-npc-data.js (скрипт + npm-скрипт
  sync:mobgroups, идемпотентный, CI-готовый — 000054); если 000055/000059
  уже задали единый интерфейс sync-скриптов — следовать ему.

Работа
1. assets/mob_groups: 7 JSON-файлов + schema.json (данные — из
  MOB_GROUP_NAMES/GROUP_RECIPES/MOB_KINDS — 1:1, без изменений смыслов).
2. JS-фолбэк-модуль + (если выбран генерируемый путь) синхронизация.
3. src/map.js: MOB_GROUP_TYPES/COUNT/NAMES — из каталога (лениво,
   как в 000055); генерация hash2 % COUNT — без изменений.
4. src/combat.js: GROUP_RECIPES — из каталога (лениво/гарды; бой должен
   работать и в vm-песочнице без каталога — фолбэк-модуль).
5. src/sprites.js: MOB_KINDS — из каталога (гарды, без require
  combat.js/dungeon.js — паттерн 000049).
6. SPEC.md: НОВЫЙ раздел «Архитектура хранения групп мобов»
   (каталог, схема, фолбэк, синхронизация, тесты) по образцу
   «Архитектура хранения NPC».

Тесты
* Валидация каталога схемой (tests/json-schema.js — паттерн npc).
* Зеркало ≡ JSON (deepEqual фолбэк-модуль ↔ файлы каталога).
* id мобов в `состав` ∈ assets/mobs (все 7 групп; неизвестный id —
  ошибка).
* Сверка с текущим кодом (миграционный тест, пока есть старые таблицы —
  либо их удаление по факту вывода из каталога): составы/имена/виды

* Golden: составы групп на фиксированных координатах/сиде —
  детерминизм (как в 000055/000058).
* vm-песочницы: tests/sprites.test.js, combat-ui — без каталога/
  зданий работают (гарды).
