Оптимизация рендера B: subset-списки по слоям вместо полных сканов frameTiles (RENDER-OPTIMIZE §5B)

## Цель

Каждый rAF-кадр выполняется 4 полных прохода по frameTiles (≈5 сканов суммарно
с rebuild: текстуры/вода/декор/лут, якоря построек через Set, агро-окружности,
мобы) ради горстки объектов; худший случай ~5×131k итераций/кадр при z=4.
Строить при пересборке frameTiles субсписки слоёв и на хите кэша итерировать
их, а не полный массив.

## Знания (вынесены из RENDER-OPTIMIZE.md, анализ 2026-11-08)

* frameTiles — single-entry кэш (000276, memory/000276-frame-tiles-cache.md):
  ключ (x0,y0,x1,y1,worldVersion,exploredVersion) (main.js ~:3749–3756,
  пересчитать символом `frameTilesKey`/`exploredSize`); на хите массив
  переиспользуется; legacy-гейт 000176 выполняется каждый кадр и на хите
  (после 000339 — пропускается в steady).
* Проходы-потребители (main.js, строки дрейфуют — якорь `for (const t of
  frameTiles)` ~:3759/:3951/:4005/:4053/:4083): текстуры/вода/декор/лут;
  якоря построек (через Set); агро-окружности; мобы.
* Субсписки для построения: waterTiles, decorCandidates, lootCandidates,
  anchors, mobGroups.
* Live-фильтры collectedLoot / defeatedAt / groupVisible ОБЯЗАНЫ остаться в
  петле отрисовки (они дешёвые и динамические; вынос в момент сборки =
  устаревший subset-призрак собранного лута/скрытой группы).
* Row-major порядок внутри субсписка сохраняется → draw бит-в-бит
  (пины CC-2 z-порядка и LM/000042 держатся; носители CC-* —
  tests/chunk-render.test.js, tests/frame-tiles-cache-000276.test.js).
* Инвалидация субсписков: сбор лута (collect), смена дня (defeatedAt), respawn
  мобов — bump версии КЛЮЧА субсписков по паттерну `bumpWorldVersion`
  (main.js ~:4618; контракт версий 000276 §3).
* Оценки (§5.1): Эффект 7, Простота 5, Риск 4; для движения (§5.2) — 8
  (сканы якорей/агро/мобов/лута на каждом movement-кадре).
* Эффект: худший steady-кадр с 5 полных сканов до 1 скана (или 2, если A
  ещё не смержена — плюс гейт) + горстки кандидатов.

## Что сделать

1. При пересборке frameTiles собирать субсписки (waterTiles, decorCandidates,
   lootCandidates, anchors, mobGroups) в row-major порядке обхода.
2. На хите кэша — iterate субсписки; live-фильтры остаются в петле; версии
   субсписков инвалидировать bump'ом по collect/день/respawn.
3. Красные тесты (tests/render-frame-subsets-000340.test.js, kind=node):
   T1 эквивалентность: последовательность вызовов отрисовки через субсписки
   (с live-фильтрами) == полная покомпонентная golden-последовательность
   полного скана на fixture-кадре (бит-в-бит);
   T2 row-major субсписков (порядок id в субсписке = возрастание тайлового
   index — пин z-порядка);
   T3 collect лута → bump → subset пересобран, призрак не рисуется;
   T4 смена дня (defeatedAt) / respawn → bump/фильтр корректны (группа не
   «воскресает» без инвалидации);
   T5 hit кэша frameTiles → субсписки переиспользуются без пересборки
   (счётчик сборок);
   T6 регресс CC-2/LM z-порядка на фикстуре;
   T7 live-фильтры работают БЕЗ rebuild (скрытая группа исчезает на хите).
