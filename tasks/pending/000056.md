Единая таблица террейнов (имена, проходимость, цвета)
(подзадача 000053)

Родительская: 000053 (аудит дублирования данных; принцип — JSON в
assets/ первичный источник; данные мира — единая таблица)

Цель: на одни 8 террейнов существует ТРИ таблицы (имена, проходимость,
цвета), разнесённые по четырём модулям — собрать в единую таблицу
в src/map.js и выводить из неё все потребители.

Состояние сейчас (сверено с кодом master)
* src/map.js: TERRAIN_NAMES (строки имён 0..7) + PASSABLE (Set
  проходимых).
* src/buildings.js: T (литералы имён террейнов: «песок, трава, лес,
  холмы, болото»…) + ALL_PASSABLE + DENSE — СОБСТВЕННЫЕ копии имён и
  проходимости (дублируют map.js).
* src/sprites.js: TILE_BASE (hex-цвета 8 террейнов, ~строка 37) —
  «родственные» с TILE_COLORS, но отдельная таблица (коммент в коде).
* src/main.js: TILE_COLORS (RGB-цвета 8 террейнов, ~строка 44).
* Третья копия имён — enum `допустимые_тайлы` в
  assets/buildings/schema.json (песок/трава/лес/холмы/болото);
  имена файлов assets/tiles/*.svg (TILE_FRAMES в sprites.js) — тоже
  содержат имена террейнов. НИ ОДИН тест не связывает эти таблицы.

Ключевое проектное решение
Единственная таблица террейнов — в src/map.js:
  TERRAIN = { [id]: { имя, passable, dense, base:<hex>, rgb:[r,g,b] } }
(имена и проходимость — как сейчас; dense — из DENSE buildings.js;
цвета — объединить TILE_BASE (hex) и TILE_COLORS (rgb), согласовать
значения). Все остальные модули — ПОТРЕБИТЕЛИ, без собственных
литералов:
* buildings.js: T/ALL_PASSABLE/DENSE — из map.js (buildings.js грузится
  ПОСЛЕ map.js в index.html — прямое обращение допустимо; для
  vm-тестов, где buildings.js грузится с map.js, — порядок перlin→map
  сохранён; если нужен buildings.js без map.js (тесты) — гарды/лениво);
* sprites.js: TILE_BASE — из map.js (sprites.js грузится ПОСЛЕ map.js,
  318 > 294; vm-песочница sprites.test.js грузит map.js — проверено);
* main.js: TILE_COLORS — из map.js (main.js последний, 323).
Формат вывода: потребители, которым нужен hex, — hex; кому rgb — rgb;
одна таблица, два представления (или hex + чистая функция hex→rgb —
решение в задаче, зафиксировать в SPEC).

Работа
1. src/map.js — единая таблица (см. выше) + экспорт (TERRAIN целиком
  либо TERRAIN_NAMES/PASSABLE как производные + TERRAIN_COLORS/
  TERRAIN_DENSE).
2. src/buildings.js — T/ALL_PASSABLE/DENSE из map.js, литералы имён
  убрать (исключения: если buildings.js нужен автономным для vm —
  ленивое получение, паттерн 000055).
3. src/sprites.js — TILE_BASE из единой таблицы.
4. src/main.js — TILE_COLORS из единой таблицы.
5. SPEC.md, раздел «Карта мира» (или «Архитектура хранения типов
  зданий» — по месту): единая таблица террейнов в src/map.js;
  потребители без собственных копий.

Тесты
* RED (до правки падает): отсутствие литералов имён террейнов в
  buildings.js (grep-тест по содержимому файла, паттерн — как
  проверяются маркеры генерации).
* Сквозная связь имён: `допустимые_тайлы` ВСЕХ записей assets/buildings
  ⊆ keys(имён таблицы) (сейчас не проверяется — enum схемы, имена в
  map.js и T в buildings.js ничем не связаны); TILE_FRAMES/имена файлов
  assets/tiles/*.svg ↔ таблица (каждый террейн с файлом текстуры —
  есть в таблице).
* Цепочка потребители≡таблица: T/ALL_PASSABLE/DENSE (buildings.js),
  TILE_BASE (sprites.js), TILE_COLORS (main.js) deepEqual соответствующим
  полям единой таблицы (в node-ветках).
* Детерминизм: генерация мира (perlin→map) не меняется — golden
  tileAt (fixed seed) идентичен (как в 000055).
* Регрессия: npm test — все зелёные (в т.ч. vm-песочницы).

Файлы: src/map.js, src/buildings.js, src/sprites.js, src/main.js,
tests (map/buildings/sprites), SPEC.md, memory/.

Ограничения

  buildings.js; 000055 уже выводит данные map.js из каталога).

  последовательно, по возрастанию пересечения.

  согласование данных.

  (map.js должен грузиться без buildings.js/sprites.js).
