# Архитектура хранения подземелий
Данные о 5 типах подземелий (раздел «Входы в пещеры») хранятся в
каталоге `assets/dungeons`:
 * Один тип подземелья — один JSON-файл: `000001.json`, …,
   `000005.json`. Файл `0000NN.json` хранит `id` = NN−1, то есть значения
   `DUNGEON_TYPES` 0..4 (CAVE, CRYPT, RUINS, DROWNED, ABYSS).
   Перенумерация ЗАПРЕЩЕНА: фон боя `assets/combat/bg` выбирается именно
   по этим числам (задача 000049), а `DUNGEON_TYPES` — часть публичного
   API `src/dungeon.js`.
 * Структура файла закреплена в JSON-схеме `assets/dungeons/schema.json`
   (тот же ограниченный набор ключей валидатора, что и у остальных
   каталогов — задача 000015; русские имена полей, стиль
   `assets/buildings/schema.json`):
   * `id` — целое 0…4, совпадает с номером файла минус 1; множество id
     по файлам — ровно {0..4} (уникальность схемой не выразима —
     проверяется тестом и sync-скриптом);
   * `название` — имя типа (кодовый регистр — строчный: строки
     HUD/логов не меняются);
   * `мобы` — список id мобов из каталога `assets/mobs`;
   * `предметы` — список id предметов из каталога `assets/items`;
   * `размер` — БАЗОВЫЙ размер лабиринта в клетках (квадрат) — глубина 1
     (глубина — целое ≥ 1, первый этаж = 1, код `d.depth`); рост этажей —
     формулой в `src/dungeon.js`: `W = min(63, round(размер·1.1^(глубина−1)))`,
     cap 63 — решение 000153.02 (JSON-каталог хранит базу; 63 — CAP схемы,
     не база).
   * Сид этажа `d.seed` — функция (координат входа, шумов Перлина,
     assets/map.png, глубины): глубина 1 — от координат, глубины ниже —
     от сида формы первого этажа + глубина (детерминированно, без rng —
     000153.02); содержимое (мобы, сундуки, залежи) — от `d.seed` +
     количества опыта персонажа, т.е. зависит от глубины (000153).
   * `постройка` — id постройки-пещеры из `assets/buildings` (31…35,
     категория «пещера»): явная связь «подземелье ↔ вход в мире».
     Связь ОДНОНАПРАВЛЕННАЯ (dungeons → buildings): в `assets/buildings`
     ОБРАТНОГО поля нет (меньше пересечения с задачами 000055/000060);
   * `предметы_стен` — список видов «непроходимых» предметов стен
     типа (enum `rock`/`column`/`stalactite`, ≥ 1): стену
     (клетка `CELL_WALL`) рисуют не тёмным фоном, а предметом
     (камень, колонна, сталактит). Автотайлинг кромки (000258;
     фасад 000070 предвычисленных wall-объектов УБРАН): wall-клетка
     рисуется, когда её маска 4 соседей (N=1/E=2/S=4/W=8, бит=1,
     если сосед в пределах карты и пол; за пределами — стена)
     НЕНУЛЕВАЯ — краевой спрайт вида по индексу маски — либо маска
     0 + ровно одна диагональ пола (угловая плитка cSE/cSW/cNE/cNW);
     2+ диагонали пола — не рисуется. Индекс плитки и вид —
     детерминированные функции `src/dungeon.js` (`wallTileIndex` —
     только от сетки, без RNG; `wallKindFor` — от (x, y, d.seed,
     d.type) через hash2): вид стен зависит только от точки входа
     (сид формы), а НЕ от опыта персонажа (сид содержимого); стены
     НЕ предвычисляются (раздел сейва `dungeonMemory` не меняется;
     отрисовка — floor-pass 000066/000258).
 * JS-фолбэк `src/dungeons-data.js` (в браузере — `Game.DungeonsData`,
   в node — `require()`) ГЕНЕРИРУЕТСЯ скриптом `node
   scripts/sync-dungeons-data.js` (npm `sync:dungeons`) из JSON-каталога
   (source of truth — JSON, как в `src/spells-data.js` /
   `src/buildings.js`): генерация идемпотентна (повторный запуск —
   byte-identical), зеркало «довольное» (только ключи файла),
   CI-готовый (задача 000054). JSON нужен именно как файл-модуль, а не
   fetch: игра открывается двойным кликом (file://), где fetch()
   локальных JSON недоступен.
 * `src/dungeon.js` выводит `DUNGEON_NAMES/MOBS/ITEMS/SIZE` из каталога:
   node-ветка — `require('./dungeons-data.js')`, браузерная —
   `Game.DungeonsData` (`dungeons-data.js` в `index.html` подключён ДО
   `dungeon.js`; УМД-ловушка 000038 — данные должны быть в Game раньше,
   чем dungeon.js их снимает). БЕЗ data-модуля (vm-песочница
   `tests/dungeon-ui.test.js` его не грузит) гард деградирует до
   fallback-литералов 1:1 с каталогом (прецедент
   `FALLBACK_BUILDING_COUNT` в `src/map.js`, задача 000055) — генерация
   не «умирает»; равенство fallback ≡ каталог закреплено тестом.
   Логика генерации (`createDungeon`, `generateDungeonContents`,
   `dungeonTypeFor`) и форма экспортов не меняются (задача 000070
   расширяет экспорты только аддитивно: `+DUNGEON_WALL_KINDS`;
   задача 000258 заменяет фасад предвычисленных wall-объектов:
   `+wallMask`, `+wallTileIndex`, `+wallKindFor`, функция-фасад
   удалена).
 * `COMBAT_BG_DUNGEON` в `src/sprites.js` — ЛИТЕРАЛЬНОЕ зеркало
   каталога (числа 0..4 → имена фонов cave/crypt/ruins/drowned/abyss),
   БЕЗ require `dungeon.js` и БЕЗ data-модулей (vm-песочница
   `tests/combat-ui.test.js`, задача 000049); тест сверяет зеркало с
   каталогом по порядку файлов (перенумерация сдвинет фоны боя).
 * Тайлы пола `assets/dungeon/floor/<slug>_<n>.svg` (3 на тип, задача
   000069) в каталог НЕ перенесены: `DUNGEON_FLOOR_FRAMES` в
   `src/sprites.js` — как `COMBAT_BG_DUNGEON`, ЛИТЕРАЛЬНОЕ зеркало по
   числам 0..4 БЕЗ зависимости от `dungeon.js`; тесты связывают
   зеркало с каталогом и слогами фонов боя (рисует 000066).
 * Сейв подземелий — топ-раздел `dungeonMemory` (000153.01): карта по
   ключу `'x,y:depth'` (координата входа + глубина) → запись
   `{ contents, lastVisitDay, pos? }` — по одной записи на посещённый
   этаж-вход. Пишется ВСЕГДА (даже пустая); НЕЛОМКО: версия сейва не
   повышается, миграций нет — старый сейв без раздела восстанавливается
   молча пустым (fail-open). Обрезка — записи старше параметра
   `dungeon_memory_days` (и при сейве, и при восстановлении).
   `contents` — валидированная копия контента этажа: seed/createdAtXp/
   step, mobs, chests (+ опциональный `deposits` — с 000157.03,
   собранность `gathered` — ПРАВО как opened — см. раздел «Залежи»;
   `validateDungeonContents` — `src/dungeon.js`). `stairsDown` в
   содержимом НЕТ (поле формы — пересчитывается при каждом входе);
   `pos` — позиция героя только в in-flight-сейве (восстановление на
   этаж, fallback — клетка-вход). Текущий выезд (`dungeonState`) не
   персистируется: после перезагрузки герой в мире, повторный вход —
   world-step'ом; explored-маска не персистируется (туман
   перестраивается). Детерминизм генерации закреплён golden-тестами
   (tests/dungeon.test.js).

## Лут
* Победа — лут с каждого поверженного моба (rollVictoryLoot,
  src/combat.js): по таблице `u.loot` (1 вызов rng на запись) +
  базовый ролл P(D) на моба (пул — еда/зелья, данные модуля);
  затем 1 общий ролл редкого пула: тот же P(D), где
  P(D) = clamp(0.25 + 0.04·D, 0.05, 0.25), D = playerLevel −
  maxLvl (уровень старшего поверженного моба, 000245).
  Именованные дельты (000269, src/combat.js): heroLevelDelta
  (лут: D = playerLevel − maxLvl) и mobLevelDelta (свитки: D =
  maxLvl − playerLevel) — spec/spells.md «Свитки: тир и лут».
* Свитки (000235.05) — НОВЫЙ ролл СТРОГО ПОСЛЕ существующих,
  отдельный солёный rng-поток mulberry32(hash2(seed, day,
  SALT_SCROLL)) — ноль вызовов c._rng (per-mob/базовый/редкий/
  голд — бит-в-бит):
  * D = maxLvl(группа) − playerLevel;
  * P_scroll = min(0.25, 0.05 + 0.02·max(0, D)) (кап при D ≥ 10);
  * тир: при D > 0 — T = min(4, 1 + floor(D/3)); при D ≤ 0 —
    перехватывающая ветка T ∈ {1, 2} (50/50; базовая формула к ней
    не применяется);
  * школа — равномерная из 6; выбор — свиток школы+тира из
    каталога (нет — ближайший тир вниз, затем вверх; пусто —
    не выпадает).
* Сундуки (выбор предмета — ПО ГЕНЕРАЦИИ ЭТАЖА, openChest — только
  выдача): шанс предмета CHEST_ITEM_CHANCE = 0.4 (без изменений);
  пулы `предметы` каталога — статичные (механизм 000133; волны
  000235.07–.12 добавляют свитки); выбор — среди предметов пула с
  tier ≤ T, где T = min(4, 1 + floor((depth−1)/2)) (паттерн
  залежей; пусто — любой из пула). Сдвиг goldens (000235.05):
  число вызовов главного rng на сундук не изменилось —
  seed/mobs/gold/deposits бит-в-бит, сдвинулись ТОЛЬКО значения
  chests[].item (5 репинов tests/dungeon.test.js).
* Снаряжение сундуков (000230.05; 000251 — задокументировано): роулнутый
  предмет с ЯВНЫМ `slot` (брони 000230.10, оружие 000230.12) ЗАМЕНЯЕТСЯ
  предметом роулнутой редкости из EQUIP_POOLS (данные
  src/loot-equip-data.js): СВОЙ rng-поток mulberry32(hash2(seed, depth,
  CHEST_EQ_SALT = 0x0E5C) >>> 0) — блок ПОСЛЕ залежей (000157.02), вызовы
  строго по порядку сундуков c0..cN, только триггернутые: 1 (tier) + 1
  (select, если тир-пул не пуст); редкость — ПЛОСКАЯ RARITY
  50/30/15/4.9/0.1: глубина НЕ участвует в редкости (принятая модель
  сундуков — в отличие от tier-потолка T(depth) первичного выбора пула
  и залежей); замена IN-PLACE (НОВЫХ КЛЮЧЕЙ В ОБЪЕКТЕ СУНДУКА НЕТ —
  сейв v1 не тронут). Главный rng / seed / mobs / gold / deposits не
  трогается (000251: бит-в-бит, кроме значений chests[].item). 000251:
  фантомные legacy-брони — chainmail (CRYPT, dungeons/000002.json) и
  knight_plate (RUINS, dungeons/000003.json) — УБРАНЫ из пулов
  «предметы»: у них явный slot, и выпасть из сундуков они не могут
  (замена всегда действовала).

## Залежи

Залежи руды/минералов/самоцветов (задача 000157.02) — контент ВСЕХ 5
типов подземелий:
 * Данные — ОПЦИОНАЛЬНОЕ поле `руда` каталога `assets/dungeons`
   (source of truth — JSON, `schema.json`, sync
   `scripts/sync-dungeons-data.js` → `src/dungeons-data.js`;
   FALLBACK-литералы `src/dungeon.js` — 1:1 с каталогом, пин тестом):
   массив (minItems 1) записей `{предмет: <id предмета>, вид:
   'руда'|'минерал'|'самоцвет'}`. Редкость В ЗАПИСИ НЕТ — tier
   предмета читается из каталога `assets/items` (000157.01 — единый
   источник редкости, DRY). Инварианты (пinned): в каждом пуле ≥1
   T1-предмет (глубина 1 даёт добычу во всех типах), предметы
   уникальны в пуле (вид однозначен для рендера), пересечение с
   полем `предметы` того же файла пусто (залежи ≠ лут сундуков).
   Экспорт `DUNGEON_ORES[type]` — аддитивный (паттерн
   `DUNGEON_WALL_KINDS`, 000070).
 * Генерация — `generateDungeonContents(d, player, opts)`: параметр
   `depth` (по умолчанию 1 — КОДОВОЙ зависимости от 000153 НЕТ;
   подключение реальной глубины этажа — в точке вызова
   `src/locations.js`). Блок залежей — СТРОГО ПОСЛЕ цикла сундуков:
   число залежей и потолок тира доступных предметов растут с
   глубиной (формулы — в коде и тестах, не в SPEC: шкала 000153
   «+1 уровень за глубину», тир растёт вдвое медленнее). Каждая
   залежь: предмет (равномерно из пула типа с tier ≤ T(depth)),
   количество, клетка. Guard: нет поля `руда` ИЛИ нет записей с
   tier ≤ T → `deposits = []`.
 * RNG — СВОЙ поток `mulberry32(hash2(seed, depth, 0x0DE5))` (соль
   ЗАПИНЕНА golden-тестом; seed — сид контента), в главном потоке
   НОЛЬ новых вызовов после цикла сундуков — существующие goldens
   (seed/mobs/chests) БИТ-В-БИТ. Порядок вызовов на залежь:
   предмет → количество → клетка. Клетка — СОБСТВЕННЫЙ takeSpot на
   общем `occupied` (Set занятых клеток): взаимоисключение с
   мобами/сундуками/босс-клеткой (паттерн 000183) и с безопасной
   зоной 5×5 — БЕСПЛАТНО; две залежи не делят клетку.
 * Рендер — спрайт по «виду» (`sprites.js`: `DUNGEON_DEPOSIT` →
   `assets/dungeon/deposit_{ore,mineral,gem}.svg`, 64×64 в стиле
   `chest.svg`), туман-маска 000136; собранная (gathered) залежь —
   НЕ рисуется (паттерн открытого сундука, 000067); изображение не
   готово — фолбэк-квадрат + полоса ЦВЕТОМ ПО ВИДУ. «Вид» — из пула
   `DUNGEON_ORES[d.type]` по предмету (уникальность — вид
   однозначен). HUD — счётчик «Залежи: N» в инфо-окне НЕ выводится
   (000212); строка hint «Залежь — [E]» — в подземелье/пещерах убрана вместе с панелью
   `.combat-side` (000229), в городе — панель убрана СОВСЕМ (000247): hint нет ни в городе, ни в
   подземелье — строка «Залежь — [E]» отсутствует нигде; механизм (hintEl/hintBase/onDeposit) удалён
   СОВСЕМ (`src/dungeon-ui.js`: 0 ссылок на `.combat-state`/`.combat-log`); единственный потребитель
   floorStatusLine (locations.js) — locationLine hud.js.
 * Сейв: залежи — в секции `dungeonMemory` (000153.01) с 000157.03
   (до этого — не персистировались): `contents` этажа несёт `deposits`
   (опциональный ключ — `validateDungeonContents` копирует
   seed/createdAtXp/step, mobs, chests + deposits); собранность
   (`gathered`) — ПРАВО как opened (версия сейва не повышается).
