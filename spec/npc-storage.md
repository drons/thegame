# Архитектура хранения NPC
Описания NPC (раздел «NPC») хранятся в каталоге `assets/npc`:
 * Один вариант NPC — один JSON-файл: `000001.json`, `000002.json`, … —
   сквозная нумерация, без пропусков и дубликатов.
 * Структура файла закреплена JSON-схемой `assets/npc/schema.json`
   (тот же ограниченный набор ключей валидатора, что и у остальных
   каталогов — задача 000015). Имена полей — русские
   (стиль `assets/buildings/schema.json`):
   * `id` — строка `[a-z][a-z0-9_]*`, уникальна в каталоге;
   * `имя` — имя NPC (не пустое);
   * `роль` — роль по-русски («торговец оружием», «наставник-боец»);
     совпадает по смыслу с `типичный_npc` каталога зданий, но связью не
     является;
   * `описание` — (необязательно) облик и характер;
   * `постройки` — не пустой список id типов зданий из `assets/buildings`
     (1…50), где NPC находится — авторитетная связь «постройка → NPC»
     (поле зданий `типичный_npc` — только описательная проза);
   * `диалог` — не пустой список опций `{id, текст, действие, требования?, для?}`;
     `действие` — `торговля | обучение | квесты | подсказка`;
     `для` — (необязательно) ключ scope опции (задача 000299.02):
     отсутствует или `"все"` — опция видна любому активному
     персонажу; `"efir"` — только Эфиру; `"merc"` — любому
     наёмному (любая роль найма); `{"роль": "melee" | "ranged" |
     "shield" | "support"}` — наёмному с ЭТОЙ ролью найма
     (`найм.роль` каталога NPC). Опция фильтруется в
     dialogOptions (src/npc.js) по переданному активному
     персонажу (src/ui.js: отрисовка вкладки «диалог» и клик
     по опции); несовпавшая — НЕ в списке; требования
     харизма/навык/проверка — по тому же активному, без изменений.
     `требования` — (необязательно) `{харизма: N, навык: {id, уровень},
     проверка: N}`: опция доступна, если выполнены ВСЕ указанные
     требования: `харизма` — основной навык «Харизма» ≥ N; `навык` —
     навык (основной или вторичный) уровня ≥ N; `проверка` — бонус к
     диалогу (уровни «Старейшина» + «Оратор», `derived().dialogueBonus`
     в src/player.js) ≥ N;
   * `торговля` — (необязательно) `{предметы: [{предмет, mult_покупки?
     (по умолчанию 1), mult_продажи, количество?}]}` — сток NPC: id
     предметов `assets/items`; цена — базовая цена предмета
     (`base_price` в JSON предмета, при отсутствии — `value`; 000322) ×
     множители NPC (покупка: игрок → NPC, продажа: NPC → игрок);
     стартовое количество (по умолчанию 1). Цены дополнительно
     корректируются навыком «Торговец» АКТИВНОГО персонажа партии
     (000299.03): buyPriceMult/sellPriceMult — src/sheet.js derived,
     формулы — src/npc.js (NPC), src/items.js (магазины построек);
     владелец покупки/продажи — ВСЕГДА Флогистон (000194);
   * `обучение` — (необязательно) `{навыки: [...], цена_за_уровень,
     цена_переноса_за_уровень}` — школа навыков: список id вторичных
     навыков, которых обучает NPC. Прокачка — за золото по формуле
     (раздел «NPC» → «Школы (обучение)»; требования к основному навыку
     и веткам те же, что при трате очков; очки при этом НЕ тратятся).
     `цена_за_уровень` — цена наставничества по видам крафта (раздел
     «Крафт»). «Перенос вложенных очков» (возврат уровней в пул свободных
     очков за золото) отменён (задача 000297, анти-эксплойт прокачки чужого
     навыка): `цена_переноса_за_уровень` остаётся в данных/схеме, потребителя нет;
   * `квесты` — (необязательно) список `{id, название, описание, цель,
     награда, предыдущий?}`:
     `цель` — `{тип: "kill_group", группа: 0…6, количество}` (повергнуть
     стационарные группы заданного типа, см. MOB_GROUP_TYPES в src/map.js)
     или `{тип: "bring_item", предмет, количество}` (принести предмет);
     `награда` — `{опыт, золото, предметы?}` — выдаётся ровно один раз
     при сдаче;
     `предыдущий` — id предыдущего квеста цепочки (null/отсутствует —
     начало цепочки); следующий квест становится доступен после сдачи
     предыдущего.
 * Игровые функции (чистый код без DOM) — `src/npc.js`; данные NPC
   передаются в функции аргументом: доступность опций диалога, торговля
   NPC (инварианты: золото ≥ 0, сток ≥ 0, лимиты инвентаря), школы
   (прокачка за монеты), журнал квестов: состояния
   «принят → в работе → готов к сдаче → выполнен», не более
   `MAX_ACTIVE_QUESTS = 5` активных квестов; цель `kill_group`
   отслеживается по победам над стационарными группами — `src/main.js`
   уведомляет журнал о победе по типу группы.
 * Экран — оверлей диалога в `src/ui.js` (`Game.npcUI`, вкладки
   «диалог / торговля / школа / квесты»); открывается клавишей [E]
   на тайле постройки (src/main.js). Ряд портретов партии
   (000299.01) — вверху панели: клик — смена активного + ин-плейс
   ре-рендер вкладок «диалог» и «торговля» (000299.02/000299.03);
   оверлей не закрывается. Журнал квестов — один на всю сессию
   игры (main.js). Строки «торговли» — только предметы со стоком
   ≥ 1 (000314): сток 0 или отсутствующий ключ — строка отсутствует
   (не «ост. 0»); ре-рендер после покупки/продажи; строка
   возвращается при регенерации стока (лагерь — по дню, город —
   city_respawn_days, мирской NPC — респавна нет).
 * Игра запускается без сервера (file://), где `fetch()` локальных JSON
   недоступен, поэтому каталог дублируется в униформном JS-модуле
   `src/npc-data.js` (в браузере — `Game.NpcData`, в node — `require()`).
   Модуль генерируется:
       node scripts/sync-npc-data.js
 * JSON-файлы — source of truth. Консистентность `assets/npc` ↔
   `src/npc-data.js` и ссылочную целостность (здания, предметы, навыки,
   типы групп мобов) проверяет `tests/npc-data.test.js`; механику
   (диалоги, школы, квесты, торговля) — `tests/npc.test.js`.
