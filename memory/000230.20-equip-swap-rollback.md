## 1. Брак (верифицирован по коду f002a04)

src/items.js `equip()` (L1232-1267): swap делал
`eq[slot] = itemId; eb[slot] = taken.bonus || null; inv.slots.splice(pos, 1)`
ДО `addItem(c, prev)`. При отказе addItem (checkAdd: вес/слоты) — ветка
`{ok:true, note:'вернуть <prev> не удалось: …'}` (БЕЗ slot/item):
eq[slot] уже перезаписан новым, prev не вернулся ни в инвентарь, ни в
слот → **prev ПОТЕРЯН**, а форма {ok:true, note} читается как «успех».
addItem при отказе ничего не мутирует (gate checkAdd чистый, L645-666) —
единственные мутации до отказа: eq[slot], eb[slot], splice(taken).

Достижимо в игре ОБАМИ путями: герой (G.equip) и наёмник
(allyEquip → G.equip(allyView(hero, sheet)), companions.js L1096-1101;
allyView — inventory hero.inventory ОБЩИЙ, equipment = live-лист
наёмника). UI: src/ui.js doItemAction L436 `if (r && !r.ok)
flashNotice(r.reason || 'не удалось')` — при {ok:true, note} игроку НИЧЕГО
не показывалось (тихая потеря); после фикса {ok:false, reason} уйдёт в
flashNotice — **UI-прав НЕТ** (ветки читают {ok, reason}).

## 3. Ключевое решение: откат swap, семантика «все или ничего»

Формы equip после фикса (note-ветка УБИРАЕТСЯ навсегда):
* **успех**: swap совершён полностью — prev в инвентаре (с бонусом,
  000046), new в слоте, `{ok:true, slot, item}` — бит-в-бит текущий
  success-путь (инвариант ТЗ «НОЛЬ изменений»).
* **отказ возврата prev**: swap НЕ совершён вовсе — prev в слоте как был,
  new в инвентаре КАК БЫЛ (ОРИГИНАЛЬНАЯ позиция в inv.slots —
  `splice(pos, 0, taken)`, инвентарь побайтово до вызова),
  `{ok:false, reason}` — reason ПАСТРУЧНО из back.reason.

Реализация (минимальный ханк — только ветка отказа L1258-1264,
success-путь побайтово):

```
    if (prev) {
      const back = addItem(c, prev, 1, prevBonus || undefined);
      if (!back.ok) {
        eq[slot] = prev;
        eb[slot] = prevBonus;
        if (pos >= 0) inv.slots.splice(pos, 0, taken);
        syncEquipmentMirrors(eq);
        return { ok: false, reason: back.reason };
      }
    }
```

* prevBonus — уже захвачен ДО мутаций (L1252: `prev ? (eb[slot] || null)
  : null`) — restore точный (null и бонус-объекты).
* `splice(pos, 0, taken)` — возврат new в ОРИГИНАЛЬНУЮ позицию: между
  splice(pos,1) и отказом addItem инвентарь НЕ мутирует (checkAdd чисто,
  addItem мутирует только после чистого checkAdd) → restore точный;
  «new в инвентаре как был» (ТЗ) = инвентарь побайтово, включая ПОРЯДОК
  слотов (детерминизм сейва 000031). push-в-конец отклонён (меняет
  порядок слотов — не «как был»).
* `syncEquipmentMirrors(eq)` — ОБЯЗАТЕЛЕН на откате: eq[slot] мутирован
  (itemId → prev), зеркала weapon/armor (D-01, items.js L432-435)
  обновляются только этой функцией; прецедент M11-фикса 000230.02 §9:
  старая note-ветка уходила БЕЗ sync — зеркало weapon застревало. Теперь
  sync на ВСЕХ выходах equip, как в unequip (L1290/L1293).
* reason — единый словарь checkAdd (items.js L645-666): достижимы в
  swap-fail 'слишком тяжело (лимит веса)' | 'нет свободных слотов
  инвентаря' — тот же словарь, что unequip-failsafe (L1285-1292,
  `return r` — прецедент passthrough) и dismiss-failsafe 000230.06.01
  (прецедент единого словаря — allyReject). Патологические строки
  ('неизвестный предмет'/'неверное количество'/'неверный бонус') в
  swap-fail недостижимы (prev из каталога, qty=1, prevBonus из eb —
  валиден по конвейеру sanitize) — единая семантика с unequip
  сохранена.
* Граничный случай ПОЛНОГО инвентаря (20/20 слотов): splice(taken)
  СНАЧАЛА освобождает слот (20→19), затем checkAdd prev: 19+1 ≤ 20 →
  swap ПРОХОДИТ (легальный swap при полном инвентаре — поведение НЕ
  меняется; «проверка ДО splice» дала бы ложный отказ 'нет свободных
  слотов инвентаря' — 20+1 > 20).
* Кольца: swap-fail недостижим — ring-слот всегда выбирается ПУСТЫМ
  (все 8 заняты → отказ ДО этого), prev на ring = null; ветка колец не
  трогается.

**Отклонённый альтернативный A1** (canAddItem-dry-run ПОСЛЕ splice-out,
прецедент атомарности крафта 000046, версия a1-анализа и прототип
/tmp/thegame-wf-000230.20/items-fixed.js): корректен и наблюдательно
идентичен (прототип: current 9 RED только в ре-пинах, fixed 13/13
GREEN), НО переставляет порядок мутаций success-пути (запись eq[slot]
после чека вместо до splice) — против инварианта ТЗ «НОЛЬ изменений
success-путей» + больший ханк = выше риск конфликтов при ребейзе под
параллельные волны. Выбран откат (B). Для зелёной станции: верификация
B тем же verify-red.js после замены items-fixed.js на реализацию B
(наблюдательная идентичность подтверждена разбором: rejection-условие —
тот же checkAdd на том же состоянии (после splice), restore покрывает
ровно 3 мутации до отказа).
