# 000341 — cap tileCache под худший вьюпорт (TILE_CACHE_MAX)

Задача tasks/done/000341.md (RENDER-OPTIMIZE §5C). Правка — только src/map.js:
константа `TILE_CACHE_MAX = 262144` (2^18) рядом с ZOOM-константами,
дефолт-параметр `createTileCache(map, maxSize = TILE_CACHE_MAX)`, JSDoc
`[maxSize=TILE_CACHE_MAX]`, экспорт `TILE_CACHE_MAX` в списке return.
main.js вызывает `G.createTileCache(map)` БЕЗ аргумента cap — новый дефолт
подхватывается сам, main.js не тронут (там параллельная 000339).

## Пересчёт worst-case N (не с веры из RENDER-OPTIMIZE)

Формула `visibleTileRange(camX, camY, viewW, viewH, zoom, margin = 2)`:
countX = ceil(viewW/zoom) + 2, countY = ceil(viewH/zoom) + 2 (обе границы
включительно; main.js в пересборке frame вызывает БЕЗ margin ⇒ margin = 2).
Зум клампится колесом мыши в [ZOOM_MIN=4, ZOOM_MAX=128] (ZOOM_START=80).
Худший = минимальный зум × типовое окно:

- 1920×1080 @ z=4 → 482 × 272 = **131 104** (пин T1)
- 2560×1440 @ z=4 → 642 × 362 = 232 404
- 3840×2160 @ z=4 → 962 × 542 = 521 404
- 1280×720  @ z=4 → 322 × 182 = 58 604
- рабочий зум ~22 (1080p) ≈ 4 680

Старый cap 65 536 < 131 104 — классический FIFO-trash рабочих наборов:
пересборка frame заново обходит весь вьюпорт, при cap < N каждое движение
(пересечение тайла = miss-кадр) содержит десятки тысяч синхронных регенераций
tileAt (2×fbm elevation/moisture ×4 октавы + fbm + pixelAt + footprint) на
main thread. Эмпирика 000276: «~65 568 регенераций tileAt/кадр», 1.16 мкс/тайл
только на look-up.

## Решение: константа, а не адаптивный cap

- Адаптивный потребовал бы передавать размеры канвы в createTileCache и
  обновлять при resize — правка main.js вне SCOPE (регион 000339).
- Детерминизм: дефолт перестал бы зависеть от размера окна харнесса/юзера —
  тесты-кадры стали бы невоспроизводимыми.
- Довод «не платить памятью на малых окнах» иллюзорен: cap — ПОТОЛОК, не
  аллокация; размер кэша = min(уникально посещённых, cap), малое окно никогда
  не платит за большой cap.

Почему 262144, а не 163840: при cap == N (131 104) row-major pan вытесняет
старейшие ещё видимые строки и трэшится полосой ~750 регенераций/кадр —
запас ОБЯЗАТЕЛЕН (T2 пинит это на N+4096: второй проход по тому же набору не
генерирует НИ ОДНОГО тайла). 262144 покрывает целиком и эталон 1920×1080@z4
(131 104), и следующий типовой экран 2560×1440@z4 (232 404); степень двойки.
Альтернатива 163840 остаётся зелёной всей гарнитурой (мутация M6) — выбор
зафиксирован кодом-константой, сьют пинит СВОЙСТВО (cap ≥ N + запас, evict
жив, содержимое cap-инвариантно), а не литерал.

## Память: честные десятки MB (RENDER-OPTIMIZE «несколько MB» занижено)

Замер Node (heapUsed с --expose-gc,slope по 65k/131k РЕАЛЬНЫХ объектов
tileAt): ≈268 Б/тайл.

- cap 65 536 → ~17–21 МБ
- резидентно при 1080p@z4 → ~33 МБ при ЛЮБОМ cap ≥ N (столько платит сам
  вьюпорт, от выбора константы НЕ зависит)
- потолок 262 144 → ~67 МБ, и то только после реального посещения 262k
  уникальных тайлов

## Семантика и смежные кэши

- createTileCache — строгий FIFO по порядку ВСТАВКИ (hit-ветка не вставляет,
  порядок не обновляет — это НЕ LRU); evict только на miss-path после set при
  `size > maxSize` (size наблюдаемо никогда не > maxSize) — семантика
  сохранена, off-by-one не «чинился» (не заявлен).
- tileAt — чистая функция координат (Math.random в map.js = 0 hits, сиды
  GLOBAL_SEED/CITY_SEED_CONST/SUBTYPE_SEED_CONST/LOOT_SEED + сид-PNG +
  каталоги) ⇒ при любом cap и FIFO-порядке содержимое бит-в-бит (deepEqual),
  меняется только object identity при miss — пин T3. Рендер от смены cap не
  меняется НИКАК.
- НЕ путать с fpCache и nmCache (замыкания createMap, тоже литерал 65536 —
  совпал случайно): семантика ПОЛНЫЙ clear(), а не FIFO. НЕ тронуты; guard —
  T5 (readFileSync src/map.js содержит `fpCache.size > 65536` и
  `nmCache.size > 65536` + дефолт createTileCache привязан к TILE_CACHE_MAX
  — main.js зависит именно от дефолта).
- hit-ветка frameTiles (000276) в tileCache НЕ ходит — steady-кадры cap не
  трогает; steady-state от задачи не зависит.

## Тесты и мутации

tests/map-tilecache-cap-000341.test.js — 5 (kind=node, прямой импорт map.js):
T1 worst-case N=131 104 + TILE_CACHE_MAX ≥ N (падение = пересмотр капа);

⇒ size ≤ cap, старейший вытеснен, последний — хит; T5 guard fp/nm +
привязка дефолта. RED 4/5 ERR_ASSERTION (T3 — инвариант-пин, зелёный и до,
и после — он защищает свойство, на которое опирается задача). Мутации
