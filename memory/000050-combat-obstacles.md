## Где что лежит

* **c.obstacles** — Set строк 'x,y' непроходимых клеток; всегда есть
  (может быть пустым). Заполняется `generateObstacles` в createCombat
  РОВНО между `placeUnits` (нужны стартовые прямоугольники мобов) и
  `refillPools` — ТОЛЬКО через c._rng (детерминизм по сиду).
* **Настройки** — SETTINGS.combat_obstacle_min_frac / max_frac
  (src/global-settings.js, 0.10 / 0.20 — доля клеток поля; для 7×7 это
  5..10 клеток). Live-чтение (паттерн level_delta_max): правка SETTINGS
  меняет генерацию без перезагрузки.
* **src/sprites.js** — OBSTACLE_DIR, OBSTACLE_SPRITES ([rock, boulder,
  bush].svg), чистая `obstacleSprite(x, y)` = (x*3 + y*5) % 3 (нецелое /
  отрицательное → null → рендерер рисует фолбэк-квадрат). Пути — в
  allAssetPaths(); index.html не менялся (sprites.js и так до
  combat-ui.js).
* **src/combat-ui.js** — слой строго ПОСЛЕ сетки, ДО юнитов (z-порядок:
  фон → сетка → препятствия → юниты → эффекты). Картинка — из
  spriteLoader КАЖДЫЙ render (паттерн фона 000049); G.obstacleSprite —
  guard (УМД-ловушка «G снимается один раз»); фолбэк — тёмный квадрат
  #3a4150, CELL−6, отступ 3 px.
* **assets/combat/obstacles/{rock,boulder,bush}.svg** — 3 универсальных
  спрайта, viewBox 0 0 48 48, нейтральная палитра (серые #6a6472-
  #938da0 + приглушённая зелень) — читаются на всех 11 фонах 000049.
  Перенесены готовые из старой ветки задачи (решение пользователя).
* **SVG-гейт** — tests/svg.test.js: EXPECTED_SVG_BY_DIR 'combat/
  obstacles': 3 (итого 275 файлов: 271 база + 3 obstacle + chest 1 из
  000067).
* **Экспорт combat.js** — +reachableCells (чистая BFS-функция для
  тестов): Set клеток, достижимых из (c.px, c.py) по НЕ-препятствиям,
  мобы игнорируются, старт включён, c не мутирует.

## Ключевые решения (нетривиальные)

* **Решение (б) 000030** — препятствие = отдельный спрайт ПОВЕРХ общего
  фона (000049), а не процедурный «запечённый» SVG-фон на каждый бой:
  визуально неотличимо, детерминировано, фон переиспользуется.
* **Блокируется ТОЛЬКО движение.** Атаки и заклинания (в т.ч. дальние)
  летают ПОВЕРХ камней — линий видимости в модели НЕТ (unitDist —
  Манхэттен, hitChance — по дистанции). Если когда-нибудь понадобится
  «стрельба не через камень» — отдельная задача (модель видимости).
* **Непроходимость — правило ядра** (combat.js), а не визуал: без
  ассетов/лоадера клетка — тёмный квадрат, бой играбелен.
* **Поток RNG закреплён** (детерминизм алгоритма): target — ОДИН бросок
  (min + floor(rng × (max−min+1))), кандидат — ДВА (x, y); генерация
  строго между placeUnits и refillPools; при max_frac ≤ 0 бросков НЕТ
  вообще — поток c._rng совпадает с боем без генерации (критично для
  снэпшот-тестов). Не менять порядок/число бросков.
* **reserved-клетки**: старт игрока + ВСЕ клетки стартовых
  прямоугольников всех мобов (у крупных 2×2/3×3 — весь прямоугольник, не
  только якорь) — препятствие там не рождается.
* **Достижимость**: после добавления клетки — BFS из старта игрока по
  не-препятствиям обязан достигать ≥1 клетки стартового прямоугольника
  КАЖДОГО моба (мобы игнорируются — могут сойти с дороги); нарушение —
  только что добавленная клетка удаляется (и следующая попытка — новый
  кандидат). Лимит MAX_OBSTACLE_TRIES = 500: исчерпан раньше target —
  меньше препятствий (разрешённый фолбэк п. 3 задачи: плотность < min,
  поле играбельно).
* **reason playerMove**: порядок «стена» → «препятствие» → «тут стоит
  моб» (камень на клетке моба — раньше моба).
* **stepToward/stepAway** учитывают препятствия через rectFree (одна
  точка проверки для обоих). Жадный ИИ мобов НЕ обходит камни: моб за
  камнем стоит (зафиксированное поведение задачи «если некуда — стоят»).
  Тестовый autoPlay deadlock'ится за камнем — баланс/лут/смерть-сценарии
  в tests/combat.test.js делают c.obstacles.clear() с комментарием (5
  мест); новый баланс-сценарий на autoPlay — тоже.
* **obstacleSprite** — чистая функция, (x*3 + y*5) % 3: соседи дают
  разные виды, на 3×3 встречаются все 3 вида (не «штамп»); нецелое /
  отрицательное → null (клеток вне поля не существует).
