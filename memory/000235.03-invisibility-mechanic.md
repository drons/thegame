## 2. Контракты и границы

### 2.1 isHeroInvisible(p, day) — src/spells.js

* Чистая, null-safe, без Game/map — тестируема в node. `!p` /
  не-массив `outOfCombatEffects` / пусто → false. Запись-мусор (null,
  не-объект), неизвестный spellId (нет в SPELLS_BY_ID), expiresDay
  не-число → запись игнорируется, без краха.
* Граница `expiresDay > day` — зеркало expireOutOfCombatEffects (.02):
  на onDay(D+N) запись вылетает, и запрос в тот же день false.
* Матчинг — ЛЕНИВЫЙ lookup `SPELLS_BY_ID[e.spellId].действие` в момент
  вызова, НЕ load-time Set и НЕ список id: (а) spellId 'invisibility'
  решается в контентной волне .09 (каталог append-only), (б) цепочки
  совершенствований .09 могут дать НОВОЕ id с тем же действием — по
  действию механика работает без правок (D-1 §8), (в) guest-инъекции
  тестов (live-мутация SPELLS_BY_ID) видны без перезагрузки.
* ТЗ «isHeroInvisible(G)» — G = состояние игры; spells.js (UMD) G не
  видит → сигнатура (hero, day), main.js вызывает
  `G.Spells.isHeroInvisible(hero, clock.day)` (решение D-5 §8).

### 2.2 clearInvisibility(p) — src/spells.js

* Удаляет ТОЛЬКО записи действия 'невидимость'; чужие записи (тот же
  'внебой' и др.) — живы, порядок остальных сохранён. Возврат void —
  вызывающий не ветвится на результат (состояние проверяется
  isHeroInvisible-запросом / ассертами).
* Переприсваивание `p.outOfCombatEffects = filtered` — ТОЛЬКО при успехе
  (что-то снято): для чистых путей (нет записи) идентичность массива не
  меняется → сейв-пины/roundtrips и live-ссылки state-зеркала
  (main.js:3559) не сдвигаются.
* Примитив снятия, который вызывают хуки (2.4); истечение дней — НЕ через
  него (день-хук .02 — expireOutOfCombatEffects, main.js onDay
  :1588-1591, без изменений, новых flash-строк НЕТ — байт-пин
  onDay-флэша :1607-1610 main.js).

### 2.3 zoneSuppressedReason(zone) / zoneCombatInfo — src/main.js

* В .03: `void zone;` + один глобальный чек невидимости. Возврат

  НЕТ (верифицировано: main.js keydown — движение + I/C/B/E; все «атаки» —
  внутри боя; мобы мира — статичные группы, погони НЕТ — 000155 это
  боевой A*). Поэтому «снятие при атаке» ⊂ «снятие при вступлении в
  бой» — ОДИН хелпер на 3 точках покрывает оба триггера ТЗ (D-2/D-4 §8).

## 8. Открытые вопросы → решения (Д-1..Д-8)

* D-1: ключ запроса/снятия — ДЕЙСТВИЕ 'невидимость' (ленивый lookup),
  не id. Почему: id решится в .09 (append-only), цепочки-
  совершенствования могут дать новое id с тем же действием — по id
  механика бы их пропустила; guest-тесты видны без перезагрузки.
* D-2: снятие — хук на 3 точках startCombat main.js, combat.js НЕ
  трогать. Почему: внебоевой атаки героя НЕТ (вериф. — шаги/кнопки
  I/C/B/E), «атака» ⊂ «вступление в бой»; a1-вариант (playerAttack +
  combatInternals-мост) отклонён: +1 правка бит-в-бит-критичного
  combat.js (8648-строчный combat.test.js, детерминизм) ради триггера,
  фактически подмножества; в бою герой уже видим.
* D-3: подавление — ОДНА точка zoneCombatInfo (до findZoneCombat),
  HUD-«— зона» гаснет вместе. Почему: ТЗ просит одну точку расширения
  (расщепление бой+HUD — две); предупреждение о не начнётсящемся бое —
  «врать». Открытый вопрос ОQ-2 (живое предупреждение?) — решён: гаснет;
  если родитель потребует живого — строка переезжает в zoneCombatTile
  (одна строка), zoneCombatInfo не трогают.
* D-4: установка/истечение — БЕЗ НОВОГО КОДА (generic-ядро .02 +
  onDay-хук .02). Почему: DURATION_ACTIONS уже несёт 'невидимость';
  мгновенных эффектов нет; .02-каркас .04 остаётся intact. Явный кейс
  switch 'invisibility' — маркер обработанности (контракт .02 §2.1
  зарезервировал именно .03 под эту точку) + паттерн id-кейсов .04;
  пустой break = успех, поведенческой дельфы 0.
* D-5: сигнатуры isHeroInvisible(p, day) / clearInvisibility(p) — чистые
  функции без Game (spells.js UMD не видит G; node-тестируемо). Почему:
  ТЗ «isHeroInvisible(G)» — G = состояние; проводка в main.js
  (hero, clock.day); main.js — единственный вызывающий.
* D-6: тайл-бой (мир + подземелье) не подавляется; neutral/timid
  без изменений. Почему: D6 «моб на одном тайле героя видит» — явное
  решение контракта; ветка pt.hasMobGroup не проходит через
  zoneCombatInfo → сохраняется автоматически (код — только НЕ сломать).
* D-7: имя/сигнатура точки расширения — zoneSuppressedReason(zone)
  (а не zoneNoTriggerReason(zx,zy) a1 / zoneSkipReason() a3). Почему:
  аргумент zone — объект тайла группы {x,y,mobGroup} — именно то, что
  нужно .04 (Чебышёв до тайла зоны); сигнатура с аргументом с самого
  начала → .04 не трогает вызывающую конструкцию, только тело + вторую
  строку вызова.
* D-8: вторая строка вызова zoneSuppressedReason(z) после findZoneCombat
  — НЕ в .03, а в .04. Почему: в .03 она мертва (причин, кроме
  глобальной, нет) — мёртвый вызов = ревью-запах; ТЗ-дословие «
  findZoneCombat не вызывается» уже выполнено строкой ДО; место второй
  строки зафиксировано в §2.3 (конструкция .04) — дельфа .04 минимальна.
* D-9 (бонус): e2e-guest — id 'invisibility' (будущий реальный id из
  §7.3), мани 5, days 1. Почему: контракт-идентификатор совпадает с
  .09 (механика проверяется на «своем» id), live-инъекция не растит
  файл-каталог (пин «ровно 17» цел); мани произвольный в тесте (mp-
  ассерт self-consistent через saveHero).
