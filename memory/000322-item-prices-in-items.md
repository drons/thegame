# 000322 — базовая цена предмета — в JSON предмета, а не в JSON NPC

## Зачем (архитектурный баг)

База NPC-торговли жила в JSON NPC (`торговля.предметы[i] =
{предмет, цена_покупки, цена_продажи, количество?}`): один предмет у
двух продавцов имел ДВЕ разные «базы», а отклонение продавца
(дороже/дешевле рынка) было вмято в цену — множители не восстанавливались,
меняли цену, перебирая всех продавцов.

## Контракт (000322)

- Поле `base_price` в JSON предмета: ОПЦИОНАЛЬНОЕ, integer, 1..100000,
  НЕ в required. Позиция — СРАЗУ ПОСЛЕ `value` (assets/items/schema.json,
  KEYS scripts/sync-items-data.js). Зеркало src/items-data.js печатает
  только существующие ключи в порядке KEYS → у 41 предмета с полем
  порядок `value, base_price`, у остальных 470 — `value` без base_price.
- Формат входа `торговля` NPC JSON: `{предмет, mult_покупки?
  (по умолчанию 1), mult_продажи, количество?}`. `цена_покупки`/
  `цена_продажи` УДАЛЕНЫ; assets/npc/schema.json —
  additionalProperties: false → старый формат падает валидацией.
  Порядок ключей в JSON входа: предмет, mult_покупки (если ≠ 1),
  mult_продажи, количество (если есть).
- Формулы — src/npc.js; изменён ТОЛЬКО источник базы:
  - `base = it.base_price (typeof number), иначе it.value (фолбэк)`
  - npcBuyPrice  = max(1, round(base × (mult_покупки || 1) × buyPriceMult))
  - npcSellPrice = max(1, round(base × mult_продажи × sellPriceMult))
  - buyPriceMult/sellPriceMult — derived() src/sheet.js по «Торговцу»
    АКТИВНОГО персонажа партии (000299.03) — НЕ МЕНЯЛОСЬ.
  - Владелец покупки/продажи — ВСЕГДА Флогистон (000194) — НЕ МЕНЯЛОСЬ.
- Магазин постройки (src/items.js makeShop/buyPrice/sellPrice) —
  формула от `value` НЕ ТРОНУТА: base_price — НЕ база магазина
  (регресс-пин R4).

## Миграция (бит-в-бит сохранение цен)

- 41 JSON предмета получил `base_price`: 000001–000024, 000033–000041,
  000052, 000055, 000077–000082. base = MIN цены покупки среди
  продавцов (см. BASE в git diff tests/item-prices-000322.test.js
  OLD_PRICES/проверок; черновик /tmp/000322-migrate.js — не в репо).
- 7 NPC-файлов / 46 входов переписаны: 000001 (оружейник, 7),
  000002 (бронник, 4), 000003 (аптекарь, 12), 000004 (маг, 7),
  000006 (кузнец, 1), 000011 (странник-торговец, 9),
  000018 (лагерный странник, 6).
- Для ВСЕХ 46 входов base × mult === старая цена ТОЧНО как double
  (целочисленные пары) → при ЛЮБОМ «Торговце» и любом множителе
  round(base × mult × M) === round(старая × M). Доказано тестом R3:
  46×2×(101 уровень + 115 значений M_GRID) сравнений, 0 переворотов.
- Отклонения camp_wanderer → mult_покупки > 1: хлеб 1.5, мясо 1.2,
  honey_cake 1.1111111111111112, minor_healing 1.25,
  healing_potion 1.0909090909090908 (база 12, городская цена 10 —
  лагерь дороже). mult_продажи лагеря при этом: 1 / 0.8 /
  0.6666666666666666 / 0.75 / 0.7272727272727273.
- Чертёжи 000077–000082: base = 120 (1.5 × value 80 вмято в базу),
  mult_покупки = 1 → ключ ОТСУТСТВУЕТ в JSON и в зеркале,
  mult_продажи = 0.5.
- mult_покупки = 1 → ключ отсутствует (конвенция: зеркало печатает
  только присутствующие ключи; `(p.mult_покупки || 1)` в формуле).

## Подводные камни

- JSON предметов roundtrip-чистые (JSON.stringify(obj,null,2)+'\n'
  === исходник) — строковая вставка после `"value": N,` безопасна.
  JSON NPC — НЕ roundtrip-чистые (однорядочные записи входов) →
  миграция входов — только line-based regex по строкам входов,
  полный ре-сериазабл не делать.
- Зеркало: правка JSON предметов БЕЗ `node scripts/sync-items-data.js`
  → W-08 дрейф. Зеркала и JSON — в ОДНОМ коммите.
- В зеркале npc-data ключ mult_покупки при 1 ОТСУТСТВУЕТ — в тестах
  не фабриковать; `!('mult_покупки' in e)` — пин.
- W-08 sync:check до коммита падает транзиентно («в src/ есть
  незакоммиченные изменения») — прецеденты 000302.08, 000283.01.01;
  после коммита — 0 fail.
- Формула магазина постройки от `value` — НЕ «чинить» под base_price;
  осознанное решение (R4).
- Старые цены не хранятся нигде — при проверке бит-в-бита опираться
  на OLD_PRICES в tests/item-prices-000322.test.js (46 пар).
