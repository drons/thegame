## 2. Контракты и границы

### 2.1 dismiss: сигнатура и поток (ТЗ п.1)

`dismiss(roster, npcId, hero)` — hero — ТРЕТИЙ ОПЦИОНАЛЬНЫЙ аргумент
(тот же объект персонажа героя, что в allyEquip/allyUnequip:
primary/secondary/inventory — plain-объекты). 2-арг. вызовы на
записи БЕЗ экипировки — БИТ-В-БИТ со старым кодом (splice, {ok:true}):
все существующие 2-арг. вызовы (tests/companions.test.js
L591/606/1295, squad-panel P5, npc-hire-ui U7) остаются зелёными.

Поток (src/companions.js, ~L272-278):
1. canDismiss — без изменений.
2. hasEq — entry.sheet plain-объект И sheet.equipment plain-объект И
   хотя бы один ключ с непустым string-значением. Детект НЕ читает
   G.EQUIP_PHYS_SLOTS (деградация без items.js возможна; зеркальные
   ключи weapon/armor тоже считаются — они ставятся ТОЛЬКО когда
   занят физ. слот — ложного детекта нет). hasEq нет → СТАРЫЙ путь:
   splice, {ok:true} (плоские записи без sheet — P5/U7 — побайтово).
3. hasEq + hero не валиден → {ok:false, reason:'нет персонажа'} —
   БЕЗ splice (guard 4 allyReject — единый словарь строк).
4. hasEq + typeof G.unequip !== 'function' → {ok:false,
   reason:'экипировка недоступна (items.js не загружен)'} — БЕЗ
   splice (guard 5 allyReject). Реализация — вызов
   allyReject(hero, sheet, 'unequip') ДО мутаций (guards 1-3 на
   записях отряда недостижимы — roster содержит только merc-листы —
   но единая точка словаря; порядок — как в allyReject: hero ПЕРЕД
   API).
5. Цикл по занятым слотам в КАНОН-ПОРЯДКЕ G.EQUIP_PHYS_SLOTS
   (детерминизм): allyUnequip(hero, sheet, slot) — ТОТ ЖЕ failsafe
   (при отказе предмет остаётся надетым).
   * ВСЕ ok → splice → {ok:true} (без 'note').
   * ПЕРВЫЙ отказ → STOP (остальные слоты не трогаем), БЕЗ splice →
     {ok:false, reason:<failsafe-строка дословно>,
     note:'увольнение не выполнено: предметы остались
     экипированными'}. reason дословно из unequip: 'слишком тяжело
     (лимит веса)' | 'нет свободных слотов инвентаря'.

ИНВАРИАНТ: предметы не теряются НИКОГДА — splice только когда ВСЕ
физ. слоты пусты. Блок при переполнении — FAILSAFE (иначе потеря), а
не противоречие решению ТЗ «авто-возврат, не блокировка» (которое про
ДИЗАЙН: не запрещать увольнять наёмника с надетым). All-or-nothing:
каждый unequip — +1 слот/+вес, порядок не влияет на достижимость →
первый отказ = отказ всей пачки; состояние ВСЕГДА согласовано (либо
вернули всё, либо ничего); повторная попытка после освобождения
инвентаря работает (наёмник остаётся в отряде).

ФОРМА ОТКАЗА ПРИ ПЕРЕПОЛНЕНИИ (решение a3 §6.1): {ok:false, reason}
+ запись ОСТАЁТСЯ — единственная форма, согласующая «не теряются
НИКОГДА» + failsafe allyUnequip + P5. Отклонённые альтернативы:
(a) {ok:true, note} + splice — предмет никуда не кладётся = ПОТЕРЯ
(против ТЗ); (b) конвертация в золото (a1, прецедент
combatEndLoot 000132 «не влезло: +N золота») — ТЗ просит «note,
предметы не теряются НИКОГДА», а не смену судьбы предмета; прецедент
остается в §3 на случай будущего redesign.
