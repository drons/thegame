# 000074: решения — «уровень мира» и квест постройки

Второй файл 000074 (главный — memory/000074-rune-stone-obelisk.md).
Там — контракты apply/каталога/тестов; здесь — две зафиксированные
резолюции, которые ТЗ помечало «решение зафиксировать».

## Решение 1. «Уровень мира» обелиска = hero.level

ТЗ: «уровень мира — как определяется в текущем мире: зафиксировать,
если отдельного «уровня мира» нет — уровень персонажа».

Факт (сверено с кодом): отдельного «уровня мира» в игре НЕТ (grep
по всем src/ и assets/ пуст; memory/000064-building-effects-plan.md
подтверждает). Значит — уровень персонажа.

**Резолюция: `L = st.hero.level` (целое, состояние героя; НЕ
totalXp-прогресс, НЕ clock.day). Единая трактовка для 000074 И
000092 (фонтан, зарезервирован memory/000064-building-effects-plan.md
«уровень мира — зафиксировать решение»): обе формулы читают
hero.level. 000092 — не изобретать альтернативу.**

Формула обелиска (catalog-driven):
`xp = round((опыт_база + опыт_шаг · hero.level) · xpMult)`
(опыт_база=5, опыт_шаг=2 — каталог 000042; xpMult — существующий
derived Учёного player.js:240 — 1 + 0.02·scholar; apply ЧИСТО
подставляет значения, вычисление — round на выходе).

Обоснование: ТЗ прямо санкционирует этот fallback; hero.level —
единственный «уровень», имеющийся в мире; даёт обелиску рост (чем
сильнее герой — тем жирнее опыт, как у камня с «Рунописью») и
симметрию с формулой камня (навык/уровень — один аргумент).

## Решение 2. Квест постройки — контракт (source 'building')

Первое применение НОВОГО источника квестов. Формулировки:

**Источник:** квест определяется ИЗ КАТАЛОГА постройки
(`особые_параметры.квест` записи 000042 — {id, название, описание,
цель, награда}), НЕ из npc.квесты. ЛОГИКА NPC-квестов (accept/turnIn/
лимит/гигиена) — БЕЗ ИЗМЕНЕНИЙ: npc.test.js зелёный без правок;
MAX_ACTIVE_QUESTS = 5 не меняется.

**Пер-тайл identity:** `questId = квест.id + '_' + x + '_' + y`
(пример: 'obelisk_touch_80_-51'). Ключ book.active === questId
(конвенция журнала: key = id квеста; questId — поле инстанса
дублирует). Per-tile → каждый обелиск — отдельный квест;
журнал «Выполнено» получает per-tile id (ui.js:920-926 — существующий
фолбэк «голый id» при отсутствии в каталоге NPC).

**Форма инстанса (book.active[questId]):**
```js
{ source: 'building', tile: 'x,y', questId, status: 'active',
  progress: 0, day }
```
`source: 'building'` — ЯВНОЕ поле (ТЗ: «в журнале (source
'building')»); npcId НЕТ (квест не NPC-инициирован) — следствие:
строгий deserializeQuestBook (npc.js:466) его отверг бы → поэтому
см. persistence ниже.

**Поток (выдача / выполнение) — ОБА события — прикосновения:**
* ПЕРВОЕ прикосновение (apply '42', при записи buildingQuests[key]
  НЕТ): `r.quest = { questId, day }` → main.js
  `G.acceptBuildingQuest(questBook, questId, key, day)` +
  `buildingQuests.set(key, { questId, day, status:'active' })`.
  Выдача НЕ в openBuildingUI (подход) — ВСЕ мутации состояния
  остаются в ok-ветке onBuildingAction (один saveNow/render;
  прецедент «на подходе» 000075 — только пассивный сбор данных).
* СЛЕДУЮЩЕЕ прикосновение (запись status 'active'):
  `r.questComplete = запись.questId` (персистированный id — каталог
  мог измениться) → main.js `G.completeBuildingQuest(questBook, def,
  hero, questId)` → награда + `buildingQuests.set(key, …, status:
  'done')`. Выполнение ВСЕГДА на позднейший день (daily-лимит:
  второй раз — не раньше дня выдачи + 1; тест B23: выдача день 1,
  выполнение день 2).
* запись status 'done' → apply возвращает ни r.quest, ни
  r.questComplete (повторно не выдаётся; ТЗ-тест).
* Повторный grant невозможен: apply смотрит на СНИМОК
  buildingQuests (прототип-безопасно) И main.js гардируется
  acceptBuildingQuest (book.active[questId] есть → отказ).

**Лимит:** `acceptQuest` (npc.js:333) — ЕДИНСТВЕННАЯ семантическая
правка в логике NPC-квестов: считает только НЕ-building-инстансы
(`Object.values(book.active).filter(i => i && i.source !== 'building')
.length >= MAX_ACTIVE_QUESTS`). `acceptBuildingQuest` — БЕЗ лимит-
проверки (ТЗ: лимит — для NPC-квестов). Зафиксированное поведение
(тест A51): 5 NPC + 1 building СОСУЩЕСТВУЮТ; 6-й NPC при 5 NPC +
1 building — откажется с reason «слишком много активных квестов (5)».
npc.test.js — без building-инстансов → идентичный результат.

**Награда:** каталожная, у обелиска — { опыт: 25, золото: 20,
предметы: [] }. Выдача — в completeBuildingQuest (npc.js): предметы —
атомарно (инвентарь полон → откат, квест НЕ выполняется, повтор —
следующее прикосновение; паттерн turnInQuest, универсален к будущим
каталогам, для обелиска — no-op); `character.gold += награда.золото`;
опыт — `P.addXp(character, награда.опыт)` — ШТАТНЫЙ addXp (С
Учёным: фактически round(25·xpMult) — установленный паттерн
turnInQuest для NPC-квестов; осознанная асимметрия с ежедневным XP
качения — тот идёт сырым, см. решение 3).

**Source of truth — раздел сейва `buildingQuests`** (имя — 000072):
`'x,y' → { questId: string, day: integer ≥ 1, status:
'active'|'done' }`. Раздел ПЕРВИЧЕН, questBook — КЭШ:
* секция `quests` сейва содержит ТОЛЬКО NPC-инстансы (serializeQuestBook
  — guard `inst.source === 'building' → skip`; deserializeQuestBook —
  БЕЗ ИЗМЕНЕНИЙ);
* building-инстансы ВООБЩАЮТСЯ в questBook из buildingQuests при
  restore — `rehydrateBuildingQuests(book, map)` (npc.js, чистая;
  идемпотентно: только status 'active', существующие ключи не
  затирает) — вызов в main.js ПОСЛЕ quests-блока restoreFromSave;
* гигиена дат (000029): `active && day > clock.day` → запись ОТБРОШЕНА
  (+warn) — «будущий» квест не выдаётся; `done` — ДЕРЖИТСЯ при любой
  дате (отброс done позволил бы ре-выдачу + повторную награду);
* неломкое v1: версия сейва НЕ повышается (000031), save.js —
  не трогать; fail-open (000029): мусорный раздел → console.warn +
  сброс раздела, игра не падает.

**Журнал (контракт отображения, ограничения осознаны):**
* «В работе» (ui.js:566/571, activeQuests): building-инстанс → quest
  null → строка ПРОПУСКАЕТСЯ (существующий guard `if (!quest)
  continue`; activeQuests — БЕЗ ИЗМЕНЕНИЙ, ui.js вне файла задачи).
  Косметический лимит: активный building-квест в этой вкладки НЕВИДИМ.
* «Выполнено» (ui.js:916-927): per-tile id → findQuestInCatalog
  null → выводится ГОЛЫЙ id (существующий фолбэк).
* Следующая задача (кандидат): рендер названий building-квестов во
  вкладке «Квесты» (каталог в рендере / 3-й аргумент activeQuests).

**Связь с ежедневным XP:** одно и то же прикосновение может выдать И
XP касания (r.xp) И квест (r.quest/r.questComplete) — ханки main.js
независимы, message — многострочный (прецедент 000076); saveNow —
один, общим потоком.

## Решение 3 (спутник к обоим): механизм выдачи XP — grantXpRaw

ТЗ формулирует ОБЕИ формулы как ИТОГОВЫЙ XP («XP round((10+2·R)·
runePowerMult)», «XP round((5+2·L)·xpMult)») и прямо: «xpMult Учёного
к камню НЕ применяется — решение зафиксировать».

**Резолюция:** apply ('40'/'42') вычисляет ТОЧНОЕ итоговое число по
формуле ТЗ (чистые функции stoneXp/obeliskXp над каталожными
параметрами + значения G.derived(st.hero)) и возвращает
`r.xp = number` — ГОТОВЫЙ XP. main.js — ЕДИНЫЙ ханк выдачи
`if (Number.isFinite(r.xp)) grantXpRaw(hero, r.xp);` (между r.buffs
и daily-маркой, общий для обоих эффектов — будущие эффекты зданий
(000091-000095) переиспользуют, не дублируют).

grantXpRaw — локальная функция IIFE main.js, ТОЧНОЕ зеркало addXp
(player.js:317-334) БЕЗ множителя xpMult:
`hero.totalXp += amount; hero.xp += amount;` лупа
`while (hero.xp >= G.xpForNext(hero.level)) { hero.xp -= …;
hero.level++; hero.points += G.POINTS_PER_LEVEL; }`; clamp hp/mp
через G.derived (как в addXp). Комментарий в коде ОБЯЗАТЕЛЕН:
«зеркало addXp player.js:317 — при изменении addXp синхронизировать».
player.js — НЕ ТРОГАЕТСЯ (вне списка файлов ТЗ; альтернатива a2 —
addXpRaw в player.js — отвергнута как правка файла вне списка;
альтернатива a1 — addXp для обелиска + ролл для камня — отвергнута
как двойной путь выдачи).

Почему НЕ addXp: player.addXp ВСЕГДА умножает на xpMult (player.js:320)
— «сырого» варианта API нет; камню xpMult НЕ положен по ТЗ.
Награда квеста идёт ШТАТНЫМ addXp (с Учёным) — паттерн turnInQuest.
Тесты фиксируют: A45 (scholar 5 → XP камня 10/25/100, НЕ 11/28/110),
B21 (дельта 25, не 28), B22 (дельта 12 = round(11·1.1)), B23 (награда
28 = round(25·1.1) + касание 12 = 40). totalXp — вестись ОБЯЗАТЕЛЬНО
(инвариант addXp:320; пин B21 totalXp-дельта).
