## Контракты: канал c._uiMoves (ядро → UI)

* **Формат**: `null | [{ id, x, y }, …]` — плоский массив принятых
  «to»-тайлов в ПОРЯДКЕ ИСПОЛНЕНИЯ. `from`-поле НЕТ: UI уже снимает
  `beforePos` (снимок ДО фазы, существующий :453) — «до» у него есть.
* **Пишущий** — только замыкания `mobAct` (stepToTarget/stepFromTarget):
  ЧЕРЕЗ НИХ идут ВСЕ движения мобов (000155; melee-цикл, ranged-подход/
  ретрит, TIMID-побег). Запись — ПОСЛЕ успешного тайл-шага и ТОЛЬКО если
  позиция реально изменилась (гард: `pathStepTo` f0===0/замурован → false,
  `stepFromTarget` зажат → false — записи нет):
  ```
  const stepToTarget = () => {
    const bx = u.x, by = u.y;
    const r = pathStepTo(c, u, target,
      u.role === MOB_ROLES.RANGED && dToP > RANGED_MAX_DIST ? RANGED_MAX_DIST : 1);
    if (u.x !== bx || u.y !== by)
      (c._uiMoves || (c._uiMoves = [])).push({ id: u.id, x: u.x, y: u.y });
    return r;
  };
  const stepFromTarget = () => {
    const bx = u.x, by = u.y;
    const r = stepAwayRect(c, u, target) || pathStepFrom(c, u, target);
    if (u.x !== bx || u.y !== by)
      (c._uiMoves || (c._uiMoves = [])).push({ id: u.id, x: u.x, y: u.y });
    return r;
  };
  ```
* **Читающий** — только endTurn-тханк combat-ui.js (drain: прочитал →
  `c._uiMoves = null`). Ядро поле НЕ читает (UI-поле на c; прецеденты
  `c._fx` (UI пишет) / `c._unitFx` (UI пишет) / `c._uiEvents` (намерение из
  комментария combat-ui.js:370 — здесь реализовано в минимальном виде)).
* **Жизненный цикл**: createCombat → `null` (литерал); ПОСЛЕ pre-roll →

* **Детерминизм**: запись — 0 `c._rng`, 0 строк `c.log`, никаких полей

## Переиспользование пути A* (почему UI не пересчитывает)

A* 000155 — BFS-поле расстояний + одношаговый жадный спуск с «вето поля»;
один вызов = один тайл; «полного пути» нигде не хранится (поле
пересчитывается на каждый шаг и учитывает позиции ДРУГИХ юнитов, ставших
стенами за фазу). Варианты:
* (a) пересчитать путь в UI — ОТКЛОНЕНО: решения зависят от `c._rng`
  (UI его не видит) и от реакций/смертей других юнитов в фазе — replay
  разойдётся с ядром;
* (b) экспортировать из ядра «полный путь» — ОТКЛОНЕНО: реструктуризация
  ядра 000155, угроза пинам R1–R10;
* (c) ВЫБРАНО: ядро записывает принятые шаги (транспорт c._uiMoves), UI
  рисует ИМЕННО эту последовательность тайлов — точная запись, не
  реконструкция и не сглаживание.

## Механизм анимации (combat-ui.js)

* **Состояние**: `moveAnims` — модульный `null | Map id → { path, at }`,
  где `path = [{x,y}, …]`: `path[0]` — визуальный якорь на СТАРТЕ фазы
  (дробная точка, если моб ещё глейдит предыдущую фазу; иначе модель из
  beforePos), `path[n]` — финальный тайл модели; `n` = число шагов (1,
  у fast-мобов 2). `at` — `nowMs()` в момент drain. null = нет анимаций
  (steady-state: `px/py = u.x*CELL` бит-в-бит, 0 новых draw-вызовов —
  golden :1618 и все drawCalls-пины).
* **Тайминг**: `MOB_MOVE_MS = 300` на СЕГМЕНТ (1 тайл; порядок FX_MS
  000062); волна fast-моба (2 сегмента) = 600 мс. Easing — ПООТРЕЗОЧНЫЙ
  smoothstep (каждый сегмент — свой глейд, «шаг по клеткам», как 000033).
* **Селектор** (чистый по (u, moveAnims, now), кроме self-cleaning):
  ```
  mobAnchor(u, now):
    if (!u.alive || !moveAnims || !moveAnims.has(u.id)) → {x: u.x, y: u.y};
    motion = liveGame();                    // лениво, в момент вызова;
    // motion.js API (lerpPos/easeInOut/stepProgress) — НАПРЯМУЮ на
    // объекте Game (UMD: Object.assign) — неймспейса Game.motion НЕТ
    segs = path.length − 1;
    if (!motion || typeof motion.stepProgress !== 'function'
        || segs <= 0) → модель (при segs<=0 — удалить entry);
    tAll = motion.stepProgress(now, at, segs * MOB_MOVE_MS);
    if (tAll >= 1) → удалить entry (и moveAnims=null при пустой), модель;
    raw = tAll * segs; i = clamp(floor(raw), 0, segs−1);
    return motion.lerpPos(path[i], path[i+1], motion.easeInOut(raw − i));
  ```
  Все слои ветки моба (спрайт px+8/py+8, HP-полоса px+8/py+2, уровень,
  подсветка цели) следуют за px/py АВТОМАТИЧЕСКИ (формулы не меняются).
  Multi-cell мобы (2×2/3×3): якорь — верхний-левый (u.x,u.y), весь
  прямоугольник движется как одно (rectFree гарантирует проходимость).
* **Drain** (`startMoveAnims(c, beforePos, now)` в endTurn-тханке):
  `moves = c._uiMoves; c._uiMoves = null;` → если пусто — return (старые
  entries предыдущей фазы живут до своего истечения); сначала prune:
  entry юнита, который !alive/fled/исчез — удалить (труп — на модели);
  затем по группам id (порядок записей сохранён): `from` — `mobAnchor(u, now)`
  ТОЛЬКО если старый entry жив (тот же now/формула: `stepProgress(now, at,
  segs·MOB_MOVE_MS) < 1`, сегменты > 0, motion-ядро на месте) — re-timing от
  ТЕКУЩЕГО визуального якоря (непрерывность без snap-back при быстром Space;
  ограниченная задержка ≤600 мс — прецедент createMover 000033: new target
  от текущей точки); ИНАЧЕ (нет entry ИЛИ entry истёк без рендера) —
  `beforePos.get(id)` (старый финальный тайл; мобильная модель в этот
  момент = НОВЫЙ финал — брало бы reverse-глейд). mobAnchor при tAll≥1
  self-cleaning-обнуляет moveAnims — поэтому `if (!moveAnims) moveAnims =
  new Map()` стоит ПОСЛЕ вычисления from (правки ревью, регрессии R7/R8).
  Новый entry `{path: [from, … to-тайлы], at: now}` (ЗАМЕНА, не накопление).
  Гарды: `!u || u.side !== 'mob' || !u.alive || u.fled` → entry не ставится
  (союзники/герой — НЕ анимируются: их ходы — ввод игрока, дискретно).
* **rAF**: новых НЕТ (пин :725) — playback на существующем tick-цикле
  000047: якорь = функция (состояние, now); в vm (без rAF) — событийный
  синхронный рендер по клавишам. Self-cleaning — в mobAnchor при tAll≥1
  (мутация в render — прецедент ctx.breathedPrev 000118; идемпотентно при
  том же now → golden :1618 держится).
* **z-порядок** — по ФИНАЛЬНОЙ модели (сортировка `list` не тронута):
  стабильно, без мерцания порядка на ходу (моб в полпути «ошибается» z
  относительно соседа на кадр — косметика на сетке 48px, минимальный
  дифф важнее).
* **Блокировки ввода НЕТ**: ядро уже в финальном состоянии (паритет с
  000062 FX-окном); длина ≤600 мс — не мешает.

## Решение C: pre-roll НЕ анимируется

Прерол в createCombat (:2945-2947) — мобы с инициативой выше игрока
действуют ДО первого кадра (стандарт: seed 42, волк — очередь
['m0','player'], pre-roll сдвигает волка (1,0)→(1,1); orc_rider/centipede
— инициатива 6). Если анимировать шаги pre-roll, первый render нарисует
моба на СТАРОМ тайле при фиксированном now в песочнице — сломает
координатные пины первого кадра (:518, :568, :2656). Поэтому ядро
выбрасывает `c._uiMoves` после pre-roll. Игрок pre-roll «телепортом» НЕ
видит (первого кадра ещё не было) — все телепортации, которые он реально
видит (каждая волна после его/союзника действия), анимируются. Цель ТЗ
выполнена; репинов ноль. Ограничение фиксируется в result.
