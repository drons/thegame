# 000387 — канон «замороженного префикса» для реестров «номер→id»

Канон: **замороженный префикс** — строки реестра правятся append-only
против HEAD, длина реестра живая, а рост каталога вне реестра легален
shipped-фолбэком компаратора «в конец по lex». Перенос решения 000379 (items)
на skills-плечо + контракт формата для будущего флипа npc (000318.10).

Актуально на 5a20035f.

## 1. Модель и отличие от items (.379)

- Реестр `tests/scripts/skills-num2id-000318.09.json` (44 пары на rename
  0c17f66b) — замороженный префикс numeric-эпохи: позиции ключей
  000001..000044 и их значения неизменны, справа допустимо только
  дописывание новых строк (append-only против HEAD — зуб T11 файла
  `tests/skills-rename-000318.09.test.js`, helper `LEDGER_APPEND_ONLY_I09`).
- У items (.379) реестр участвует в каноне nums ≡ {1..N}
  (`tests/canon-items-sync-000284.02.test.js`), поэтому рост каталога items
  тянет за собой дописывание строк реестра. У skills такого потребителя нет:
  компаратор `scripts/sync-skills-data.js` (000384) читает ПОРЯДОК КЛЮЧЕЙ
  реестра как канон, а вне-реестровые id ставит в хвост своей группы по lex
  (`:68-91`). Значит рост каталога skills проходит, не трогая файл реестра
  вообще — 0-diff реестра при росте является нормой, а дописывание строки —
  инструментом позиционирования (см. §2).
- Порядок ключей реестра остаётся каноном байтов сейва и панели [I]
  (`src/sheet.js` PRIMARY_KEYS, `src/ui-tab-skills.js`, 000384 ретро-b23 П1)
  при любом росте каталога — canonical-предикат «позиция в реестре, затем
  lex-хвост» воспроизводится тестами `byCanonI09` (skills-rename),
  `designOf` (skills-save-order-000384), `byCanonUI` (ui-skills),
  `byCanon` (skills-registry-unfetter-000387).

## 2. Рецепт роста каталога skills (для будущих волн)

1. Добавить `assets/skills/<id>.json` (slug-шейп, валидный по схеме).
2. `node scripts/sync-skills-data.js` — перегенерация `src/skills-data.js`;
   новый id попадёт в хвост своей группы по lex; байтовая детерминированность
   двух независимых прогонов — канарейка T2 файла
   `tests/skills-registry-unfetter-000387.test.js`.
3. Файл реестра править НЕ нужно — это и есть механизм роста. Правка
   существующих строк (удаление, перестановка, подмена значения) запрещена
   зубом T11 и красит его осмысленным сообщением с этим рецептом.
4. Дописывание строки `pad(N+1) → id` (append) нужен только тогда, когда
   id обязан встать сразу после хвоста реестра, то есть ПЕРЕД прочими
   вне-реестровыми id своей группы. Ключ — следующий свободный numeric,
   порядок существующих ключей 000001..N при этом остаётся неизменным.

## 3. Контракт npc-num2id ДЛЯ 000318.10 (формат флипа)

- Путь будущего реестра: `tests/scripts/npc-num2id-000318.10.json`
  (на базе 5a20035f его ещё НЕТ — зуб T3 сторожит именно момент флипа).
- Реестр при флипе создаётся как замороженный префикс, покрывающий ВСЕ
  файлы каталога `assets/npc` на базе флипа: ключи — подряд
  `000001..000NNN`, значения — id файлов. Счётчик каталога на базе флипа —
  число живое (49 на 5a20035f; волны .320.2x добавляли файлы), в память и
  в тесты он кладётся только с sha-скоупом формата
  «`NN на базе <sha>`» / «Актуально на <sha>» (урок 000385 П2).
- Дальше файл живёт по той же схеме, что skills: строки append-only против
  HEAD; рост каталога npc вне реестра легален через тот же фолбэк «в хвост
  по lex», который компаратор npc обязан унаследовать при флипе.
- Зубы на реестр npc: только «реестр ⊆ каталога» + живой предикат каталога
  (файлы идут подряд префиксом `000001..N`, где N — живой счётчик диска,
  как в T3) + append-only-сверка с HEAD + self-gate от возврата
  замороженных счётчиков (порт T12). Зуб «bijection реестр ≡ всему
  каталогу» заводить нельзя — он убьёт законный рост каталога ровно так,
  как это делал skills-аналог до 000387 (ретро-b23 П4).
- Порядок-потребители npc ДО флипа — живые строки
  `scripts/sync-npc-data.js`:
  `const files = fs.readdirSync(NPC_DIR)`, `.filter((f) => /^\d{6}\.json$/.test(f))`,
  `.sort()` — то есть зеркало `src/npc-data.js` строится по имени файла, а
  генерируемый комментарий-инвентарь печатает строку-контракт
  `порядок массива = нумерация файлов` (`:162`).
  Потребители порядка в src: `src/npc.js` —
  `npcsForBuilding` документирован «в порядке каталога» (`:36`),
  `npcForBuilding` берёт первый элемент этого списка (`[0]`), overlay
  построек `building-ui.js` сопоставляет `Digit([1-9])` с позицией в списке.
- ПОСЛЕ флипа (.10) порядок массива перестаёт быть нумерацией файлов и
  становится порядком ключей реестра — компаратор `sync-npc-data.js`
  обязан тогда читать ключи `tests/scripts/npc-num2id-000318.10.json`,
  hard-fail'ить при его отсутствии (exit 1 — порт SO5 skills) и ставить
  вне-реестровые id в хвост по lex (порт `:68-91` sync-skills-data.js).
  Цитаты этого файла выше — дофлипные; после флипа их переснимать диском
  (зуб T3 при отсутствии реестра краснеет на несуществовании файла, при
  наличии — на расхождении цитат).
