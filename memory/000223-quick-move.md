## 1. Что добавлено / перенесено

Модель «пин» (ссылка на инвентарь) → модель «СВОЯ ЕДИНИЦА»: быстрый слот
(герой — `hero.inventory.quick: (string|null)[3]`, союзник — `ally_quick`
на mid `(string|null)[3]`) хранит id предмета (ФОРМАТ НЕ МЕНЯЕТСЯ,
бит-в-бит сейв, version=1, миграций нет, sanitize — без правок), но это
теперь СВОЯ единица персонажа, а не ссылка:

* закреплении («быстр.») — ровно 1 единица ФИЗИЧЕСКИ СНИМАется
  (герой — из `c.inventory.slots`, союзник — из ОБЩЕГО инвентаря
  `c.player`) и записывается в слот;
* «убрать» — единица ВОЗВРАЩАЕТСЯ в инвентарь;
* бой — расход ИЗ СЛОТА (не из инвентаря).

Слот = ровно 1 единица (qty не хранится; строка, а не {id,qty,bonus} —
иначе бамп версии сейва или серое чтение двух форм — против append-only
и пин save.test.js «миграций нет»).

Действие «Вытащить предмет из инвентаря» ([I], Удача) НЕ МЕНЯЕТСЯ —
всегда из общего инвентаря (hero — playerInvItem, ally — allyInvItem).

Почему физическая (а не display-only, a3): display требует ВЫЧИТАНИЯ
пинов на КАЖДОМ инвентарном экране (панель города, [I] в бою 000195,
торговля, хранилище 000221) — логика дублируется и ломается на новых
поверхностях; продажа/−1/перекладка дают краевые случаи на каждый
экран отдельно. При этом счёт в display-модели системно согласован
(инвентарь+слоты = фактический запас) — отклонён по поверхности/лёгкости
обслуживания, НЕ по «дрейфу счёта» (контраргумент a1 переформулирован).

## 2. Контракты и границы

D1. Перенос `setQuick(c, slot, itemId)`: ровно 1 единица; порядок снятия
    — как «−1»: `removeItem(c, id, 1, false)` (с конца, bonusFirst=false)
    — обычные копии СНАЧАЛА, бонусная — только если обычной нет.
D2. setQuick на ЗАНЯТОМ слоте (API; UI всегда в свободный): СНАЧАЛА
    возвращается старая единица (`canAddItem` dry-run → `addItem`),
    ТОГДА снимается новая; отказ (слоты/вес) — {ok:false, reason} ДО
    любой мутации (атомарность: новая единица не снята, старая в слоте).
    `setQuick(c, slot, null)` = clearQuick.
D3. «Убрать» `clearQuick`: canAddItem → addItem → slot=null; не влезает
    (20 слотов/вес) — {ok:false, reason}, слот НЕ чистится (единица не
    теряется НИКОГДА); пустой слот — {ok:true} (идемпотентно).
D4. Повторный перенос того же типа — в следующий свободный слот
    (freeQuickSlot), до 3 единиц на тип; 4-й — «все быстрые слоты

    единица — интент 000195/CI-9 сохраняется.

## 3. API items.js (новые/изменённые, экспорт)

* `setQuick(c, slot, itemId)` — D1+D2 (перенос 1 единицы; overwrite —
  возврат старой; itemId==null → clearQuick).
* `clearQuick(c, slot)` — D3 (возврат; отказ — slot сохранён).
* `removeItem` — авто-очистка пинов убрана (D5).
* НОВОЕ `useQuickUnit(c, it, learnTarget, effectTarget)` — ядро
  применения БЕЗ расхода: kind-отказы с ТЕМИ ЖЕ причинами, что useItem
  ('оружие — экипируется'/'броня — экипируется'/'реагент нельзя
  применить (торговый товар)'); resurrection_scroll → 'Свиток
  воскрешения можно применить только в бою' (обработка — в combat.js);
  spell_scroll: canLearn(learnTarget||c, spell, 'scroll') ОТКАЗ ДО
  расхода (слот цел — паттерн useItem L606-634), успех — learn;
  эффекты — тот же цикл, что useItem (qty=1, bonusUnits=0, bonusVal=0,
  effectTarget T-валидация как useItem L641-646); результат — useItem-
  shaped {ok, name, hp, mp, skill, practice, craft?, message}.
* НОВОЕ `useQuickItem(c, slot)` — hero-обёртка: range → 'неверный
  быстрый слот'; пустой → 'быстрый слот N пуст'; ghost-id →
  'неизвестный предмет: <id>'; r = useQuickUnit(c, it, c, null);
  отказ — r (слот цел); успех — quick[slot]=null, r.
* НОВОЕ `takeQuickSlot(c, slot)` — D7.
* Внутренний хелпер: цикл эффектов useItem L666-721 выносится в
  `applyItemEffects(c, it, d, T, qty, bonusUnits, bonusVal)` (+ сборка

  побайтово: pre-checks → spell-ветка → resurrection-отказ → d/T/
