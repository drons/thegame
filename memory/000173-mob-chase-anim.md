# 000173 — Механика анимации (motion / trigger / red-test)

Дополнение к memory/000173-mob-chase.md: как устроено движение, что
триггерит, и как красный тест проверяет последовательность позиций.

## 1. Механизм движения (tick/интерполяция)

* **Нет отдельного тика.** Анимация — pure-функция от времени кадра:
  мировой rAF-цикл `frame(now)` (main.js:2505) уже гоняется каждый кадр
  (БЕЗУСЛОВНО — в т.ч. во время боя; inCombat гейтит только tryMove).
  Каждый кадр оба слоя спрашивают у заряда дробную позицию:
  * `drawSprites(now, rp)` — Проход 3: для тайла заряжающейся группы
    `ch = mobCharge.mover.position(now)`, спрайт рисуется в
    `toPt(ch.x, ch.y)` с НЕИЗМЕНЁННОЙ формулой
    `(sx − zoom*0.1, sy − zoom*0.15, zoom*1.2, zoom*1.2)`;
  * `buildFrame(rp, now)` — WebGL-маркер MOB_COLOR той же группы —
    в дробной точке `ch` (`mx+0.30 … mx+0.70`).
  Один кадр = одна точка для обоих слоёв (принцип 000033).
* **Интерполяция** — переиспользуемый `G.createMover` (src/motion.js,
  000033), тот же мувер, что у героя (main.js:330):
  * `step(from={t.x,t.y}, to={цель}, nowMs=T, intervalMs=1500)` — один
    глейд-сегмент «тайл группы → цель» (НЕ тайл-за-тайлом: прямой
    лерп по отрезку, диагональ разрешена — на карте нет препятствий
    для визуального рывка);
  * `position(now)` = `lerpPos(from, to, easeInOut(p))`, где
    `p = stepProgress(now, T, 1500) = clamp01((now − T)/1500)`,
    `easeInOut(t) = t²(3−2t)` (smoothstep, motion.js:79-82): плавный
    старт/финиш, строго возрастающий на (0,1), f(0.5)=0.5;
  * p ≥ 1 — ЦЕЛЬ (кламп, без отката и без перелёта): после 1500 мс
    спрайт стоит на цели до onEnd; p ≤ 0 / NaN-время — старт.
  * Чистая функция: повторные вызовы position — равные объекты;
    детерминизм (MC6) — без RNG, без чтения живых настроек.
* **Тайминг:** T = now кадра, в котором сработал шаг-атака (frame
  передаёт `now` в `maybeStartCombat(true, now)`). Оконечание заряда —
  onEnd боя (victory/fled/dead) — ПЕРВАЯ строка `mobCharge = null`.
  Бой при этом стартует В ТОМ ЖЕ КАДРЕ, что и заряд (D2) — анимация
  идёт ПОД боевым оверлеем (88% непрозрачности) и после возврата.
* **Цель (заморожена на момент атаки, D4):** зона-атака — тайл игрока
  (`player.x/y`); атака на тайле группы — `prevPos`; цель == тайлу
  группы → заряда нет (гард from==to). Игрок в бою заморожен
  (inCombat) — цель не «уплывает».

## 2. Триггер (player attack)

* «Атака персонажа» на глобальной карте = УСПЕШНЫЙ ШАГ, запускающий
  мир-бой через `maybeStartCombat` (единственный игровой орган атаки на
  карте; независимой кнопки атаки нет):
  1. шаг на тайл живой группы (любой класс) — `t` = тайл игрока;
  2. шаг в триггерящую 5×5-зону агрессивной/территориальной группы
     (000135, `G.findZoneCombat`) — `t` = тайл ГРУППЫ;
  3. бут/спавн на тайле группы (`maybeStartCombat()` без аргументов) —
     фактически from==to → заряда нет.
* Заряд устанавливается ВНЕДРИ `maybeStartCombat` ПОСЛЕ всех guard'ов
  (`isActive`, `defeatedAt`) и выбора `t`, ПЕРЕД `startCombat`:
  `G.combatUI.isActive()` guard (первая строка) гарантирует, что второй
  заряд поверх активного боя невозможен.
* НЕ триггер: `startCombatAt` (debug/`__game.actions.startCombat`/босс
  000077 — отдельная функция), `startDungeonCombat` (подземелье),
  вход в зону БЕЗ шага (спавн/сейв в зоне — HUD предупреждает, заряда
  и боя нет — пин Z6б).

## 3. Как красный тест ассертит последовательность позиций

Файл: `tests/mob-chase-e2e.test.js` (vm, полная цепочка `<script>` из
index.html; шаблон tests/mob-zones-e2e.test.js: makeGl/makeContext2d/
makeEl/seedSave/boot/drain/makeWalker/spyStartCombat/
resolveCombatVictory; фолбэк-мир: map.png всегда onerror →
G.generateSeedPixels, детерминированно).

* **Помп (D-ПРОТОКОЛ):** после boot и drain'ов — `worldFn =
  h.raf[h.raf.length - 1]` (до боя последний rAF-колбэк — мировой
  frame). Далее кадры гоняются ТОЛЬКО через `worldFn(now)` — НЕ
  `h.raf[last]`: в открытом боевом оверлее combat-ui.js рекурсирует
  собственный `tick` (combat-ui.js:1455-1458, L1603) в той же очереди —
  «последний» не гарантированно мировой. `performance.now()` в
  песочнице заморожен (NOW=1000) — все now явные, растущие.
* **Сценарий MC1 (zone-атака, «position sequence advances toward the
  player»):** спавн (0,0); `walk(0,1)` (makeWalker: keydown → кадры
  +200 мс → keyup) — вход в 5×5-зону пауков (2,3), бой на шаге (пин
  Z5: cap.calls=1, seed=hash2(2,3,0x5eedc0de), tile=(2,3) — НЕ
  меняются). Возвращённый now шага = T. Затем 12-14 кадров
  `worldFn(T + 50·k)` (окно ~650-700 мс). В каждом кадре:
  * `mc = g.state.mobCharge` — ненулевая, `key='2,3'`, `from=(2,3)`,
    `to=(0,1)` (тайл игрока на момент атаки);
  * последовательность `pos_k = mc.pos` (тайловые координаты, на
    lastFrameNow): дистанция Чебышёва/Манхэтена до `to` (== до игрока)
    СТРОГО уменьшается кадр за кадром (easeInOut строго возрастающ —
    12-14 строгих убываний до конца окна) и `pos_12/14` уже близко к
    `to` (p(T+700/1500)=easeInOut(0.467)≈0.44 → ≤1.2 тайла);
    `pos_0` (первый кадр после T) ≠ `pos_last` — сдвиг есть;
  * канал drawCalls: кадр атаки — спрайт g4 ровно на якоря (формула
    000122: `worldToScreen(2,3,cam) − (0.1z, 0.15z)`); кадр середины
    окна — drawImage g4 НЕ совпадает ни с якорем from, ни с якорем to
    (дробная точка, Δ ≥ ~0.5·zoom по оси) — «глейд, а не телепорт/
    скачок».
  * КРАСНЫЙ сейчас: mob-спрайт на фиксированном якоря (проход 3
    `toPt(t.x,t.y)`) → дистанция КОНСТАНТНА, `state.mobCharge` —
    undefined → ассерты «строго убывает / движется» падают осмысленно
    («моб не приближается к игроку»), не синтаксически.
* **MC2 (монотонность и множественность кадров):** по тем же сэмплам
  MC1: (а) `dist(pos_{k+1}, to) ≤ dist(pos_k, to) + EPS` для ВСЕХ
  соседних пар (монотонность — без осцилляции); (б) ≥ 3 СТРОГИХ
  убывания в окне (без «прыжка в конец за один кадр»: если бы глейд
  завершался мгновенно, строгих убываний было бы ≤ 1); (в) окно
  содержит ≥ 2 кадра с `0 < p < 1` (глейд ещё не закончен — не
  «снап на цель»).
* **MC3 (атака НА тайле, D4 on-tile цель = prevPos):** `walk(1,0)` на
  логово скелетов (1,0) (g2, neutral — пин Z3b: seed=hash2(1,0,SALT),
  tile=(1,0) — НЕ меняются): `mc.from=(1,0)`, `mc.to=(0,0)` (=prevPos —
  тайл, с которого шагнул; НЕ `(1,0)` — иначе от анимации ничего не
  осталось бы в самом частом случае). Последовательность pos → (0,0):
  дистанция строго убывает за окно. ВАЖНО: ассерт — до ЗАМОРОЖЕННОЙ
  `to`, а не до живой точки рендера героя (герой сам глейдит
  (0,0)→(1,0) за 420 мс — дистанция до живой точки не монотонна:
  сближение → пересечение → расхождение).
* **MC0 (GUARD, зелёный с рождения):** ВСЕ кадры ходьбы ДО шага-атаки
  — все видимые группы ровно на якорях (формула 000122),
  `state.mobCharge` null — «погоня не начинается раньше атаки»
  (страховка от дизайна «старт по входу в зону»).
* **MC4 (GUARD):** после атаки на (2,3) ВСЕ прочие видимые группы — на
  своих якорях; число mob-draw (= число групп кадра) не изменилось
  (ни шлейфа, ни двойного draw); порядок слоёв «мобы < Флогистон»
  сохранён.
* **MC5 (GUARD):** победа (resolveCombatVictory) → `mobCharge` null,
  спрайт g4 скрыт (000122, defeatedAt), draw = 0 по g4; побег
  (результат 'fled' — через combatInternals-паттерн: игрок на prevPos)
  → следующий кадр: `mobCharge` null, спрайт g4 снова НА ЯКОРЯ (нет
  «залипшего» смещения).
* **MC6 (GUARD):** два независимых boot одного сценария (MC1-шаблон) →
  ПОБАЙТОВ одинаковые последовательности `pos_k` (EPS 1e-9) —
  детерминизм (ноль RNG, время — только аргумент кадра).

expectedRedCount = 3 (MC1/MC2/MC3). Guards (MC0/MC4/MC5/MC6) — зелёные
на обеих стадиях. Существующие тесты — БЕЗ ПРАВОК (D10): 000135-пины
(Z3b/Z5/Z6a/Z6б/Z8) и 000122/000039-пины (формула прохода 3, порядок,
число draw) проходят без изменений — заряд неактивен в их сценариях
(без шага-атаки) либо не влияет (тайминг боя не меняется, D2).
