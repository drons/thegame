## 2. Решения (D1–D14) — решение — почему

**D1. W(depth) = min(63, round(base·1.1^(depth−1))); cap = 63, чистая
экспортированная `dungeonSizeFor(base, depth)`; рост ТОЛЬКО в коде от
базы JSON; depth=1 → base бит-в-бит** — cap 63 = максимум схемы
assets/dungeons/schema.json «размер» 5..63, т.е. задокументированный
диапазон базы остаётся истинным (JSON не трогаем); перформанс НЕ
лимитирует (W=63 → 3.0 мс, W=128 → 2.6 мс, N=30 — cap — дизайн-решение,
не вынужденное). Числовой параметр base (не type): функция чисто
числовая, тестируема без каталога, каталог-lookup остаётся на вызове
(:319). Math.round — half-up в +∞: 25·1.1=27.500…0004→28,
35·1.1=38.5→39 — зафиксировано W-таблицей в тесте SZ-1 (если V8 когда-либо
поменяет FP-окружение — тест поймает). ТЗ «perформанс-тест W>63»:
измерено в /tmp (headroom W=64..128) + npm-guard SZ-3 на cap.

**D2. Уровни мобов: `effLevel = player.level + (d.depth − 1)` (константа,
одна строка после :432); группы = max(1, effLevel ± δ); босс ABYSS =
max(1, effLevel + δ)** — ТЗ: сдвиг БАЗЫ уровня (не дельты); число
вызовов rng НЕ меняется (одна rng-строка на группу как было); обе
формулы свёртываются ТОЧНО при depth=1 (`x + 0 === x` — тождество FP).

**D3. Сундуки: `nChests = 2 + floor(rng·4) + (d.depth − 1)` (+1 сундук/
этаж; диапазон [d+1, d+4])** — выбрано вместо a1 `+floor((d−1)/2)` и a3
`2+floor(rng·(4+(d−1)))`: красное свойство ТЗ «≥ depth=1 и монотонно
растут» выполняется НАИЛУЧШЕ (диапазон строго доминирует на каждом
этаже: нижний край d+1 > верхнего края depth=1 (=5) уже при d=5); та же
ритмика +1/этаж, что и сдвиг уровня; площадь растёт ×1.21/этаж → плотность
сундуков остаётся консервативной; ОДИН вызов rng (как сейчас); свёртка
depth=1 точная (+0). Явного cap нет — takeSpot→null уже останавливает
цикл (существующее поведение). ПОСЛЕДСТВИЕ: chest-значения в
goldens-precomputed.json (сгенерированы по формуле a1) — ПЕРЕЗАХВАТИТЬ
на зелёной стадии; ФОРМА и mobs НЕ зависят от D3 (mobs рулятся ДО
сундуков, один roll nChests в обоих вариантах).

**D4. stairs-down = replica АЛГОРИТМ ВЕРБАТИМ: max-BFS-дистанция от
entrance среди FLOOR ∖ 5×5 safe ∖ {босс ABYSS}; тай — min hash2(x, y,
STAIRS_SALT ^ d.seed); финальный тай — min (y·W+x); соль 0x53d10d53;
fail-open → null; размещается в createDungeon после d.wallObjs (форма,

## 3. Контракты и границы

### Формулы (финальные, для .05)
* `W(depth) = min(DUNGEON_SIZE_CAP, round(base · 1.1^(depth−1)))`,
  DUNGEON_SIZE_CAP = 63; base = DUNGEON_SIZE[type] из JSON (CAVE 25 /
  CRYPT 27 / RUINS 31 / DROWNED 27 / ABYSS 35). СТОРОНА ×1.1/этаж →
  ПЛОЩАДЬ ×1.21/этаж (фиксируется в .05).
* `effLevel = player.level + (depth−1)`.
* Группы: `level = max(1, effLevel + floor(rng·(2δ+1)) − δ)`,
  δ = level_delta_max (default 3, live-чтение :432).
* Босс ABYSS: `level = max(1, effLevel + δ)`.
* `nChests = 2 + floor(rng·4) + (depth−1)`; `gold = round(10 + rng·20·
  (1 + 0.2·effLevel))`; item — uniform, шанс 0.4 (НЕ меняется; редкость
  предметов = территория 000157, НЕ .02: ТЗ п.4 «качество» = gold +
  кол-во сундуков).

### W-таблицы (предвычислено; cap с помеченной глубины)

### Поле d.stairsDown
* `stairsDown: {x, y} | null` — поле ФОРМЫ (createDungeon), НЕ contents.
* Инварианты (ВСЕ глубины): на FLOOR; достижима от entrance
