## 2. Контракт размещения призывного (что важно будущим задачам)

* Свободная клетка = в границах + ∉ occ + ∉ c.obstacles. occ = клетка
  игрока (c.px,c.py) + ВСЕ прямоугольники c.units (без alive-фильтра —
  старая семантика не меняется).
* Алгоритм БЕЗ ИЗМЕНЕНИЙ: 5 якорей вокруг (c.px, c.py) В ФИКСИРОВАННОМ
  ПОРЯДКЕ ((px−1,py−1), (px+1,py−1), (px,py−1), (px−1,py), (px+1,py)) →
  при занятости — построчный скан СНИЗУ ВВЕРХ (y: height−1 → 0, x: 0 →
  width−1). Кастер призыва ВСЕГДА игрок (combat-ui.js castSpell :2921/:3020
  — персонаж; efirCastAction combat.js:2469 кастует только «урон») →
  якоря = вокруг кастера.
* 0 c._rng в расстановке — поток RNG боя не тронут, детерминизм по сиду
  сохранён, сейв-формат v1 не меняется.
* allyRoom — ТОЧНОЕ ЗЕРКАЛО placeAllies (тот же порядок якорей/скана,
  та же free). Расхождение недопустимо: ложь allyRoom → «нет места для
  призыва» (fail-closed ДО расхода пула/маны, spells.js:500); при
  расхождении placeAllies бросил бы «нет места для союзника» (:3312)
  ПОСЛЕ успешного гейта.
* Единый корень: точки вставки в c.units — ДВЕ: createCombat (concat
  allies :3672-3673) и case 'призыв' (push spells.js:819). Мид-комбат —
  только призыв.

## 3. Почему баг был только у призывных (SCOPE 3 ТЗ — дочерней задачи НЕТ)

* createCombat: placeUnits (:3663) → placeAllies (:3672) →
  generateObstacles (:3690). В момент placeAllies c.obstacles ПУСТ
  (инициализация :3614) → расстановка состава (наёмники/Эфир) бит-в-бит.
* generateObstacles строит reserved = клетка игрока + ВСЕ клетки
  c.units (:3479-3487) → камень не ляжет на стартовые юниты (пин
  tests/combat.test.js:2327-2339).
* Каст призыва — единственный путь, где placeAllies/allyRoom исполняются
  при НЕПУСТОМ c.obstacles → единственный битый сценарий. Фикс общего
  корня закрывает и любой будущий mid-combat-путь через placeAllies.
* Не-призванные мобы целы → ТЗ SCOPE 3 решён в этой задаче (общий
  корень), дочерняя задача НЕ создаётся.
