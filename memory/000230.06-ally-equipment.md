## 2. Контракты и границы

### 2.1 Паттерн КОМПОЗИТНОГО «персонажа» (почему items.js не
### меняется)

Generic `equip(c, itemId)` / `unequip(c, slot)` (000230.02)
требуют от «персонажа» только: `inventory` (общий инвентарь —
hasItem/ensureInventory/addItem), `primary`/`secondary` (вес:
addItem → checkAdd → maxCarryWeight → `P.derived(c).carryWeightMult`
— «Крепкая спина»), `equipment`, `equipmentBonus` (ensure*
нормализуют НА МЕСТЕ). Экипировка наёмника ОТДЕЛЕНА от общего
инвентаря (ТЗ: «Предмет — из ОБЩЕГО инвентаря героя» + «эффект — на
самого наёмника»): прямой `equip(entry.sheet, id)` падает «предмета
нет в инвентаре» (у sheet нет inventory — дельта a1 D1). Решение —
композитный объект (НОВЫХ функций в items.js НЕТ):

```
view = {
  inventory:        hero.inventory,        // владелец веса (000194)
  primary:          hero.primary,          // вес-чек — от героя
  secondary:        hero.secondary,        // «Крепкая спина»
  equipment:        sheet.equipment,       // ЖИВАЯ ссылка (pre-init {})
  equipmentBonus:   sheet.equipmentBonus,  // ЖИВАЯ ссылка (pre-init {})
}
G.equip(view, itemId) / G.unequip(view, slot)
```

* `sheet.equipment`/`sheet.equipmentBonus` инициализируются `{}`
  ДО вызова (если не plain-объект). ПОЧЕМУ: `ensureEquipment(c)`
  ПРИСВОИВАЕТ новый объект при не-объектном `c.equipment` — без
  pre-init «экипировка» записалась бы в выбрасываемый композит, а
  предмет ушёл бы из инвентаря героя (проверено исполнением a3
  I1: entry.sheet.equipment === undefined — предмет теряется).
  Живые ссылки → ensure* делают идемпотентную in-place
  канонизацию (18 физ. слотов + зеркала weapon/armor) живого
  листа.
* Материализация sheet.equipment/equipmentBonus на живом листе —
  ЛЕНИВО при ПЕРВОМ allyEquip/allyUnequip (паттерн 000230.02
  «ленивое создание при первом equip») — НЕ в createMercSheet
  (пин CS-1: 10 ключей) и НЕ на read-пути allyDataForEntry
  (§2.3). Форма листа — 10 или 12 ключей. НЕУДАЧНАЯ попытка
  (generic-отказ: «такое не экипируется» — зелье, «неизвестный
  предмет», «предмета нет в инвентаре») ТАКЖЕ материализует
  ПУСТЫЕ секции: pre-init (D-03) идёт ДО generic и обратно не
  откатывается (откат — лишний код без выигрыша, ревью
  2026-10-20: принято). После неудачи лист — 12 ключей с
  null-слотами: канон 20/18 после round-trip, все читатели
  absent ≡ {} — НОЛЬ поведенческой разницы, байты сейва
  (12-ключевой лист с пустыми секциями) — легальная форма
  (ревью-верификация: allyEquip(hero, sheet,
  'healing_potion') → {ok:false, reason:'такое не экипируется'},
  'equipment' in sheet === true, serializeRoster —
  "equipment":{}→канон 20 null). После UI .07 (клик по
  «надеть» на любом предмете) пустые секции будут у большинства
  наёмников — это и есть задокументированная D-09.
* Зачем primary/secondary ГЕРОЯ: лимит веса — владельца общего
  инвентаря (000194: весь лут/магазин/крафт партии — в
  hero.inventory). addItem-вес-чек при swap/unequip (возврат
  прежнего/снятого предмета) прогоняется от derived героя. Лист
  наёмника «носит» предмет — сам его не «носит».
* Бонус качества (000046) ПЕРЕНОСИТСЯ на наёмника: generic equip
  берёт ПЕРВУЮ копию (первый слот инвентаря с этим id — НЕ
  bonusFirst — геройская семантика .02/.046) и переносит её
  бонус в `eb[slot]`; unequip возвращает его с предметом. Статы
  включают бонус (equipmentStats — 000046 обязателен, .02 §2.11).
  Код на это НЕТ — generic API делает сам (ОТКЛОНЕНИЕ от
  a1 §5.2 — D-02).

### 2.2 API allyEquip / allyUnequip (экспорты companions.js —
### контракт для 000230.07)

```
allyEquip(hero, sheet, itemId) →
  {ok:true, slot, item}
  | {ok:true, slot, item, note:'вернуть <id> не удалось: <reason>'}
  | {ok:false, reason}
allyUnequip(hero, sheet, slot) →
  {ok:true, item} | {ok:false, reason}
  (slot — EQUIP_PHYS_SLOTS или алиасы 'weapon'/'armor' —
   generic unequip разрешает их)
```

Guards (порядок, ДО API):
1. `sheet` не plain-объект → `{ok:false, reason:'нет листа персонажа'}`
2. `sheet.kind === 'efir'` →
   `{ok:false, reason:'Эфир — дух, не экипируется'}`
   (точная строка ТЗ — пинится; UI-форма для .07)
3. `sheet.kind !== 'merc'` →
   `{ok:false, reason:'не лист наёмника'}` (hero-лист не цель —
   «не больше, чем просит ТЗ»)
4. `hero` не объект / его `primary`/`secondary`/`inventory` не
   plain-объекты → `{ok:false, reason:'нет персонажа'}`
   (без primary/secondary — `P.derived` в вес-чеке упал бы с
   TypeError; без inventory при unequip — предмет ушёл бы в
   выбрасываемый композит)
5. `typeof G.equip !== 'function'` (resp. G.unequip) →
   `{ok:false, reason:'экипировка недоступна (items.js не загружен)'}`
   (деградация — §3)

Дальше: pre-init sheet.equipment/equipmentBonus (§2.1) +
`return G.equip(view, itemId)` / `G.unequip(view, slot)` —
generic-результат возвращается КАК ЕСТЬ. Reason generic (дословно,
геройские пины): 'неизвестный предмет: …', 'такое не экипируется',
'уже экипировано', 'предмета нет в инвентаре', 'нет свободных
слотов колец', 'ничего не экипировано'; failsafe unequip
(инвентарь полон / вес) → `{ok:false, reason:'нет свободных слотов
инвентаря' | 'слишком тяжело (лимит веса)'}` — предмет ОСТАЁТСЯ
надетым (зеркало геройского unequip — паттерн 000194).

Для .07 (вкладка «Снаряжение» активного союзника, 19 строк;
Эфир — заблокирован): hero = объект активного персонажа
(Game.hero / activeCharId 000145), sheet = entry.sheet (roster
000143); перечисление слотов — `G.EQUIP_PHYS_SLOTS`/`G.RING_SLOTS`
(items-экспорты, топовые ключи Game); read-путь —
`G.equipmentStats(entry.sheet)` / `G.equipmentAffixes(entry.sheet)`
напрямую (НОВОГО read-API НЕ НУЖНО — «не больше, чем просит ТЗ»);
reason/note из возврата — в UI; отказ Эфира — guard 2 (точная
строка).

### 2.3 Зафиксированные формулы allyDataForEntry (цели пинов)

```
dd = G.Sheet.derived(entry.sheet, { modifier: mercModifier, h })
     // база — affix-ОСВЕДОМЛЕННАЯ (.03 D-01 — единая точка pct)
es = (sheet.equipment — plain-объект && typeof G.equipmentStats
     === 'function') ? G.equipmentStats(entry.sheet) : null
aff = (typeof G.equipmentAffixes === 'function')
        ? G.equipmentAffixes(entry.sheet) : null
freeCast = (aff && aff.freeCast) ? [...aff.freeCast] : []

damage = dd.damage + (es ? es.damage : 0)
armor  = (es && es.armor > 0) ? ((h.armor || 0) + es.armor) : h.armor
```

* damage = база mercModifier (каталожные кнопки dmg + уровень +
  fist/heavy/ranged) + `equipmentStats(sheet).damage` =
  stats.damage оружия right_hand + бонус качества (000046). БЕЗ
  dmgBonus/subtype/hitBonus — у ally-юнитов subtype-механик НЕТ
  (allyAttack — плоский u.damage, hitChance по уровню; ТЗ «урон
  оружия/броня» = каталожные статы + бонус).
* armor — Σ stats.armor всех 18 физ. слотов + бонусы: применяется
  ТОЛЬКО если > 0; иначе `h.armor` КАК ЕСТЬ (undefined остаётся
  undefined — Вольк с мечом в руке: armor: undefined; Бальдор: 3
  без брони-экипировки). Одна формула — два поведения — бит-в-бит
  пин.
* freeCast — Set из equipmentAffixes (итерация = порядок
  вставки = порядок EQUIP_PHYS_SLOTS — ДЕТЕРМИНИРОВАННО) → plain-
  массив (makeAlly принимает массив; снапшот D-05 .03). Seam .03
  D-12 дословно: «в .06 станет
  [...I.equipmentAffixes(entry.sheet).freeCast]».
* `es` — только при НАЛИЧИИ sheet.equipment: `equipmentStats`
  вызывает `ensureEquipment(c)` (МАТЕРИАЛИЗАЦИЯ!) — read-путь не
  должен создавать раздел у наёмника без экипировки (сейв
  «absent → absent», §2.4). `equipmentAffixes` — ЧИСТАЯ (без
  ensure, .03 D-03) — вызывается безусловна, с typeof-guard.
* Skill-affixes на экипировке наёмника — АВТОМАТИЧЕСКИ
  существующим пайплайном (НОВОГО КОДА НЕТ): mercModifier
  получает affix-осведомлённую базу (derived/pct — единая точка
  .03 D-01; player.js:195 re-export sheet.derived, т.е. P.derived
  в equipmentStats — тот же с affix-seam) — напр. 'heavy'-affix
  автомасштабирует БАЗУ урона наёмника.
* Бит-в-бит БЕЗ экипировки: eq absent → es null → damage =
  dd.damage + 0, armor = h.armor, freeCast = [] — значения
  идентичны текущим (пины companions :941-976 / :994-1008 / CS-4
  — зелёные БЕЗ правок).
* Порядок ключей возвращаемого объекта НЕ меняется (id, name,
  role, level, maxHP, damage, armor, skills, spells, attrs, kind,
  freeCast).
* makeAlly/combat.js НЕ ТРОГАЮТСЯ: `data.damage` — ЕДИНСТВЕННЫЙ
  рычаг урона наёмника (makeAlly: `data.damage != null →
  max(1, round(data.damage · moraleMult))`; allyAttack читает
  u.damage), `armor = (data.armor || 0) + floor(level/10)` — как
  было. 000082-золотые (сырые фикстуры, не через
  allyDataForEntry) — бит-в-бит.
* Set-бонусы — АВТОМАТИЧЕСКИ через ОБЩИЙ агрегат 000230.04 после
  её мержа; код наборов в .06 НЕ пишется (ТЗ «Что сделать» 2;
  общий файл companions.js — мерж ПОСЛЕ .04, §5).

Опорные значения для пинов (реальный каталог, верифицировано
2026-10-20): iron_sword — dmg 5 (sword, 1.5 кг), wood_sword — 3,
battle_axe — 8 (heavy), chainmail — armor 4, leather_armor — 2,

  (absent = пусто — ВХОД sanitize, а не выход)». Мусор не-

  `G.sanitizeEquipment(Bonus)` отсутствует (деградация,

* Семантика «absent ≡ {}»: ВСЕ читатели (allyDataForEntry §2.3,
  affixSkillsFor .03, ensure*) трактуют отсутствие
  sheet.equipment как пусто — СТАРЫЙ сейв (до .06) ВАЛИДЕН,

* Старая 5-полевая форма (e.sheet == null) — backfill через
  createMercSheet — БЕЗ ИЗМЕНЕНИЙ (без equipment) — CS-3 зелёный.
* dead_mercs (000161) — АВТОМАТИЧЕСКИ: запись несёт 12-ключевой

### 2.5 Эфир (трёхкратный guard .03 D-09 — сохраняется)

* Write-путь — НОВЫЙ guard 2 в allyEquip/allyUnequip (точная
  строка ТЗ «Эфир — дух, не экипируется»).
* Read-путь — Эфир НЕ ходит через allyDataForEntry: roster —
  только наёмники; эфирный юнит строится buildEfirUnit (efir.js)
  из efirAllyData — `{id:'efir', …, kind:'efir'}` БЕЗ
  equipment/freeCast (green sub-pin, C3). «allyDataForEntry
