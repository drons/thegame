## 1. Дефект и решение станции (фиксируется ДО кода, по требованию ТЗ)

Прежняя форма: §2 канона memory/000230.16-spec-equipment-doc.md, абзац
«Текущий spec/items.md: … N байт (<дельта-история волн инлайн>)» — ОДНА
физическая строка (разбитая переносами) вмещала и tip-байты, и все
дельты ~24 волн. Любые две параллельные items/spec-волны конфликтуют
ВНУТРИ неё (git не склеивает вставку в одну позицию), разрешение —
ручное при каждой ре-базе (прецеденты: .374×.321.08; doc-trio .321.09
spec/items.md +148 байт ≡ memory ≡ wording W8A).

ВЫБОР СТАНЦИИ: лог = каталог `memory/000230.16-c9/`, ПО ОДНОМУ ФАЙЛУ
`<taskid>.md` на волну. АЛЬТЕРНАТИВА ОТКЛОНЕНА ЭМПИРИЧЕСКИ: один общий
лог-файл с построчными дельтами — две параллельные вставки в конец
одного файла = гарантированный git-конфликт (проверено в scratch-репо
на стадии анализа); значит синтетическое требование ТЗ «авто-мердж двух
волн БЕЗ конфликта» в однофайловой форме было бы нечестным. Разные
пути ⇒ конфликт структурно невозможен (паттерн-прецедент: реестр
tests/scripts/items-num2id-000318.08.json — append-only; здесь — файл
на волну вместо строки на волну). Промежуточная «строка лога» ≡ первая
строка entry-файла — форма ТЗ «<задача>: <байты после> (+дельта)»
сохранена дословно, только носителем стал отдельный файл.

ПРЕДИКАТЫ (зуб tests/items-spec-bytes-log-000386.test.js):
- P0 схема: первая строка entry ≡ /^(\d{6}(?:\.\d+)*): (\d+) \(([+-]\d+)\)$/
  и id ≡ basename файла.
- P1 биекция: множество entry-файлов ≡ множеству taskid коммитов
  «Задача <id>…», трогавших spec/items.md в истории HEAD (поиск ПО
  SUBJECT, не по хешу — ff-мержи и rebase-станции меняют хеши, subject
  сохраняется; `--no-merges` — мерж в проекте ff, merge-коммит не волна;
  наивный 3-way merge двух волн делает tip-запись ≠ диск — станция
  обязана rebase+re-замер, это демонстрирует T8).
- P2 историческая правда (это и есть «каждая строка верна на своём
  срезе истории», запиненная доступным механизмом): для каждой entry
  bytes ≡ Buffer.byteLength(git show <коммит волны>:spec/items.md), а Δ
  ≡ bytes − bytes предыдущего трогателя spec/items.md В ИСТОРИИ САМОГО
  КОММИТА (`git log -2 <коммит> -- spec/items.md`, для первого — от 0).
  Локальность коммиту принципиальна: в победившей истории после
  out-of-order мержей линейная цепочка log не обязана совпадать с
  дельтой волны — монотонность по позиции в тексте НЕ пинится (это и
  есть оговорка ТЗ про «чужие вставки между мержами»).
- P3 tip: entry последнего трогателя spec/items.md ≡ живому
  Buffer.byteLength(spec/items.md); плюс «ровно одна entry ≡ живому
  байту» (канарейка: сработает при точном возврате к историческому
  объёму — разбирается вручную).
- P4 append-only (HEAD-guard класс): entry-файлы, присутствующие в
  HEAD, побайтово равны диску; исчезновение/переписывание истории
  красит; новые файлы — только добавление. Тот же класс, что
  items-rename-000318.08 T9 / skills-rename T8: зелёно только на чистом
  закоммиченном дереве — станции: КОММИТ ДО прогонов.
- P5 форма §2: абзац «Текущий spec/items.md:» — стабильная форма без
  байтового литерала («байтовый канон = живой расчёт
  canon-items-sync-core.specMeta.bytes»; в norm'd §2 нет ни одного
  «NNN байт»); дельты живут только в логе.
