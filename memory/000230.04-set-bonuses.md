## 2. Контракты и границы

### 2.1 schema.json — точная под-схема `set_bonus`

Позиция: ПОСЛЕ `affixes` (новый конец properties; канон-порядок = порядок
properties = порядок KEYS sync — связка E1b/E20). «set_bonus» НЕ в
required (старые предметы валидны). Точная форма (deepEqual-пин SB1):

```
set_bonus = {
  type: 'object',
  anyOf: [ {required:['2']}, {required:['3']}, {required:['4']} ],
  properties: { '2': EFFECT, '3': EFFECT, '4': EFFECT },   // EFFECT ×3
  additionalProperties: false
}
EFFECT = oneOf: [
  { type: 'array', minItems: 1,
    items: oneOf: [
      { type: 'object', required: ['type','skill','amount'],
        properties: { type: {const:'skill'},
                      skill: {type:'string', pattern:'^[a-z][a-z0-9_]*$'},
                      amount: {type:'number'} },
        additionalProperties: false },
      { type: 'object', required: ['type','spell'],
        properties: { type: {const:'free_cast'},
                      spell: {type:'string', pattern:'^[a-z][a-z0-9_]*$'} },
        additionalProperties: false } ] },
  { type: 'object',
    anyOf: [ {required:['armor']}, {required:['damage']} ],
    properties: { damage: {type:'number', minimum:1, maximum:100},
                  armor:  {type:'number', minimum:0, maximum:100} },
    additionalProperties: false } ]
```

* Аффикс-вариант — Дословно properties.affixes (SB1: deepEqual
  `set_bonus.properties['2'].oneOf[0]` ≡ `properties.affixes`).
* Стат-вариант — «те же ограничения, что affixes» (ТЗ п.1) интерпретация:
  ГРАНИЦЫ как у существующего объекта `stats` схемы (damage 1..100,
  armor 0..100) — зафиксировано; порядок ключи damage→armor — зеркало
  существующего stats.
* Ключи "2"/"3"/"4" — строки (JSON-ключи); additionalProperties false
  отбрасывает "1"/"5"/«2.5» — пороги ⊆ {2,3,4} на уровне схемы.
* Непустота: set_bonus — anyOf [required 2/3/4] ({} → невалидно);
  стат-объект — anyOf [required armor/damage] ({} → невалидно).
* EFFECT инлайнится ×3: минивалидатор (000015, tests/json-schema.js) НЕ
  поддерживает $ref/definitions/patternProperties/propertyNames
  (ALLOWED_SCHEMA_KEYS: type/required/properties/additionalProperties/
  items/enum/const/minimum/maximum/minItems/maxItems/pattern/anyOf/oneOf)
  — единственный доступный приём. oneOf array|object взаимоисключаем по
  type («подошло вариантов oneOf: N, нужно 1» работает).

### 2.2 Валидация (load-time throw; браузер/vm — ТОЛЬКО JS-валидатор)

* `validateItem` — equipment-only-гард (:255-257) += `it.set_bonus !==
  undefined`; сообщение → «поля экипировки (slot/rarity/set/set_bonus/
  affixes) — только у экипируемых» (E18-пин /только у экипируемых/ жив
  без правок — regex на хвосте).
* После set-паттерна (:275-278): `set_bonus !== undefined && set ===
  undefined` → throw «set_bonus — только с set» (ТЗ п.3 дословно).
* `validateSetBonus(it)`: не объект/массив → throw «set_bonus — объект
  {2, 3, 4}»; Object.keys.length === 0 → throw «set_bonus — непустой
  объект»; ключ ∉ {'2','3','4'} → throw «set_bonus — порог N вне {2,3,4}»;
  значение-массив: пустой → throw; иначе каждый элемент —
  `validateAffixEntry(it, a, 'set_bonus.' + t + '[' + i + ']')`;
  значение-объект: пустой → throw; ключи только armor|damage; armor —
  finite ≥ 0; damage — finite ≥ 1 (JS — НИЖНИЕ границы, верхние — в схеме
  — паттерн stats :210-213); иное (число/строка) → throw «set_bonus.N —
  массив (affixes) или объект {armor?, damage?}».
* Рефактор: ядро `validateAffixEntry(it, a, label)` вынесено из
  validateAffixes (label 'affixes[' + i + ']' → сообщения ПОБАЙТОВО те же:
  «… — объект» / «.skill — id навыка» / «.amount — число» / «.spell — id
  заклинания» / «.type — skill|free_cast»); validateAffixes = array/
  non-empty-проверки + цикл по ядру.
* Пустой стат-объект {} — throw (R-D3): в схеме НЕ выразить minProperties
  (нет в ALLOWED_SCHEMA_KEYS) → anyOf-трюк на уровне схемы + JS-гард
  (D4-прецедент: форма — валидатор, схема — node-щит).

### 2.3 activeSets(character) — НОВЫЙ чистый агрегатор (items.js)

* Сигнатура/возврат (рабочий контракт, единая точка слияния):
  `activeSets(c) → { counts: {<setId>: n}, skills: {<skillId>: Σ amount},
  freeCast: Set(<spellId>), armor: n, damage: n }`.
* ЧИСТАЯ: raw `c.equipment` (объект? иначе → пустой результат
  {counts:{}, skills:{}, freeCast:∅, armor:0, damage:0}), БЕЗ
  ensureEquipment (D-03 .03 — НЕ копировать из equipmentStats :1164).
* Итерация ТОЛЬКО EQUIP_PHYS_SLOTS (18; зеркальные ключи weapon/armor —
  алиасы .02 — НЕ итерировать, двойной подсчёт). Guards: id falsy → skip;
  getItem(id) null (ghost) → skip; `typeof it.set === 'string' && it.set`
  (иначе skip).
* Счёт: counts[set]++ — каждый надетый предмет = 1; кольцо = 1 (каждое из
  8 ring-слотов — свой предмет, TZ). counts содержит наборы с count ≥ 1
  (даже без активных порогов — прогресс N/4 для .07).
* Данные набора — **REPRESENTATIVE per-порог (D-03 здесь)**: для порога t
  значение берётся у ПЕРВОГО (по порядку EQUIP_PHYS_SLOTS) надетого
  предмета набора, у которого определён `set_bonus[String(t)]`. Детер-
  минизм: порядок слотов фиксирован; Object.keys — insertion order; id
  набора ^[a-z][a-z0-9_]*$ — не целочисленный → порядок стабилен.
  Обоснование: контентные волны пишут ОДИНАКОВЫЙ set_bonus во ВСЕ файлы
  набора (контракт §5.3) — суммирование по предметам дало бы ×count-
  переучёт (4 предмета с одной таблицей = ×4). Representative: бонус
  порога — РОВНО ОДИН раз на набор.
* Пороги SET_BONUS_THRESHOLDS = [2,3,4] КАНОНИЧЕСКИМ порядком; каждый
  активен независимо при counts[set] ≥ t; Кумулятивно (4 надето → активны
  2+3+4 — пин ТЗ). Массив-значение → mergeAffix-слияние в skills/freeCast;
  объект-значение → armor += v.armor / damage += v.damage (finite-guards).
* RUNTIME — БЕЗ throw (defensive skip): валидность каталога — validateItem
  при загрузке; сейвы/гости не роняют игру (паттерн .03).
* ЭКСПОРТ UMD: `SET_BONUS_THRESHOLDS` (рядом с константами .01, ~:1505) +
  `activeSets` (после equipmentAffixes, ~:1520). .07-тултипам — counts +
  пороги + каталожная таблица item.set_bonus.

## 3. Решения (зафиксировано на станции Проектирование)

* **D-01** Канон: `set_bonus` КОНЦОМ properties schema.json (ПОСЛЕ
  `affixes`) + KEYS += 'set_bonus' концом. — Почему: закоммиченный в
  master контракт .01 §4 предписывает дословно «set_bonus КОНЦОМ (ПОСЛЕ
  affixes — то есть новый конец), KEYS += 'set_bonus' (концом)»; a2-arch
  («между set и affixes») — ОТКЛОНЁНО как расхождение с закоммиченным
  контрактом (источник правды — коммит, а не черновик анализа).
* **D-02** Точка попадания стат-формата: armor — БЕЗУСЛОВНО в сумму брони
  equipmentStats; damage — ТОЛЬКО в оружейную ветку (right_hand предмет С
  stats.damage): «damage — в урон оружия» (ТЗ п.1). — Почему: без гейта
  set-damage без оружия создал бы «фантомное оружие» (combat.js:1425
  `eq.damage > 0` → оружие-ветка с subtype null, hitBonus 0 вместо
  кулачной формулы base = 3 + floor(str·0.8) + floor(lvl·0.5)) — тихий
  регресс unarmed-пути; с гейтом — бит-в-бит (M6-паттерн «ghost — вклад
  0»). Отсюда combat.js 0-diff УСТОЙЧИВО (обоснование ТЗ «если анализ
  покажет иную точку» — точка НАЙДЕНА).
* **D-03** Representative per-порог: данные набора читаются у ПЕРВОГО
  надетого предмета набора по порядку слотов, у которого определён
  set_bonus[t]. Контракт КОНТЕНТА: ВСЕ предметы набора декларируют
  ОДИНАКОВЫЙ set_bonus — контролируется ТЕСТОМ SB13 (E22-паттерн), в
  валидатор НЕ закладывается (ТЗ не требует; кросс-предметная проверка —
  не формат-валидация). — Почему: анти-×count-переучёт (главный
  семантический риск, a1 §5.1); детерминизм — фиксированный порядок.
* **D-04** Возврат activeSets = {counts, skills, freeCast, armor, damage}
  (слитый агрегат + counts), ЧИСТАЯ, EQUIP_PHYS_SLOTS only, без
  ensureEquipment; пороги [2,3,4] каноническим порядком, каждый
  независимо, кумулятивно. — Почему: ОДНА точка слияния (дублирование
  merge-логики в потребителях НЕТ — per-элемент-слияние вынесено в
  общий `mergeAffix(a, skills, freeCast)`, используют и item-affixes-
  цикл, и set-бонусы); .07-тултипам — counts (N/4) + пороги (активные —
  вычисляются из counts + каталожной таблицы item.set_bonus — один
  источник истины: каталог, прецедент .03 §5 «тултип предмета — читать
  поле напрямую»); a1-форма {setId: {count, bonuses:[raw]}} — ОТКЛОНЕНА
  (потребители дублировали бы слияние raw-значений); a3-минимализм
  {setId: [порогов]} — ОТКЛОНЕН (потребителям пришлось бы повторно
  вычислять representative-таблицу).
* **D-05** equipmentAffixes — форма возврата НЕ меняется {skills,
  freeCast}; set-статы НЕ раскрываются в её возврате — equipmentStats
  вызывает activeSets(c) напрямую. — Почему: закоммиченный контракт .03

  меньше» (инвариант); .03-контракт в master остаётся истинным без

* **D-06** Валидация двухуровневая: load-time throw (JS: equipment-only,
