### 2.3 Механика, на которую опираются рецепты (сверено с кодом)

* `allyUnequip(hero, sheet, slot)` → `G.unequip(allyView(hero, sheet),
  slot)` (items.js:1274-1293): eq[slot] → null → `addItem` → отказ →
  failsafe (eq[slot] и бонус ВЕРНУТЫ, syncEquipmentMirrors, reason
  пробрасывается). `removeItem(c, id, qty)` → `{ok:true}` (L772).
* `ensureEquipment` (items.js:441-453) на сыром 2-ключевом
  equipment-объекте: ДОПОЛНЯЕТ отсутствующие физ. слоты null + зеркала
  weapon/armor — поэтому после первого успешного unequip ассерт
  `e.sheet.equipment.torso === null` валиден (ключ существует).
* `checkAdd` (items.js:645-664): non-stackable — слотовый check
  ПЕРВЫМ; вес: `inventoryWeight + w*qty > maxCarryWeight + 1e-9`;
  `maxCarryWeight = 30 · P.derived(c).carryWeightMult` (fresh hero —
  mult 1, лимит 30).
* Таверна-рендер строк «Отряда» (ui.js:1089-1107) читает ТОЛЬКО
  плоские level/loyalty + каталог (имя/жалованье) — sheet-запись
  рендерится без проблем (прецедент U8: найм создаёт sheet-запись,
  строка рендерится). Филтр кандидатов (U3): NPC из roster НЕ в
  списке до dismiss — U11 ассерт «кандидат вернулся» — ПОСЛЕ клика.
* Squad-рендер (ui.js:1561+) — rosterSummary (только плоские поля) +
  efirData; `character` в render НЕ читается (только в click-ветке
  L1506) — setCharacter до init безопасен.
