## 2. Решения (open questions + расхождения а1/а2/а3) — каждый с «почему»

**D1. Вариант A (lastCanvasW/lastH, сравнение в frame), сентинел −1.**
Почему A: ResizeObserver отсутствует во всех ~75 vm-харнесах (нужен
stub+guard, fallback = тот же A; асинхронный fire ломает кадр-детерминизм
тестов); прецедент уже в репо — src/dungeon-ui.js step() L1236-1238
(тот же паттерн «если размер ≠ целевого — присвоить»); ТЗ: «при
отсутствии веского довода за B брать A». Почему сентинел −1 (а не
инициализация из canvas.width, как в a1, и НЕ из window.innerWidth —
запрет a3): первый кадр ВСЕГДА делает ровно один ресайз в ЛЮБОМ
окружении (в браузере canvas по умолчанию 300×150, в vm-моках 0 — оба ≠
окну; −1 не равен ни одному реальному размеру битмапа) → детерминистичный
контракт «кадр 1 = 1 присвоение», который пинует RZ-1.

**D2. Gated-блок в той же позиции (после updateCamera, до
viewport/clear), оба слоя в одном блоке.** Почему: сохраняет
000276 «resize ДО buildFrame» (miss-логика frame-tiles-кэша на
resize-кадре интактна) и 000033 (слои синхронны; spriteCanvas-ресайз,
висевший после drawArrays L4119-4121, переезжает — безопасен: drawSprites
читает spriteCanvas.width/height в начале себя L3631, все 2D-состояния
задаёт сам — §3 GL/2D-аудит).

**D3. GL-явность: useProgram + enableVertexAttribArray×2 — БЕЗУСЛОВНО
каждый кадр** (после gate, до viewport). Почему «в кадре», а не «после
известных сбросов»: 3 дешёвых driver-вызова без аллокаций покрывают
любую семантику сброса (включая catch-reset 000170 и неизвестные
будущие); трекер «был ли сброс» — больше кода и краёв без выигрыша.
Инициализация L189/L194-195 остаётся (минимальный диф). Остальное
viewport/clearColor/clear/uniform/bindBuffer/bufferData/
vertexAttribPointer — уже безусловны каждый кадр, НЕ ТРОГАТЬ (§3).

**D4. Сброс в catch — явные `window.innerWidth/innerHeight`** (a2/a3),
не `canvas.width = canvas.width` (a1). Почему: намерение явно
«вернуть слои на ТЕКУЩИЙ размер окна»; краевой случай (окно изменилось
между кадрами + исключение ДО gated-блока, напр. в tryMove) сходится за
один догоняющий ресайз следующего кадра (lastW/lastH устарели → gate
сработает) — корректно, редкость; common-кейс (размер не менялся):
catch ставит тот же размер → трекер не сбивается, следующий кадр: 0
присвоений. lastCanvasW/H в catch НЕ обновляем (значения те же —
инвариант «lastW/lastH = окно, на которое канвасы имеют размер» не
ломается; в краевом кейсе он и так сломан до catch).

**D5. Хелпер resetCanvasLayers() НЕ создаётся** (a2 помечал опционным).
Почему: места различаются по сути (gate ещё пишет lastW/lastH; catch —
нет), каждое ≤4 строк; новый closure в IIFE ради 2×2 строк — больше
индирекции, чем экономии (минимальный диф — стиль репо).

## 1.1 НАХОДКА (a1 §1): латентный баг — WebGL-фолбэк-слой в реальном
браузере НИЧЕГО не рисовал

Цепочка на мастере (все строки 5c0b88a; механизм — ревью-правка
2026-11-03, исходная версия ошибочно утверждала «пересет КАЖДЫЙ кадр»):
1. L4100-4101 каждый кадр присваивает canvas.width/height = окно.
   Реальный пересет (HTML-спека: присвоение width при СМЕНЕ размера =
   пересоздание backing store + сброс состояния WebGL-контекста к
   начальным: current program → null, vertex attrib arrays → disabled,
   viewport → 0,0,1,1, clearColor → 0,0,0,1, bound buffer → null,
   per-program uniform'ы → 0) происходит при смене размера;
   same-size-присвоение в браузерах — no-op (движки — ранний return
   без reallocation). Реальных пересетов на мастере ровно ОДИН —
   1-й кадр (canvas в index.html без width/height — дефолт 300×150 →
   окно) + один на каждую реальную смену окна; «60 раз/сек» в
   steady state — мнимая перфоманс-мотивация (gated-ресайз всё равно
   корректен и чище).
2. Код 1-го кадра восстанавливает: viewport (L4102), clearColor/clear
   (L4103-4104), bindBuffer/bufferData/vertexAttribPointer (buildFrame
   L3611-3614), uniform (L4108-4111) — НО НЕ `gl.useProgram(program)`
   (init-only L189) и НЕ `enableVertexAttribArray` (init-only L194-195).
   Дальше пересетов нет (same-size — no-op) → program/attrib'ы НЕ
   восстанавливаются НИКОГДА.
3. `gl.drawArrays` L4116 без bound program (и/или с disabled
   attrib'ами) — тихий no-op (WebGL-спека: не error, не пиксели)
   каждый кадр.
4. Итог: #game-канвас в браузере = только clearColor (0.06,0.08,0.10).
   Фолбэк-сцена 000011/000176 (цветные тайлы/ромб Флогистона/маркеры в
   окне загрузки ~299 ассетов; legacy-фигуры при упавших спрайтах)
   никогда не рендерилась; весь реальный визуал несёт 2D-слой #sprites.
5. vm-тесты не видят (моковый gl — noop'ы, canvas-моки не симулируют
   сброс): tests/global-map-draw.test.js RM-4/RM-8 и др. — зелёные.

Последствие фикса: фолбэк-слой начнёт рендериться ВПЕРВЫЕ в реальном
браузере (окно загрузки + упавшие спрайты). В штатном steady state
(все ассеты ready) визуал НЕ меняется: XOR-гейт 000176 → 0 вершин
(пины RM-3/RM-10) — слой пуст, как и «был» (clearColor). Риски
двойной отрисовки прикрыты XOR-контрактом 000176 + пины RM-1..RM-9.

Следствие для error-path семантики (зафиксировать в отчёте): ЛЮБОЕ
исключение в кадре → catch (пересет + ЯВНОЕ очищение обоих слоёв:
gl.clear + s2.clearRect — ревью-правка 2026-11-03; гарантия НЕ
зависит от семантики same-size-присвоения, где тот же пересет в
браузерах может быть no-op без reallocation) ДО возврата rAF-коллбека →
браузер композитит ПОСЛЕ коллбека → **ошибочный кадр презентует в
худшем случае пустой кадр (clearColor), никогда — частичную сцену**.
На мастере поздний exception (после отрисовки, напр. в renderHud)
презентовал полностью отрисованную сцену ошибочного кадра; после
фикса тот же сценарий — пустой кадр. Это ЦЕЛЕВАЯ семантика ТЗ п.2
(«частичный кадр не просачивает»); персистентная ошибка = каждый кадр
пустой (цикл жив, logged once) — деградация, не крах.

## 2. Контракты и границы

**К1 (resize).** canvas (#game) и spriteCanvas (#sprites) ресайзятся
ТОЛЬКО при `window.innerWidth/innerHeight !== lastCanvasW/lastCanvasH`;
первый кадр — ВСЕГДА (сентинел −1). Инвариант: lastCanvasW/H = окно,
на которое канвасы имеют размер; обновление — только в gate. Значения
canvas.width/height на каждом кадре = окно (как на мастере) → все
существующие drawCalls/HUD/golden-пины бит-в-бит (a3 §3.3: ни один
существующий тест не читает размеры и не считает присвоений).

**К2 (GL-явность).** Состояние, от которого зависит drawArrays,
декларируется КАЖДЫМ кадром явным: useProgram, enableVertexAttribArray
(aPos, aColor) — новые; viewport/clearColor/clear/uniformMatrix4fv/
bindBuffer/bufferData/vertexAttribPointer — уже были. Рендер не зависит
от семантики сброса GL-состояния при пересете (сбросит браузер или нет
— безразлично). Init L189/L194-195/L199 остаётся.

**К3 (само-исцеление 000170, НОВЫЙ механизм).** Слабый слой (безусловен,
был всегда): per-frame gl.clear (L4104) + s2.clearRect (L3632) —
частичный кадр живёт ≤1 презентованного кадра. Сильный слой (новый,
error-путь; детерминирован — ревью-правка 2026-11-03): catch frame()
пересетает ОБА слоя И ЯВНО очищает их (gl.useProgram/ea×2/viewport/
clearColor/gl.clear + s2.clearRect) — частичная сцена гасится 100% в
любом браузере, НЕ опираясь на reallocation (в браузерах same-size-
присвоение — no-op: без reallocation буфер НЕ чистится) — частичный
кадр НЕ презентуется (§1.1, последнее следствие). Watchdog-контракт
000170 НЕ тронут: try/catch/finally, reschedule в finally ВСЕГДА,
console.error logged once, keys.clear() в catch НЕТ.
