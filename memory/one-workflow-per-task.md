# Одна задача — отдельный workflow (решение, 2026-10-02)

Правило пользователя: «запускай много задач, но каждая в своём workflow».
CLAUDE.md: «Запустить workflow в отдельном git worktree для каждой задачи
из выбранных» — юнит параллелизма = ЗАДАЧА, не «волна из N задач».

* Запуск: `Workflow({scriptPath: <скрипт thegame-task-wave>, args: {tasks: [однаЗадача]}})`.
  Скрипт понимает и `{lanes: [[...]]}`, и `{tasks: [...]}` — для одной задачи
  это один lane.
* Целевой параллелизм на машине (12 CPU): 6–12 одновременных task-workflow.
  npm test тяжёлый (~45–90 с), merge-очередь сериализована `.merge-pending`
  (~2–4 мин на мерж, потолок ожидания агента — 45 мин).
* Проверка старта партии: в journal.jsonl run'а должны быть строки
  `"type":"started"`. Если только одна строка `"launched"` — args не дошли
  (см. баг ниже), запускать заново.

## Подводный камень: большие args Workflow

Опыт 2026-10-01/02: 4 провала мульти-лейн запусков со большими args
(~11–20KB JSON, с `<`/`>` и кириллицей) vs 0 провалов малых args (~1–2KB).
Большие args нестабильно доходят в скрипт как JSON-строка (с HTML-экранированием
`&lt;`/`&gt;`) — `args.lanes` оказывается undefined, lanes теряются.

Меры: (1) guard в скрипте — `JSON.parse` при строковых args + явный throw
«args: пустые lanes/tasks»; (2) в текстах задач не использовать литеральные
ASCII `<`/`>` («ниже», «больше», «не выше»); (3) главное — одна задача на
Workflow, маленькие args всегда доходят.

Связано: test-runner-worktrees.md (тесты мерить внутри worktree),
main-js-split-plan.md.

## Подводный камень: worktree — общее состояние для всех станций workflow (000204, 2026-10-14)

Станции ОДНОГО workflow работают в ОДНОМ worktree задачи. Станция
проверки красной фазы делает `git checkout <RED-коммит задачи>`
ПРЯМО в этом worktree (рефлог 000204: «checkout: moving from
task/000204 to b4fc922» и обратно; окно ~1,5 мин, в котором
ревьюер зафиксировал staged-откат src/combat-ui.js +
tests/combat-ui.test.js к RED-состоянию b4fc922, мtime 01:46:56).
Дерево восстанавливает сам сородич, но другая станция (особенно
мерж) НЕ должна полагаться на это: squash (reset --soft + commit по
состоянию index/working tree, one-commit-per-task-squash) в таком
окне уедет на master ЧУЖОЕ состояние (для 000204 — старый рендер
при красных CU204-тестах, функциональность задачи тихо потеряна).

ПРОТОКОЛ мерж-станции (major-файдинг ревью 000204), выполняется
после КАЖДОГО чужого касания worktree, а не один раз:
1. `git status --porcelain` — пусто + `git diff HEAD --exit-code` — 0.
2. При расхождении — `git reset --hard <ветка задачи>`; HEAD при
   этом должен быть проверен (построчный diff + зелёный полный
   набор с чистого дерева).
3. Перед `reset --soft + commit` — полный `node --test tests/` с
   чистого дерева + точечные grep-пины реализации (у 000204:
   `grep '6px ui-monospace' src/combat-ui.js` → 2 строки L1138/
   L1192).
