## 1. Почему путь (б) экранный bake, а не (а) маска в мире/клетках

- **(а) offscreen-маска в мировых координатах (текстура по сетке)** — ОТВЕРГНУТ:
  маска размера ВСЕГО подземелья при зуме — 63×63 клеток × 115.2 px ≈ 7258 px
  на сторону ≈ 52.7 Мп RGBA ≈ 210 МБ; при bbox «только explored+margin»
  1920×1080-окно уже ≈ 8.3 МБ, но bbox-подход всё равно требует ЗАГРУЗКИ
  клеток (тех же N-операций) и отдельного ре-аплоада при движении окна.
  Монотонная загрузка «только explored» (памятка 000263 §3.5 для чанков)
  НЕ применима: окно видимости двигается, клетка выходит из dim переходом
  1→2 (вид→затемнение при уходе из радиуса) — множество dim НЕ монотонно.
- **(б) экранная bake-маска размера ВЬЮПОРТА** — ПРИНЯТ: константная цена
  памяти 1920×1080 RGBA ≈ 8.3 МБ (в тестах вьюпорт 800×600 ≈ 1.9 МБ);
  steady-кадр = 0 пересборок + 1 drawImage; пересборка = тот же цикл
  fillRect по viewport-диапазону, ТОЛЬКО при изменении ключа.

## 2. Доказательство бит-в-битности к прежнему per-cell циклу на main

1. **Эквивалентность blending.** fillRect(FOG_DIM_FILL) по прозрачному bake
   пишет в каждый пиксель premultiplied(0.65·RGB, 0.65); drawImage(bake, 0, 0)
   с ЦЕЛЫМ нулевым смещением 1:1 и source-over на main применяет ровно тот же
   source-over blend к сцене. Для НЕпересекающихся клеток (снап-случай — см. 3)
   это тождественно одному fillRect на main. Для пересекающихся (fallback-ветка
   `cellRect`, где snappedTileRect не дал общих краёв) — тоже: source-over с
   КОНСТАНТНОЙ краской ассоциативен и коммутативен по покрытию — последовательность
   «два fillRect на main» и «два fillRect в bake + один blit» дают
   побитово равный результат (двойная альфа 0.65² воспроизводится одинаково).
2. **Отсутствие швов/двойной альфы на снап-сетке.** snappedTileRect
   (`src/map.js`, `snappedTileEdges`): край = Math.round(viewW/2 + (i − camX)·
   zoom) — КРАЙ СОСЕДНИХ клеток = ОДНО И ТО ЖЕ целое выражение ⇒ ря примыкают
   без пикселя перекрытия ПРИ ЛЮБЫХ дробных zoom/cam (пин TS-12 перенесён
   внутрь bake — сетка dim относительно пола не изменилась).
3. **Ловушка двойного затемнения** живёт ТОЛЬКО в fallback-ветке `cellRect`
   в `src/dungeon-ui.js` (наследие до 000215): bake-путь использует ровно
   тот же `cellRect(x, y, proj(x, y))`, что и удалённый цикл — источник
   правды один, расхождения путей невозможны по построению.
4. **Anti-vacuum целочисленности.** При зажатом clampCam lo/hi
   (`clampCam`: extent·z ≤ viewPx → жёсткий центр extent/2, иначе
   cam ∈ [viewPx/2/z, extent − viewPx/2/z]) произведение cam·zoom == viewPx/2
   ТОЧНО ⇒ сырая проекция целая trivially — дробные зумы для анти-вакуума в
   тестах берутся из коридора 46.296/57.6/66.667/115.2 (не 96).

## 3. Ключ пересборки и корректность инвалидации

```
(d ref, cam.x, cam.y, zoom (|Δ|>1e-6), w, h, pos.x, pos.y, fogR, explored.size)
```
- mask = maskFor(d.w, d.h, pos, R, explored) определяется тройкой (d, pos, R);
  геометрия ряда — (cam, zoom, w, h); `fogR` вынесен в переменную рядом с
  maskFor (иначе радиус кадра не попал бы в ключ).
- **explored.size как версия множества**: мутаторы explored внутри визита —
  только lazy-init, union клеток mask==2 после каждого render(), new Set() в
  start(), null в close(); `.delete`/`.clear` НЕТ ⇒ множество МОНОТОННО ⇒
  равный размер + равные (pos,R) ⇒ равные множества ⇒ равный dim. Это
  единственный дешёвый sound-ключ (полное сравнение множества — O(explored)).
- **Сбросы**: `fogBake = null` в start() и close() — защита протекания маски
  между подземельями даже при вызове start() без close(). Переезд вьюпорта —
  пересоздание по несовпадению w/h (в ключе).

## 4. ЛЕНИВОЕ СОЗДАНИЕ — контракт CC-6

Канвас bake создаётся ТОЛЬКО в ветке `fogDim > 0`. При dim == 0 (первый кадр
визита, explored пуст) — ни `document.createElement`, ни drawImage. Правила:
- НЕ выносить создание канваса из-под `fogDim > 0` — иначе краснеют CC-6
  «16 чанков/блитов» (bake тоже попадает в `createdCanvases` харнесса) и
  все «0 blit на свежем старте» пины (dungeon-ui, wall-autotile).
- Город — вне прохода вовсе (`!isCity` guard сохранён, FOGM-5/TS-11/W-город).

## 5. Сигнатура fog-блита для тестов

`drawImage(bake, 0, 0)` — ТРИ аргумента; ВСЕ спрайт/чанк/marker блиты в
dungeon-ui — ПЯТЬ аргументов ⇒ тесты опознают fog по `c[1].length === 3`
(+ принадлежность источника `createdCanvases`). Bake-канвас в тестах доступен
как `fogBlit[0][1][0]`; его внутренние вызовы записаны тем же Proxy-stub
харнесса
(`drawCalls`), т.е. золотой паритет рядов проверяется без пиксель-симулятора
(в tests/ getImageData нет).
