# 000106: содержимое города — src/cities.js generateCityContents

Дочерняя к 000052 (города и деревни), П2; зависимость 000104
(layout города) — в master. Статус: СТАДИЯ КРАСНЫХ ТЕСТОВ (TDD) —
тесты записаны и красные; реализация — следующая стадия.

## Зафиксированные решения (пины в tests/cities.test.js,
раздел «Содержимое города (задача 000106)»)

* **CITY_CONTENT_CONST = 0x434f4e54** (ASCII «CONT») — НОВАЯ соль:
  не CITY_LAYOUT_CONST (0x4c41594f), не GLOBAL_SEED (0xf10c7a26),
  не CITY_SEED_CONST, не сиды dungeon.js (0xd0d6b5e5, 0x5e11c3a7,
  0x0c9f4b2d, 0x5e11, GLOBAL_SEED^0xabcdef, 0x7777). GOLDEN-ПИН
  (тест: литерал): смена после мержа = смена ВСЕХ городских
  содержимых — НЕДОПУСТИМА (прецеденты CITY_SEED_CONST 000103,
  CITY_LAYOUT_CONST 000104). cities.js не тянет map.js (единственный
  require — ./perlin.js, закреплено grep-тестом 000104), поэтому
  GLOBAL_SEED в соль НЕ смешивается.
* **seed = hash2(cityX, cityY, CITY_CONTENT_CONST) >>> 0** — от
  ПОЗИЦИИ якоря. НЕ totalXp (город статичен — в отличие от
  generateDungeonContents), НЕ террейн. **WEALTH В СИД НЕ
  ВОЙДИТ**: один якорь → один rng-поток на все wealth (тест:
  seed одинаков для wealth 0..3). seed ≠ layout.seed (у layout
  своя соль — тест проверяет отличие).
* **count = мин_постройки + wealth** — без верхнего лимита
  (размещение ограничено местом; формула зафиксирована тестом
  «wealth: length(w0)=4, length(w3)=7» на городе (100,−40)).
* **Активные типы = топ-(1+wealth) ключей доли_типов по
  (доля убыв, id растущ)** (ключи JSON-строки — нормализация
  Number(); доли строго > 0). Зафиксировано тестом:
  * w0: город/столица → ровно {44, 25} (топ-1 — Дом кузнеца 25:
    доля 0.3, у города он же 1-й по (доля,id));
  * деревня w0 → ⊆ {1, 44} (топ-1 — Оружейная 1: доля 0.5,
    id 1 < 44);
  * Арена (7) — ВНЕ ассортимента столицы при ЛЮБОМ wealth (5-й по
    (доля, id): доля 0.15 = у 1, но id 7 > 1; топ-(1+3) = топ-4).
* **Таверна (id 44) — минимум 1, строится ПЕРВОЙ** (count ≥ 1,
  тип без rng-выбора): найм спутников 000065/000078 в городской
  таверне. Задокументированное исключение: ХУТОР (fp1) —
  buildings: [] при ЛЮБОМ wealth (FLOOR только entrance/exit,
  spots пуст; мин_постройки = 0 — противоречие «таверна в каждом
  городе» уже разрешено 000102/000104 нулём минимума).
* **Остальные (count−1)** — взвешенный выбор по долям активных
  типов: 1 rng-вызов, кумулятивная сумма в порядке сортировки.
* **Размещение 1x1 — ВСЕ внутренние постройки**, включая Арены
  (id 7), у которых в каталоге размер 3x3: размер каталога
  внутри города НЕ уважается (решение: держать scope —
  прямоугольное размещение + достижимость резко усложнили бы
  задачу; довести до 000105/000107/000110). Только FLOOR,
  НИЧЕГО на entrance/exit. Паттерн takeSpot (src/dungeon.js):
  spots = FLOOR-клетки минус entrance/exit, стабильный порядок
  y→x, считаются ОДИН раз; occupied-Set; ≤200 случайных попыток
  из rng. **КАЖДАЯ попытка проверяется 4-направленным BFS от
  entrance** (своя копия логики reachableFrom, src/dungeon.js —
  require dungeon.js невозможен; 8-направление было бы ошибкой):
  занятые клетки (occupied ∪ {кандидат}) = стены; если какой-то
  FLOOR (включая exit) недостижим — отклонение. После 200 провалов
  — детерминированный линейный скан y→x первой валидной свободной
  клетки (БЕЗ rng). Валидных мест нет — GRACEFUL-стоп.
* **ДОСТИЖИМОСТЬ — СТРОГИЙ инвариант (функция обеспечивает);
  мин_постройки — best-effort.** Брутфорсом проверено: у деревни
  4x4 layout определяется парой колонн (вход, выход) ∈ {1,2}^2:
  ОДИНАКОВЫЕ колонны → 2 валидные клетки (минимум 2 выполним;
  якорь (−114,−119) — (2,3)/(2,0)); РАЗНЫЕ колонны → 1 валидная
  (максимум 1 < мин 2; классности (1,3)→(2,0) и (2,3)→(1,0),
  ~50% якорей). Приоритет: достижимость > минимум — функция
  останавливается (buildings.length < count — норма), не бросая.
  Тесты: «достижимость (СТРОГОЕ)» по sweep (все 4 типа × wealth)
  + 4 классности деревни; «минимум» — ≥ мин для города/столицы
  ВСЕГДА (64/144 внутренних клетки — достаточно), деревня — ≥ 1
  (таверна всегда помещается: в каждой из 4 классностей есть
  валидное место) и ровно 2 у (−114,−119).
* **Порядок вызовов rng = GOLDEN-ПИН**: rng = mulberry32(seed);
  таверна: место (≤200 rng); затем постройками: тип (1 rng) →
  место (≤200 rng); fallback-скан — без rng. Любое изменение
  порядка (сначала все типы, другое число попыток, иной порядок
  обхода) сменит ВСЕ города — недопустимо после мержа.
* **Хутор (fp1)**: 2x2, FLOOR только entrance/exit → buildings: []
  при любом wealth (тест зафиксирован для обоих якорей 000103).
* **cityRecord — source of truth (000053)**: pool и квоты только
  из особых_параметры (мин_постройки, доли_типов); код НЕ
  хардкодит диапазоны id — текст задачи устарел (7/8 —
  школы_навыков, 25 — дом_npc, 44 — прочее; реальный пул = КЛЮЧИ
  долей {1, 7, 10, 25, 44}). cities.js не может тянуть каталог
  (buildings.js/map.js/dungeon.js) — cityRecord приходит
  аргументом от вызывающего (000105: buildings.js getBuilding(id)).
  Ссылочная целостность (id ∈ каталогу, категория ≠ «город») —
  только тестом (fs-чтение JSON).
* **Валидация — throw 'cities.js: …'**: wealth — целое 0..3
  (−1/4/1.5/'2'/null/NaN/true → throw); cityRecord: особые_
  параметры / мин_постройки (целое ≥ 0) / доли_типов (непустой
  объект, числовые ключи, числовые доли > 0); layout:
  width/height/cells/entrance/exit.
* **Результат — plain**: {buildings: [{x, y, buildingId}], seed} —
  ровно эти поля, без Set/Map (JSON.parse(JSON.stringify(res))
  deepEqual res — тест; 000109 сериализует в сейв).
* **layout НЕ мутируется** (000105 кеширует layout и
  переиспользует, как dungeonMemory): реализация ведёт свою копию
  cells / occupied-Set (тест «layout НЕ мутируется»).
* **«Доли в пределах допуска»** — только через БОЛЬШОЙ
  детерминированный сэмпл (196 якорей столицы w3): эмпирическая
  частота каждого активного типа в ±0.15 (абсолютно) от
  нормализованной доли. Принудительная таверна-первая даёт
  смещение 44 на +11 п.п. (196/1764) — в допуске. На малых
  выборках (4–9 построек) проверка долей флейкает — не делать.
* **wealth-эффект** — только через формулу (count/активные
  типы): тест (якорь, w0) ≠ (якорь, w3) привязан к ГОРОДУ
  (100,−40) (запас места; у деревни w0 и w3 могут совпасть —
  feasibility-cap, у хутора всегда равны).

## API (src/cities.js — ДОБАВЛЕНИЕ, не перестройка)

* generateCityContents(layout, cityX, cityY, cityRecord, wealth) —
  ровно 5 параметров (Function.length === 5, без default).

  (расширяемый: 000105 городские тайлы, 000107 взаимодействие,
  000108 стоки, 000109 сейв допишут).
