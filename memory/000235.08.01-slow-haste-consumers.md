### 0.1 «ход_вниз» (дебаф МОБА: slow 000057 {ход_вниз, 0.15, 3};
зона ice_field 000050 {object:зона, ход_вниз, 0.15, 3, radius:2})
— ВАРИАНТ (b) ТЗ: ШТРАФ К ПОРЯDKУ ОЧЕРЕДИ: замедленный юнит — в
КОНЦЕ очереди ходов на время действия эффекта (пока
debuff.turns > 0 на момент сборки очереди).

Формула (ФИКС): в ключе сортировки buildTurnOrder из РЕАЛЬНОЙ
инициативы юнита вычитать константу модуля
`SLOW_INITIATIVE_PENALTY = 1e9`:
`unitInitiative(c, u) - (unitDebuffValue(c, u, 'ход_вниз') > 0
? SLOW_INITIATIVE_PENALTY : 0)`.

Почему 1e9, а не формулы a1/a3 (конфликт анализиров решён):
* a1 предлагал `Math.round(value×10)` = −2 к инициативе: ОТКЛОНЕНО —
  штраф слабый и относительный (init 7→5 всё выше init 4 —
  «замедленный» не «в конце»), эффект ненаблюдаем во многих
  раскладах; обещанное игроку в описании — «замедление» = в конец.
* a3 предлагал мультипликатор (1−value) (5.95 при init 7) —
  ОТКЛОНЕНО: такой формулы в ТЗ/коде НЕТ, это была лишь догадка
  а3 при калибровке фикстуры; кандидатная фикстура a3
  (wind_elemental 7×0.85=5.95 < orc_rider 6) НЕГДЕ НЕ ИСПОЛЬЗУЕТСЯ —
  SLOW-1 калибруется к «в конец очереди» (§3, T1).
* 1e9 гарантирует «в конец» при любых инициативах (dex+int — малые
  целые); вычитание из РЕАЛЬНОЙ инициативы (НЕ замена ключа на −1e9
  обоим) сохраняет относительный порядок между несколькими
  замедленными юнитами (компаратор `b[1]−a[1]` по конечным ключам —
  NaN-free), тай-брейк = стабильная база ['player',...союзники,
  ...мобы] 000167; без дебафа — вычитание 0 — БИТ-В-БИТ legacy.
* value 0.15 НЕ масштабирует эффект: бинарный признак (turns > 0),
  величина — в turns; все текущие носители имеют value 0.15.
* Штраф СТРУКТУРНО МОБОВЫЙ: unitDebuffValue читает u.debuff; у
  игрока u.debuff отсутствует (c.player.debuff — undefined → 0),
  союзники дебафы не получают (роутинг spells.js: «дебаф» →
  TARGETED моб; зона с дебаф-статом → side 'mob' только). Гварды
  не нужны.
* Новая функциональность заработает у ВСЕХ носителей «ход_вниз»
  каталога (сейчас: только slow 000057 и ice_field 000050).

### 0.2 «ход» (баф: blazing_speed 000029 {ход,1,3} — само-баф
кастера/игрока c.ps.buff; winter_haste 000055 {ход,1,3} — союзник
u.buff (каст без targetId — тоже на себя); swift_prayer 000103 и
nature_haste 000156 {ход,1,3} — PARTY_BUFF_IDS, оба пути
c.ps.buff + u.buff каждого союзника) — ВАРИАНТ (a) ТЗ: юнит
ДЕЙСТВУЕТ ДВАЖДЫ В РАУНД = +value слотов действия «Удар» в раунд
на время действия эффекта.

Формулы (ФИКС):
* игрок — refillPools (src/combat.js): `c.ps.attack =
  d.attackActions + unitBuffValue(c, c.player, 'ход')`;
* союзник — startRound, ally-цикл: `a.attackLeft = 1 +
  unitBuffValue(c, a, 'ход')`.
* Оба чтения — ПРЕ-ДЕКРЕМЕНТ (рефилл идёт ДО тика бафа в
  startRound; паттерн «реген» 000267).
* makeAlly (:367, attackLeft: 1) — НЕ ТРОГАТЬСЯ (баф кастится
  только в бою; round 1 пул без баффа — бит-в-бит).
* Движение НЕ усиливается: c.ps.moveLeft / a.moveLeft / moveCells
  — без изменений (прецедент attackActions: sheet.js:493
  `1 + Math.floor(P.strength / 10)` — сила даёт только ДЕЙСТВИЯ,
  moveCells — отдельная формула; 000257-пул шагов — домен не
  тронут). «Дважды в раунд» = 2 действия «Удар» за раунд (одно
  действие = один слот «Удар»), а НЕ 2 полных хода.

Почему атака-пул, а не дублирование слота очереди (конфликт
a1/a2 решён): a1 предлагал дублировать id юнита в turnOrder
(2 слота в очереди). ОТКЛОНЕНО: (1) меняет ДЛИНУ очереди во
всех haste-сценариях → ломают queue-пины 000167-ORDER/ROUND/
WEAK, 000168 и фиксированные endTurn-драйверы (W-12a.1, W-04b) +
UI-рендер очереди; (2) атака-пул — 2 однострочные правки без
касания очереди/advanceQueue/combat-ui; (3) а2 (архитектура —
финальная станция до Проектирования) зафиксировала атака-пуль,
заголовок задачи — «двойное действие в раунд». СЛЕДСТВИЕ:
технические правки W-12a.1/W-04b, предписанные a3 (§5.1/5.2),
НЕ ТРЕБУЮТСЯ — их драйверы (4 endTurn = раунд: игрок + 3
союзника; слот моба самодиспатчится в advanceQueue через mobAct
БЕЗ endTurn) остаются верны, т.к. длина очереди не меняется
(проверено по коду advanceQueue :3133-3174).

### 0.3 Окна действия (принужд. следствие существующего ритма
тиков 000235.01 + контракта 000167 «очередь — на старт раунда»;
зафиксировано пином SLOW-1 раунд 4 + spec-строкой)

* «ход» — ровно `turns` раундов, начиная со СЛЕДУЮЩЕГО за кастом:
  каст в раунде R (turns 3) → бонус в R+1..R+3; раунд каста пул
  уже рефиллен (refillPools в начале startRound ДО каста) — бонуса
  нет. Контракт 000235.01 «ровно N раундов, включая каст» — про
  ТИК (запись живёт, тикает), бонус — от пре-декрементного чтения
  при рефилле.
* «ход_вниз» — ровно `turns − 1` очередей: каст в раунде R →
  штраф в очередях R+1..R+turns−1 (turns 3 → R+1, R+2). Тик
  дебафа моба — в начале startRound (:3009-3015), buildTurnOrder —
  в КОНЦЕ startRound (:3097) → чтение ПОСТ-ТИК; очередь раунда
  каста собрана ДО каста (frozen, инвариант 000036) — штрафа нет.
  R+3: тик 1→0 → очередь legacy.
* АСИММЕТРИЯ окон (turns раундов vs turns−1 очередей) —
  зафиксирована как контракт (spec-строки + пин SLOW-1); обе —
  принужд. следствия, НЕ отклонения.
* Альтернатива «переставить buildTurnOrder ДО тиков» (дала бы
  полные `turns` очередей) ОТКЛОНЕНА: ломает порядок
  рассеивания призывных (ally-цикл :3035-3044 идёт раньше
  buildTurnOrder — призывной, рассыпающийся в раунде, сейчас НЕ
  входит в его очередь) и legacy-бит-в-бит; прецедент
  000167-WEAK-1 (memory/000167-initiative-core.md §14 —
  «принужд. следствие» пинится, а не «чинится»).
