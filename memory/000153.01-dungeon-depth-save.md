## 2. Контракты и границы

### 2.1 d.depth и сид формы
* depth — целое ≥ 1, ПЕРВЫЙ ЭТАЖ = 1 (контракт 000153 §3 Q1). Каноническое
  имя шкалы — **«глубина»** (000157: «растёт с глубиной (000153)»).
* depth=1: `seed = dungeonShapeSeed(x, y, pixels)` — БИТ-В-БИТ. Функция
  dungeonShapeSeed вызывается ровно ОДИН раз (число вызовов не меняется):
  ```js
  const baseSeed = dungeonShapeSeed(x, y, pixels);
  const seed = depth === 1 ? baseSeed : dungeonDepthSeed(baseSeed, depth);
  ```
  Новая формула существует ТОЛЬКО в ветке depth>1 → depth=1 не зависит от
  неё ни по коду, ни по значению.
* depth>1: `dungeonDepthSeed(baseSeed, depth) = (hash2(baseSeed, depth,
  0xd337b153) ^ ((depth * 0x9e3779b9) >>> 0)) >>> 0` — детерминированная
  функция от (сид формы depth=1, depth, соль), БЕЗ rng (hash2 — чистый
  murmur3-finalizer, perlin.js:110-116). 0x9e3779b9 — штатная константа
  кодовой базы (mapseed.js:38, perlin.js:111, map.js:613, sprites.js:671);
  соль 0xd337b153 — новая, без коллизий с существующими (0xd0d6b5e5, 0x5e11,
  0x7777, 0x5e11c3a7, 0x0c9f4b2d).
* **Заранее вычисленные золотые значения** (node-прогон реальным hash2,
  пиксели PX = syntheticPixels(8,8,128,128,128,255) как в
  dungeon.test.js:7-12):
  * CAVE (37,−12): base = 2658571374 (существующий golden) → depth2 =
    **3912048804**, depth3 = 4212266649, depth10 = 1597152373.
  * ABYSS (11,3): base = 2941640529 (существующий golden) → depth2 =
    792410970.
  * Все ≠ base, попарно различны, consecutive depths 2..12 различны —
    проверено эмпирически. Стринг cells для depth2 — зафиксировать на красной
    стадии (первый зелёный прогон).
* Сид содержимого — БЕЗ ИЗМЕНЕНИЙ (generateDungeonContents :377):
  `(hash2(player.totalXp, d.seed, 0x5e11) ^ (player.totalXp * 2654435761))
  >>> 0` — глубина наследуется пер-глубину через d.seed → ТЗ п.6
  «координаты + глубина» выполняется и для формы, и для контента.

### 2.2 Ключ dungeonMemory
* Формат: `worldKey + ':' + depth` → `'18,14:1'`. Разделитель `:` —
  прецедент buildingOncePerDay 'x,y:effectId' (main.js); чистый парсинг
  `split(':')`.
* Единый источник: dungeon.js (`dungeonMemoryKey`, `DUNGEON_MEMORY_KEY_RE =
  /^-?\d+,-?\d+:\d+$/`). Точки использования: locations.js maybeEnterDungeon
  (get) и exitDungeon (set) — через lazyGame'ов `G.dungeonMemoryKey` с
  инлайн-fallback `worldKey + ':' + depth` (без re-implementation хэша —
  LOC-2); main.js — только сборка key в activeDungeonMemoryRec (key'ы Map
  в main.js НИКОГДА не парсятся — restore ре-валидирует через regex).
* Контент этажа N не перетекает на N+1 (ключ разный). contentValid
  (dungeon.js:477-479) — как есть, per-этаж: `currentDay <= lastVisitDay +
  memoryDays` (окно day−last ≤ memoryDays — валидно; last > day — не
  валидно). СЕМАНТИКА ОКНА: валидно когда `day − last ≤ memoryDays` (и
  last ≤ day) — НЕ путать с cities.js (там day−last ≥ respawnDays → null;
  другое сравнение — respawn vs память).

### 2.3 Новый топ-раздел сейва `dungeonMemory`
* ОДИН раздел (контракт 000153 §6.3: параллельных НЕТ). Имя —
  **dungeonMemory** (1:1 с runtime-Map, самодостаточное).
* Формат: map ключа `'x,y:depth'` → `{ contents: <JSON результата
  generateDungeonContents>, lastVisitDay: int ≥ 1, pos?: {x: int, y: int} }`.
  MULTIPLE records (по одному на посещённый этаж-вход) — не одна запись:
  ТЗ «ОБРЕЗКА записей» (мн. ч.); 1:1 с runtime-Map; per-этажный фикс
  re-loot остаётся закрытым и после .03 (мульти-этажность).
* contents — глубокое валидируемое копирование (валидатор возвращает НОВУЮ
  копию — паттерн validateCityState :525-533); после restore mутации live
  contents не касаются объекта сейва.
* Nеломность: пишется ВСЕГДА (даже `{}`); старый сейв без раздела (raw==null)
  → молча пусто (000115: raw==null → пусто, без warn); явно битый раздел
  (non-object: строка/число/массив) → console.warn + пустой Map (000072/
  000109: corrupted → warn + reset); версия НЕ повышается (save.js не
  трогаем; save.test.js:256 пинит CURRENT_VERSION=1/MIGRATIONS={} — проходит
  без правок).
* Обрезка ДВУСТОРОННЯ (прецедент serializeCityStates main.js:726-729 —
  квота localStorage): на serialize (collectSaveData) и на restore —
  отбрасываются записи, где key не по regex, lastVisitDay не int ≥ 1,
  lastVisitDay > day, !contentValid(lastVisitDay, day, memoryDays), contents
  невалиден.
* **Active merge — ОБЯЗАТЕЛЕН**: в collectSaveData передаётся
  activeDungeonMemoryRec() — merge «активный поверх» (перезаписывает свою
  key). Причина: при ПЕРВОМ входе содержимое этажа ещё НЕ в Map (запись
  появляется только в exitDungeon); in-flight сейв без merge = пустой
  раздел = re-loot-эксплойт снова. Рекорд: `{ key, contents: ds.contents,
  lastVisitDay: clock.day, pos: {x: ds.x, y: ds.y} }`; null если нет
  dungeonState или kind !== 'dungeon' (город — не влияет).
* Позиция restore-блока: restoreFromSave, после cities-блока (:1256),
  перед campStocks (:1258) — день восстановлен первым (:837-851);
  try/catch fail-open (паттерн cities-блока).

### 2.4 Re-anchor спавна (восстановление pos)
* Где: locations.js maybeEnterDungeon, ПОСЛЕ makeDungeonState, ПЕРЕД
  return (не main.js — лишних state-переменных в multi-record дизайне не
  нужно; main.js не знает размеров подземелья).
* Логика:
  ```js
  const p = saved && saved.pos;
  if (p && Number.isInteger(p.x) && Number.isInteger(p.y) &&
      p.x >= 0 && p.y >= 0 && p.x < d.width && p.y < d.height &&
      G.CELL_FLOOR !== undefined &&
      d.cells[p.y * d.width + p.x] === G.CELL_FLOOR) {
    ds.x = ds.prevX = p.x; ds.y = ds.prevY = p.y;
    if (ds.mover) ds.mover.teleport(p.x, p.y);
  }
  ```
  (G.CELL_FLOOR — из exports dungeon.js :37/:543; деградационный guard как в
  dungeonMove :316-317; ds.mover.teleport — attachMover :96).
* БЕЗ BFS: FLOOR-клетка достижима по построению (карта выкапывается от
  entrance; reachableFrom :520-535 пинит связность).
* Fallback: pos отсутствует/бит/не FLOOR/за границей → спавн в entrance
  (молча, без warn — ядро не логирует).
* pos пишется ТОЛЬКО in-flight (activeRec). Завершённый этаж (запись из
  exitDungeon) — pos нет → следующий вход = entrance (ожидаемо: этаж
  «завершён»).
* Известное ограничение (документировать в .05): explored-маска
  (dungeon-ui.js:523) НЕ персистируется → после re-anchor туман пуст и
  перестраивается вокруг восстановленного спавна; exit-тайл (dungeon-ui.js:
  527-531) не перечерчивается, пока игрок не вернётся к entrance
  (косметика).

### 2.5 Механизм фикса re-loot
* До: dungeonState/dungeonMemory НЕ персистировались (000177 §2.7), а
  мирские defeatedAt — В сейве (main.js:673-674) → reload + повторный вход =
  «свежие» сундуки (opened:false, dungeon.js:456) и группы (defeated:false,
  :432) → повторный gold/item/XP.
* После: restore задевает dungeonMemory (Map) → реальный вход через
  world-step (maybeEnterDungeon) находит запись по `'x,y:depth'` →
  contentValid → используется СОХРАНЁННЫЙ contents: открытый сундук не
  открывается повторно (openChest «уже открыт» — no-op, :492), побеждённые
  группы отсутствуют, step продолжается с сохранённого значения (wanderStep
  детерминирован от (step, seed)). Gold/XP героя — из hero-раздела сейва →
  ничего не дублируется.
* e2e-тест ОБЯЗАН идти через world-step (findNearest/isCave/walkTiles →
  авто-вход), НЕ через g.actions.enterDungeon() — debug-путь намеренно не
  читает память (CB-9, main-visuals:1896-1939: fallback-ветка
  notStrictEqual ds2.contents vs ds.contents).
