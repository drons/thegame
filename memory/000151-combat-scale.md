## Решения (расхождения a1/a2/a3 + вопросы запуска)

* **D1. Механизм — бэкинг = размер отображения × dpr (с капом
  MAX_SCALE); весь рендер — в ЛОГИЧЕСКИХ единицах (клетки × CELL) через
  `g2.setTransform(sx, 0, 0, sy, 0, 0)`.** Почему: все координаты
  отрисовки уже логические (×CELL) — трансформ масштабирует ВСЁ единым
  приёмом (спрайты, сетку, шрифты, толщину линий), единичная точка
  входа; движок растрит SVG в drawImage в ЦЕЛЕВОМ (бэкинг-)размере →
  резкость на любом бэкинге. Отклонено: «умножить координаты на s»
  (касается каждого слоя, хрупко), «чистый CSS» (000124 — это и есть
  причина мыльности).
* **D2. DPR — ВКЛЮЧАЕТСЯ в формулу** (s = clamp(отображение·dpr/база, 1,
  MAX)). Почему: аудитория ТЗ «десктоп, планшет» — в основном Retina
  dpr=2; без dpr бэкинг на них = CSS-размер и апскейлится ещё ×2 — цель
  ТЗ «не мыльные» на основной аудитории НЕ достигается; в vm-песочнице
  devicePixelRatio отсутствует → typeof-гард → 1 → все 1734 пины
  бит-в-бит (тестово нейтрально). Конвенция игры (main.js/dungeon
  без dpr) не блокирует: жалоба — на экран боя, мир за скопом («не
  больше ТЗ»). Перебита рекомендация a1/a3 («не включать»).
* **D3. Носитель чистой функции — НОВЫЙ UMD-модуль src/combat-scale.js**:
  `Game.combatScale = { MAX_SCALE, computeBacking(baseW, baseH, dispW,
  dispH, dpr) → {w, h, sx, sy} }`. Почему: красное запуска «чистая
  функция «размер canvas/масштаб → размер отрисовки»» — прямой
  node-require-тест (P1-P7) БЕЗ vm-песочницы; инвариант проекта
  «новые модули JS — UMD по образцу cities.js/building-effects.js»;
  combat-ui.js (общий с 000152) остаётся тонким. Отклонены: a1
  (G.combatRenderScale внутри combat-ui.js), a3 (G.combatUI.displayScale)
  — доступны только через vm-цепочку, лишние ханки в combat-ui.js.
  Принята плата: +1 тег (index.html: между sprites.js L903 и combat-ui.js
  L904) + 1 пин порядка + 1 запись в цепочку loadCombatUi.
* **D4. MAX_SCALE = 8** (бэкинг ≤ 336·8 = 2688 px; ~29 МБ RGBA — только
  на дисплеях с отображение·dpr > 2688, т.е. 5K+; ниже капа бэкинг =
  отображение ТОЧНО, кап срабатывает редко). Почему: «качество на всех
  размерах» (контекст запуска) + 4K дп1 (отображение·dpr ≈ 2128) требует
  кап ≥ 6.33 для 1:1; кап 8 даёт 1:1 до 2688 — все десктопы/планшеты
  включая 4K дп1 и 1440p дп2. Перебиты: кап 4 (a2; Q2) — 1080p дп2
  остаётся ×1.56 мыльным, 4K дп1 ×1.58; кап 6 (фолбэк Q2) — 4K дп1 ещё
  ×1.06. Закрытие Q2: ручной чек на 4K не требуется — кап покрывает.
* **D5. КЛИК — КРИТИЧЕСКАЯ ПРАВКА: числитель нормализации — ЛОГИЧЕСКИЙ
  baseW/baseH (c.width·CELL / c.height·CELL), НЕ canvas.width/height;
  фолбэк `r.width || baseW`.** Почему: после подъёма бэкинга старая
  формула `canvas.width/rw` ВКЛЮЧАЕТ масштаб → клик попадает мимо на s
  клеток (s=2: клетка (1,2) → (3,5); десктоп s≈3.12 — промах на 3
  клетки); `baseW/rw` не зависит от масштаба (s сокращается). При s=1:
  baseW === canvas.width → бит-в-бит (3 существующих клика-теста 000124
  проходят без правок — проверено арифметически: 144·(336/672)/48 = 1.5
  → floor 1; 60·(336/336)/48 → 1). Единственный пункт, в котором СОГЛАСНЫ
  все три анализа (найден независимо).
* **D6. RESIZE — ВКЛЮЧАЕТСЯ**: top-level
  `window.addEventListener('resize', onResize)` РЯДОМ с keydown (L361-366)
  — тот же паттерн (слушатель ОДИН раз при загрузке, guard isActive()
  ВНУТРИ, в finish() НЕ снимается). onResize: переизмерить (та же
  measureBacking()) → если бэкинг w/h отличаются от canvas.width/height
  → задать + render(). Почему: ТЗ «с учётом ТЕКУЩЕГО масштаба
  отображения» — масштаб меняется ресайзом окна (CSS 000124 отвечает
  мгновенно), без слушателя качество в бою зависает на значении начала
  боя; прецедент — dungeon-ui.js step() (L728-729) ресайзит canvas под
  вьюпорт. Перебита a1 (измерение только на старт). Проверено: window-
  стабы main-visuals/companions-cycle/dungeon-vision «resize» впитывают
  без последствий (генерическая карта типов либо игнор — глянуто).
* **D7. setTransform — АБСОЛЮТНЫЙ, в НАЧАЛЕ render(), ТОЛЬКО при
  sx≠1||sy≠1 (условие ОБЯЗАТЕЛЬНО).** Почему: присваивание canvas.width
  (resize) сбрасывает состояние контекста — повторное применение
  каждый render идемпотентно и самоисцеляется; «один раз в build()»
  (a1) хрупко при D6; условие s≠1 → при 1:1 вызова НЕТ → пины индексов
  drawCalls (calls[0]=fillRect, calls[1]=фон) бит-в-бит (якорь A1).
* **D8. ПЯТЬ битмап-строк → логические W/H** (W = c.width·CELL, H =
  c.height·CELL; при s=1 значения ИДЕНТИЧНЫ canvas.width/height):
  render() — L798 база `fillRect(0,0,W,H)`, L809 фон
  `drawImage(bgImg,0,0,W,H)`, L823 `lineTo(x·CELL+0.5,H)`, L829
  `lineTo(W,y·CELL+0.5)`; drawUnits() L674 — кламп миниполосы героя
  `Math.min(c.width·CELL - bw - 2, …)`. Почему: при активном трансформе
  старые canvas.width/height (бэкинг) масштабируются ЕЩЁ РАЗ — фон
  растягивается на s² (виден только левый-верхний 1/s² участок — РЕАЛЬНЫЙ
  баг), сетка вылезает за канвас, кламп полосы неактивен. ОСТАЛЬНЫЕ
  координаты (юниты, HP-полосы, уровни, подсветка, препятствия, арки FX,
  шрифты) — уже логические и НЕ ТРОГАЮТСЯ. Полная карта canvas.width/
  height в src/combat-ui.js сверена grep'ом: только L110-111 (build),
  L194-197 (клик), L674, L798, L809, L823, L829 — иных мест НЕТ.

## Контракты и границы

### `computeBacking(baseW, baseH, dispW, dispH, dpr) → {w, h, sx, sy}` — src/combat-scale.js (ЧИСТАЯ)
* `MAX_SCALE = 8` — экспортированная константа. GOLDEN-ПИН (P4/R6):
  смена = пересчёт пинов + пометка в этом файле (задача, которая
  меняет).
* baseW/baseH: не-число/NaN/≤0 → 336 (CELL·7) (структурно
  c.width·CELL ≥ 48 — ветка защитная; без гарда NaN-бэкинг = canvas 0).
* dispW/dispH: не-число/NaN/≤0/undefined → 1:1 на ЭТОЙ оси (w = baseW)
  — фолбэк lenient-стабов (rect без width/height) и нулевого rect
  (000124).
* dpr: не-число/NaN/≤0/undefined → 1 (vm-песочница, патология).
* sx = min(MAX_SCALE, max(1, dispW·dpr / baseW)); sy симметрично.
  **НЕДАУНСКЕЙЛ (max от 1) ОБЯЗАТЕЛЕН** — маленькие экраны/мобайл не
  трогаем (ТЗ-контекст: «не ломать маленькие экраны/мобайл»):
  даунскейл = та же мыльность, только в обратную сторону.
* w = round(baseW·sx), h = round(baseH·sy) — ЦЕЛЫЕ (canvas.width —
  unsigned long).
* Оси НЕЗАВИСИМЫ (672×336 → sx 2, sy 1) — CSS aspect-ratio 1/1 делает
  это вырожденным, формула честная.
* НОЛЬ побочных эффектов, НОЛЬ Math.random/Date — детерминирована.

### Бэкинг и состояние — src/combat-ui.js
* sx/sy — модульное состояние (рядом с ctx/overlay/g2 L79-84). build()
  ПЕРЕЗАПИСЫВАЕТ на каждый бой (canvas создаётся заново — трансформ не
  накапливается); finish() НЕ сбрасывает (следующий build перезапишет —
  зафиксировано, не усложняем).
* Измерение — ТОЛЬКО build() и onResize(); **НИКОГДА в rAF-тике**
  (rect на кадр — дорого; CSS 000124 меняет размер только с вьюпортом).
* getBoundingClientRect — try/catch → null → фолбэк 1:1.
* getContext('2d') — ровно ОДИН раз на бой, ПОСЛЕ присваиваний
  canvas.width/height.
* setTransform — только в НАЧАЛЕ render(), только при sx≠1||sy≠1;
  АБСОЛЮТНЫЙ (не накопительный); при 1:1 вызова нет (пины бит-в-бит,
  якорь A1).
* ВЕСЬ рендер — в логических единицах (клетки × CELL; поле 336×336 при
  7×7): юниты, HP-полосы, уровни, подсветка цели, препятствия, арки
  Вдоха, шрифты (12px), lineWidth — НЕ ТРОГАТЬСЯ. Исключения — 5 строк
  W/H (D8), теперь тоже логические.
* Клик: `cx = floor((e.clientX − r.left) · (baseW / rw) / CELL)`,
  `rw = r.width || baseW` (сим. cy) — D5. Border 2px в rect
  (border-box) — < 0.1 клетки, НЕ компенсируется (конвенция 000124,
  сохраняется).

### resize
* Top-level 'resize' рядом с 'keydown' (L361): один раз при загрузке,
  guard isActive() внутри, в finish() НЕ снимается (паттерн keydown).
* onResize: переизмерить → ТОЛЬКО если w/h отличаются от
  canvas.width/height → присвоение + sx/sy + render() (синхронная
  перерисовка; в vm rAF нет — событийный рендер).
* Сброс контекста при смене width безвреден: трансформ ставится
  следующим render (D7).
* В vm-песочницах resize-слушатель регистрируется, но НЕ вызывается
  (кроме R3) — поведение всех существующих песочниц неизменно.
