# 000039: рендер декораций тайлов на слое спрайтов

Статус: реализовано (тесты 486 pass / 0 fail). Follow-up задачи 000021:
данные, спрайты и чистое ядро `Game.tileVisuals` были готовы, не сделан
был только рендер в `drawSprites` (src/main.js).

## Решения

* **Порог зума.** `VISUALS_MIN_ZOOM = 24` (src/sprites.js, экспортирован
  рядом с `VISUALS_SEED`/`MAX_VISUALS_PER_TILE`). main.js вычисляет флаг
  `showVisuals` ОДИН РАЗ на кадр ДО цикла `frameTiles`:
  `typeof G.tileVisuals === 'function' && zoom >= (G.VISUALS_MIN_ZOOM || 0)`.
  При zoom < 24 блок пропускается целиком. Порог нужен сразу, а не
  «при тормозах»: при малом зуме видимых тайлов explode
  (`visibleTileRange` без капа: 1080p при zoom=4 — ~130k тайлов) и
  по-тайловый проход `tileVisuals` (13 записей каталога × hash2) дорог.
  При zoom >= 24 на 1080p <= ~3.7k тайлов.
* **Порядок слоёв.** Декорации рисуются ВНУТРИ цикла `for (const t of
  frameTiles)`, ПОСЛЕ drawImage текстуры тайла и ДО веток
  `t.hasBuilding`/`t.hasMobGroup` (т.е. под постройками/мобами, и под
  Флогистоном — тот рисуется после цикла). Отдельный проход после цикла
  рисовал бы декорации поверх построек, мобов и Флогистона — тест
  «порядок слоёв» в tests/main-visuals.test.js это закрепляет
  (индексы вызовов: текстура < декорации < маркер).
* **Чистая геометрия.** `Game.visualDrawRect(e, sx, sy, zoom)` →
  `{x, y, size}` (src/sprites.js): e.x/e.y — ЦЕНТР элемента (доли
  тайла), поэтому drawImage в (sx + e.x*zoom − s/2, sy + e.y*zoom − s/2,
  s, s), s = e.size*zoom. main.js — тонкий DOM-клей: берёт rect и
  рисует; формулы не дублируются.
* **Фолбэки.** `spriteLoader.isReady(e.sprite)` — не загрузившийся
  спрайт пропускается (элемент не рисуется, слой не падает).
  typeof-гард + `|| 0`: старый sprites.js без `tileVisuals` — слой
  выключен, игра деградирует до вида без декораций, не падает.
* **Производительность (замер, ZOOM_START=80, 1280×720):** 198 видимых
  тайлов, 187 drawImage декораций/кадр; логика по-тайлового прохода
  (tileAt + tileVisuals) ~0.29 мс/кадр (node, 60 итераций). Дёшево.

## Тесты

* `tests/main-visuals.test.js` (новый, 5 тестов) — vm-песочница с
  ВСЕЙ цепочкой `<script>` из index.html (стабы: WebGL-контекст #game,
  2d-контекст #sprites с Proxy-спаем всех вызовов в `el.drawCalls`,
  снисходительный Proxy-DOM-элемент, Image-стаб с меткой `__asset` —

  декорации тест пересчитывает САМИМ из `Game` песочницы
  (`visibleTileRange` + `tileAt` + `tileVisuals`), cam/zoom — из
  `globalThis.__game.state`; zум — диспетчем wheel-обработчика
  canvas. Тесты: каркас (state/карта/ассеты/первый кадр rAF); точная
  геометрия (множество drawImage == пересчёт, EPS 1e-6); порядок слоёв;
  порог zoom<24 → 0 / >=24 → полный набор; фолбэк (Image-стаб
  отклоняет один путь — его нет в drawImage, остальные — точное
  соответствие).
* `tests/sprites.test.js`: +2 — `VISUALS_MIN_ZOOM = 24` (фиксация
  порога из ТЗ) и геометрия `visualDrawRect` (центрирование −s/2).

## Хрупкость DOM-стаба (для будущих правок main.js)

main.js при загрузке DOM-тяжёлый (hud, кнопки, wheel/keydown/
beforeunload, per-frame hudUpdate). Стаб «снисходительный»
(Proxy: unknown-методы → no-op, querySelectorAll → []). Ассерты —
ТОЛЬКО на drawImage 2d-контекста #sprites + `__game.state` — не на
DOM. Загрузки Image резолвятся микротасками: после загрузки цепочки
нужен drain (setImmediate), ИНАЧЕ все isReady false и тесты
проходят/падают «вакуумно». window.innerWidth/innerHeight фикс.
1280×720 — frame() каждый кадр перезаписывает canvas.width из них.

## Пересечение с задачей 000042

000042 (pending) правит ТОТ ЖЕ цикл drawSprites (спрайт постройки по
footprint'у) и требует НЕ рисовать декорации на тайлах-стенах
(`inBuilding && !isEntrance`) — т.е. добавит условие НАШЕМУ блоку
декораций. Чтобы мерж был простым: блок декораций компактный и
самодостаточный (один `if (showVisuals) { ... }` внутри цикла) —
000042 встроится одной строкой-условием. Задачи 000039 и 000042
запускать/мержить ПОСЛЕДОВАТЕЛЬНО (максимальное пересечение в одной
функции).
