### 2.1 Хелпер canResurrectPick(c)

Условие: «ИГРОК ИЛИ активный союзник знают 'resurrect'»:

```js
function canResurrectPick(c) {
  if (canResurrect(c)) return true;
  const a = activeUnit(c);
  return !!(a && a.alive && !a.fled && Array.isArray(a.spells)
    && a.spells.indexOf('resurrect') >= 0);
}
```

- Чистое чтение (c.player.spells + activeUnit(c).spells); мутаций,
  console, c._rng НЕТ; Game-чтений сверх G.activeUnitId внутри
  activeUnit (typeof-guard, экспорт 000167, уже в G-снапшоте —
  combat.js ДО combat-ui.js, пин index-order) НЕТ.
- Функции-декларации хоистятся — позиция функционально неважна;
  стилистически — сразу после canResurrect.
- «Активный носитель» = ЖИВОЙ НЕ-СБЕЖАВШИЙ союзник: `a.alive &&
  !a.fled` — ДЕФИНИЦИЯ «активного союзника» ядра (activeAlly,
  combat.js L3127-3132); мёртвые/сбежавшие в очередь хода не входят
  (advanceQueue skip — combat.js L2671-2683; серый слот) → гвард в
  достижимых состояниях — no-op (страховка на будущие задачи: само-
  урон/ответный удар союзника — ревью 2026-10-13).
- Деградация к canResurrect: activeUnit(c) === null (ход игрока,
  фаза мобов, pre-roll) → хелпер эквивалентен canResurrect → путь
  игрока бит-в-байт (§4).

### 2.5 Сброс stale c.targetId — новых путей НЕТ (ТЗ п.1 «и/или»,
решение: вариант «минимально» — только расширенный гейт)

Сброс (targetId → null) — ТОЛЬКО клик по клетке МЁРТВОГО игрока (в
расширенном гейте, точка 2.2#1). Клик по клетке живого
союзника/моба (selectTarget 000198) или пустой клетке НЕ сбрасывает
(статус-кво). Путь «сброс устаревшей цели ДО каста в castRow» НЕ
вводится: один клик по строке стал бы «отклонение + сброс + каст»
(нарушение «одна причина — одно поведение», 000037) и увело бы
союзника от бит-в-байт семантики игрока (у игрока такого сброса в
строке тоже нет).
Карта разрешимости stale-цели (ядро принимает ЛИБО явного мёртвого
союзника, ЛИБО null-авто — нулевого «недостающего» сброса не
существует): (а) нужен другой мёртвый союзник → клик по его клетке —
прямая установка (auto-«первый мёртвый» не нужен); (б) мёртв игрок →
клик по его клетке → null → авто (игрок приоритетно, 000163).
ИСТОЧНИК stale-цели: на входе хода СОЮЗНИКА combat.js L2683
`c.targetId = (nearestEnemy(c, u) || {}).id || null` (000198) —
«цель на живом мобе» в начале хода Эфира; ядро не трогаем.

## 4. Аргументация «путь игрока бит-в-байт» (инвариант ТЗ)

canResurrectPick(c) === canResurrect(c) ВСЕГДА при activeUnit(c) ===
null; и ИСТИНА при canResurrect(c) === true. activeUnit(c) ≠ null
ТОЛЬКО на ходу ЖИВОГО СОЮЗНИКА. Существующие фикстуры: (a) ход игрока
/ фаза мобов / pre-roll — activeUnit null → идентичный поток
(CU166-* — сцены scene166, CU171-*, CU179-*, 000198-UI-*); (b) ход
СОЮЗНИКА при носителе-ИГРОКЕ (фикстуры CU171-ALLY/-EFIR:
hero.spells ['resurrect']) — canResurrect истинен → хелпер истинен =
СТАРОЕ значение (кнопка не тронута; canvas-клик-тестов на ходу
союзника с носителем-игроком в наборе нет); (c) ход СОЮЗНИКА без
носителя (Эфир [spark, mend] по умолчанию, наёмники [] / [mend] /
[light_heal]) — хелпер ложен = СТАРОЕ значение. ПРОВЕРЕНО (grep по
тестам): ВСЕ фикстуры 'resurrect' — на hero/c.player; ни одна vm-
фикстура НЕ даёт живому активному союзнику 'resurrect' → ложных
срабатываний в зелёном наборе нет. Мёртвый союзник НЕ может быть
активным (advanceQueue skip) → приоритет click-ветки «живой >
мёртвый» (L507-512) не меняется (живой носитель — первая ветка
selectTarget 000198, бит-в-байт).
