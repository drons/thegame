## 2. Контракты и границы

* Смена контракта 000106/000148.02: «построенные игроком — ПО КЛЕТКАМ
  (w·h спрайтов)» → «один w×h-спрайт от якоря (данные — per-cell
  записи w·h)». Контракт ДАННЫХ (9 per-cell записей) — НЕ СМЕНИЛСЯ.
* ГРУППИРОВКА — только на стороне рендера (за кадр): записи
  ds.cityContents.buildings с каталожным w>1||h>1 группируются ПО
  buildingId (Map, порядок вставки = порядок первого появления id в
  массиве — детерминированно). В группировке — ТОЛЬКО записи игрока
  (b.player === true; ревью 000264): базовые (generateCityContents —
  БЕЗ флага) ВСЕГДА идут легаси-путём 1×1 (SPEC «базовые — 1×1») —
  иначе базовые записи multi-cell id (каталог 7/18/19/24/36) могли бы
  слиться с player-footprint'ом того же id в ложный полный w×h-блок,
  чей row-major-якорь РАНЬШЕ истинного → смещённый спрайт здания
  игрока + 1×1-орфаны + «пропавшие» базовые 1×1 (механизм — изолир.
  симуляция ревью: базовые (1,2)-(1,4) + player-Арена якорь (2,2) →
  ложный якорь (1,2); НЕДОСТИЖИМО в отгруженном мире: wealth 0..3
  (validateWealth) → активен топ-4 долей; в пулах 53/54 id 7 — 5-й/
  6-й по (доля убыв, id растущ) → никогда активен; активные id
  {1,5,10,25,44} — 1×1 в каталоге; ЛОВУШКА для будущих задач: новый
  тип города/wealth>3/multi-cell id в долей_типов — пин U3).
  Player-footprint'ы попарно не пересекаются (canBuildAt space-check
  против cityOccupied — ВСЕ записи, базовые ВКЛЮЧЕНЫ) → row-major
  minimum полного player-footprint'а ВСЕГДА истинный якорь. ЯКОРЬ
  ВЫВОДИТСЯ рЕНДЕРом (в записи его НЕТ): запись r — АНКОР, если ВСЕ
  w·h клеток footprint'а от (r.x, r.y) присутствуют среди
  НЕпотреблённых записей того же id; footprint ПОТРЕБЛЯЕТСЯ (cells.
  removeAll — ВСЕГДА, независимо от viewport: потребление — по
  ДАННЫМ, не по вьюпорту). Жадное потребление идёт в row-major-
  порядке (y, потом x). Непокрытые записи (ОРФАНЫ — полный footprint
  не сложился: недостижимо в production — view производный;
  дегенератный пин: одиночная запись id 36 → dungeon-ui.test.js
  «базовые id (1/25/36/44)» — ОСТАЁТСЯ 1×1) → ЛЕГАСЬ 1×1 по клетке
  (fail-open, бит-в-бит с поведением до 000264).
* ПОЧЕМУ жадное row-major, а не «все полные footprint'ы» / «id → один
  якорь»: уникальности типа в canBuildAt НЕТ (только space/cap/reach)
  → ДВЕ СОСЕДНИЕ Арены — легальное состояние (город fp≥3: cap 128,
  9+9 < 128). У записи (4,2) (правая колонна первой Арены, соседняя
  Арена x∈{5..7}) footprint x∈{4..6} тоже «полный» — ложный анкор;
  жадность: (2,2) съеден первым → (4,2) уже неполный → skip. Итог:
  ровно 2 крупных спрайта по своим якорям, ложного 3×3 на стыке нет.
* 1×1-записи (w=1,h=1; НЕТ каталога; неизвестный id; мусорные x/y) —
  ЛЕГАСЬ-ПУТЬ БИТ-В-БИТ: клип `b.x<x0||b.x>x1||b.y<y0||b.y>y1`,
  cityBuildingPath(live, id, nowT, b.x, b.y), cellRect, drawImage
  cr.x/cr.y/cr.w/cr.h. Все базовые постройки города — 1×1
  (generateCityContents: takeSpot — одна клетка) → бит-в-бит
  (G1 «ровно 3 спрайта», z-порядок 000191.6a/6b, все 000148.02-юниты).
* ГЕОМЕТРИЯ крупного спрайта — снап-прямоугольник из ТОГО ЖЕ
  снап-механизма пола города (000215): tl = cellRect(ax, ay,
  proj(ax,ay)); far = cellRect(ax+w−1, ay+h−1, proj(ax+w−1, ay+h−1));
  rect = {tl.x, tl.y, far.x+far.w−tl.x, far.y+far.h−tl.y};
  drawImage(img, tl.x, tl.y, rw, rh). Для w=h=1 far = tl → ВЫЗОВ
  БИТ-В-БИТ с легасью. Fallback (нет live.snappedTileRect / NaN) —
  cellRect сам даёт сырое (p.x, p.y, zoom, zoom) → rect = (p.x, p.y,
  w*zoom, h*zoom) (линейность worldToScreen).
* ПОЧЕМУ снап, а не raw w*zoom×h*zoom мирового прохода 2 (решение
  Проектирования, приоритет над a2-архитектурой): пол города рисуется
  снап-rect'ами (000215 — краёв без AA-шва); здание ровно покрывает
  w×h ПОВЕРХНОСТНЫХ клеток пола → края спрайта обязаны совпасть с
  снап-краями тайлов пола (иначе 1px-шов между спрайтом и полом —
  тот же дефект, что чинил 000215 для тайл-тайл). При ЦЕЛОМ зуме и
  целой/полунцелой камере снап-rect ЧИСЛЕННО РАВЕН
  worldToScreen(anchor) + w*zoom×h*zoom (ИДЕНТИЧНОСТЬ
  snappedTileRect, map.js:1329) → красные пины (worldToScreen-
  позиция, размер 3·zoom) проходят в обоих случаях. МИРОВОЙ проход 2
  (raw) — НЕ ТРОГАЕТСЯ (пины main-visuals 000042).
* ВИДИМОСТЬ: якорь рисуется, если footprint-ПРЯМОУГОЛЬНИК [ax..ax+w−1]
  ×[ay..ay+h−1] ПЕРЕСЕКАЕТ видимый диапазон [x0..x1]×[y0..y1]
  (семантика мирового прохода 2: любой видимый член footprint'а даёт
  якорь; сам якорь может быть за краем окна — запас зума < 3).
  Орфаны — легасий-клип по КЛЕТКЕ. Потребление — viewport-НЕЗАВИСИМО.
* АНИМАЦИЯ: cityBuildingPath(live, id, nowT, ax, ay) — фаза кадра — от
  ЯКОРЯ (полное зеркало мирового прохода 2; buildingFrameIndex(now,
  x, y, n) = (⌊now/800⌋ + ((x·5+y·9) mod n)) mod n — чистая f,
  sprites.js:827). Реально размещаемые 3×3: Арена → слот 4 (ARENA),
  Храм солнца → слот 8 (TEMPLE) — кадров НЕТ (BUILDING_FRAMES — только
  слоты 0/2/3/5/7/11) → статичный спрайт (visually no-op); механизм

* Z-ПОРЯДОК — БЕЗ ИЗМЕНЕНИЙ: пол → ПОСТРОЙКИ → стена(город — в
  floor-pass) → дверь → игрок. Постройки не пересекаются (space check)
  → порядок внутри слоя невидим. Красный кадр — ОДИН drawImage на

* ДЕТЕРМИНИЗМ (D10): слой — чистая функция (layout, cityContents,
