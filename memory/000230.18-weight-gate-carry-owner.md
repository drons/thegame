## 2. Ключевое решение — конвенция c.carryOwner (зафиксировано)

Вариант (1) ТЗ «Что сделать», форма «конвенция c.carryOwner».
ЕДИНСТВЕННЫЕ две кодовые правки:

```
src/items.js — maxCarryWeight:
  function maxCarryWeight(c) {
    const owner = (c && c.carryOwner &&
        typeof c.carryOwner === 'object' &&
        !Array.isArray(c.carryOwner)) ? c.carryOwner : c;
    return BASE_CARRY_WEIGHT * P.derived(owner).carryWeightMult;
  }

src/companions.js — allyView:
  function allyView(hero, sheet) {
    return {
      inventory: hero.inventory,
      primary: hero.primary,
      secondary: hero.secondary,
      equipment: sheet.equipment,
      equipmentBonus: sheet.equipmentBonus,
      carryOwner: hero,
    };
  }
```

Почему конвенция, а не явный owner-аргумент (1b):
(i) сигнатурная поверхность — 1 функция против 5
(equip/unequip/addItem/checkAdd/maxCarryWeight + 2 call-сайта
:1263/:1292); (ii) композит самонесущий — уже несёт
hero.inventory/primary/secondary (паттерн .06 §2.1), владелец веса
поедет ВМЕСТЕ с композитом, и будущий прямой `G.equip(composite,
id)` не сможет «забыть» владельца (у owner-аргумента — молчаливо
гибридный гейт при пропуске 3-го аргумента); (iii) новая семантика
пинится напрямую: `G.maxCarryWeight(view-с-carryOwner)` = 39;
(iv) canAddItem НЕ расширяется (у owner-аргумента пришлось бы
ради симметрии — dry-run с owner ≠ addItem с owner; в кодовой базе
canAddItem на композите НИГДЕ не вызывается — только hero-пути:
building-effect-storage, main, ui, building-actions, craft,
dungeon).

Почему guard «plain-объект»: идиома `typeof x === 'object' &&
!Array.isArray(x)` — местный стиль items.js (equipmentStats
:1317-1318). Мусорное carryOwner (строка/число/null/массив) →
фолбэк на c — класс ошибки ВХОДА как у текущего
maxCarryWeight(мусорный c); plain-объект без primary → TypeError в
P.derived — тот же класс, недостижимо в игре (ally-путь: hero
guard'нут allyReject №4 — primary/secondary/inventory plain-
объекты; hero-путь: carryOwner отсутствует). НОВОЙ деградации
(console.error) НЕ вводится: поведение для ВСЕХ ТЕКУЩИХ входов
не меняется (carryOwner нигде не встречается — grep 0 вхождений в
src/tests/memory до этой задачи).

ОТКЛОНЕНЫ: (1b) owner-аргумент — см. выше; (2) «вынести вес-чек за
generic API» (новый внутренний items-API с явным derived/лимитом) —
эквивалент 1b по проводке без выигрыша; предпроверка в
companions.js сама по себе НЕ РАБОТАЕТ (внутренний checkAdd в
addItem прогоняется всё равно с тем же лимитом — проверено по
коду), а failsafe «предмет остаётся надетым» обязан остаться
ВНУТРИ generic unequip (зеркало геройского, пины E1/I1); hack
подмены composite.secondary.back = S_hero·(1+a_hero)/
(1+a_merc) — отвергнут ТЗ (дробный «уровень», live-зависимость от
экипировки наёмника, деление на (1+a_merc) кромочное при a=−1,
ломает читаемость).

## 3. Контракты и границы

* **Контракт композита**: любой объект-«персонаж», передаваемый в
  generic equip/unequip/addItem/canAddItem, чей инвентарь НЕ
  собственный, ОБЯЗАН объявить `carryOwner` = владелец инвентаря
  (полный персонаж). ЕДИНСТВЕННЫЙ композит в кодовой базе —
  allyView; он carryOwner объявляет.
* **Граница «владелец не объявлен»**: композит БЕЗ carryOwner →
  `P.derived` самого композита (гибрид) — легальный режим,
  задокументирован, ЗАКРЕПЛЁН пере-пином E2a (assert
  `G.maxCarryWeight(view-без-carryOwner)` = 36). Зелёный пин
  «000230.06 (зелёный пин)» (items.test.js:4406, ручной view без
  carryOwner, pre-init {}/{}) остаётся зелёным — вес в нём
  неграничный (лёгкий меч), значением гейта он НЕ пинан (границу
  пинет E2a).
* **canAddItem НЕ получает carryOwner** — осознанная граница
  («не больше, чем просит ТЗ»): dry-run на композите нигде не
  вызывается; будущий dry-run ally-unequip — отдельная задача.
* **Только affix-навык 'back' влияет на гейт**:
  carryWeightMult = 1 + pct('back') — единственный (sheet.js:496).
  Прочие affix'и на экипировке героя/наёмника вес-гейт не смещают.
* **derived владельца — LIVE-чтение** (без кэша/снапшота): надетое
  / снятое 'back'-кольцо героя меняет гейт МЕЖДУ ally-операциями
  немедленно — это и есть фикс режима (a) ТЗ («снятие своего
  кольца у героя гейт НЕ чинит» — про ТЕКУЩИЙ баг; после фикса
  hero.equipment в гейте участвует).
* **Все ЧЕТЫРЕ пути возврата покрыты автоматом** (одна точка
  гейта): (1) allyUnequip (ui.js «снять», :1121); (2) swap-возврат
  при allyEquip (items.js equip :1263 — тот же allyView, 000230.20
  «все или ничего»); (3) dismiss → returnEquipmentToHero →
  allyUnequip (000230.06.01, stop=true); (4) payWages →
  returnEquipmentToHero → allyUnequip (000242, stop=false). Все —
  через `G.equip/G.unequip(allyView(hero, sheet))`. Memory
  000230.06.01 §3.6 и 000242 «двойного фикса не нужно» — выполнено
  конструктивно.
* **Геройский путь бит-в-бит**: герой (createCharacter / лейаут
  сейва 000031) НОСИТЬ carryOwner не может (поле новое, layout
  фиксирован; sanitizeSavedHero 000029 — фиксированный набор
  полей) → owner = c → `P.derived(c)` побайтово. Все hero-вызовы
  maxCarryWeight (ui-tab-skills.js:544 hero-ветка, main.js:3863
  maxWeight в снапшот сейва, checkAdd в hero-addItem) — без
  изменений. HUD «Вес: X/Y кг | Слоты: Z/20» — побайтово.
* **Сейв v1 не тронут**: carryOwner живёт ТОЛЬКО на одноразовом
  объекте allyView (новый на каждый allyEquip/allyUnequip) — на
  hero/sheet не записывается, сериализуется НИКОГДА. copyMerc
  Sheet/sanitizeMercSheet/serializeRoster — не трогаем. ФОРМА
  КОДА: НЕ присваивать carryOwner на hero/sheet в src (иначе ушёл
  бы в сейв при сериализации hero целиком).
* **Детерминизм**: ноль новых вызовов RNG (c._rng/Math.random/
  generateSeedPixels в пути фикса отсутствуют — проверено
  чтением); derived/equipmentAffixes — чистая арифметика, уже
  вызывалась в том же вызове (derived(composite) → derived(hero) —
  тот же класс работы). Золотые eventSeed/боя/лута — не трогаются.
* **Порядок вызовов не меняется**: 000230.20 rollback-порядок
  equip (eq[slot]=new ДО addItem(prev); откат — restore) и unequip
  (обнуление слота ДО addItem; failsafe — restore) — сохранён;
  меняется ТОЛЬКО число в сравнении вес-ветки (:662) на
  композитном пути. Epsilon 1e-9 — не трогать; re-pin E2b —
  значения с запасом ≫1e-9 (36.2 vs 36).
* **Ошибка P.derived → null при деградации (нет SkillsData)** →
  TypeError на `.carryWeightMult` — СУЩЕСТВУЮЩАЯ геройская кромка
  (memory 000230.06 §3: недостижимо, skills-data ВСЕГДА до sheet в
  играх/цепях) — НЕ новая кромка.
