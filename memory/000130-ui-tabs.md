## 2. Чистые части и их экспорт (node-ветка UMD)

Единая UMD-форма ВСЕХ 6 модулей (образец cities.js/controls.js; при
загрузке — НОЛЬ DOM, НОЛЬ require, НОЛЬ RNG, НОЛЬ console.error в
правильном порядке):

```js
(function (root, factory) {
  if (typeof module === 'object' && module.exports) {
    module.exports = factory(null, null);   // node: определение, без регистрации
  } else {
    const G0 = typeof root.Game === 'object' ? root.Game : {};
    const m = factory(G0, root);
    const reg = G0.uiTabs;
    if (reg && typeof reg.register === 'function') {
      reg.register(m.tab);                  // мутация реестра in place
    } else if (root) {
      console.error('src/ui-tab-X.js: Game.uiTabs не найден — src/ui-tabs.js ' +
        'должен грузиться ДО вкладочных модулей (задача 000130)');
    }
    root.Game = Object.assign({}, G0, m.game || {}); // паттерн «модуль
    // заменяет Game» (000018/000038); реестр — ТОТ ЖЕ объект-ссылка
  }
})(typeof globalThis !== 'undefined' ? globalThis : self,
function (G0, rootRef) {
  'use strict';
  const G = G0 || {}; // ОДИН снапшот (000038) — все провайдеры (player/
  // items/buildings/npc/map/skills-data/companions) грузятся ВЫШЕ в index.html
  // … build/render — функции, G.* — при ВЫЗОВЕ …
  return { tab: { column, id, label, build, render }, /* game: {…} */ };
});
```

Экспорты (node-ветка = то же, что spread на Game в браузере):
* ui-tabs.js: `module.exports = factory()` → реестр-экземпляр
  `{ register, get, list }` (тестируется в node напрямую).
* ui-tab-quests.js: `{ tab: {...}, game: { buildActiveQuestRow,
  findQuestInCatalog } }` — game-экспорт = ПЛОСКОЕ spread на Game
  (`Game.buildActiveQuestRow`, `Game.findQuestInCatalog`), как G.activeQuests/
  G.refreshBringItems — прецедент чистых хелперов на Game.
* Остальные 4 ui-tab-*.js: `{ tab: {...} }` (game нет; регистрация —
  побочный эффект браузерной ветки).
* `m.game || {}` → uniform-замена root.Game во всех вкладочных модулях
  (одна и та же форма, ревью по шаблону).

## 3. Ленивые ссылки и guards

* Снапшот `G = G0` ОДИН раз в factory (000038): все G.* потребители
  (derived/equipmentStats/inventoryWeight/maxCarryWeight/xpForNext/
  slotCount/INVENTORY_SLOTS/QUICK_SLOTS/PRIMARY_SKILLS/SECONDARY_SKILLS/
  canRaise/secondaryName/MAX_SKILL_LEVEL/skillXpForNext/practiceCap/
  getItem/buildingNameUi/buyPrice/sellPrice/shopKindsFor/refreshBringItems/
  activeQuests/totalQty/mobGroupName — проверено: player.js, items.js,
  buildings.js, map.js, skills-data.js, npc.js) грузятся ДО блока
  ui-tab-* → снапшот достаточен, rootRef/ленивый Game НЕ нужен.
* Реестр в ядре читается ЛЕНИВО в buildPanel (не при загрузке!):
  ui.js обязан грузиться чисто БЕЗ реестра (tests/index-order.test.js
  гоняет ui.js один в голом sandbox без document).
* Degradation (000053 — «отсутствие зависимости — console.error +
  деградация, игра не падает»):
  * вкладочный модуль без Game.uiTabs → console.error + НЕ регистрируется
    + НЕ роняет (в т.ч. в голом sandbox без Game — G0 = {}, console.error,
    без throw);
  * ui.js без реестра → console.error в buildPanel + панель строится с
    ДВУМА ПУСТЫМИ столбцами (makeColumn: `active: defs.length ? defs[0].id
    : null`, цикл по пустым defs — no-op); без краха;
  * npcUI без Game.buildActiveQuestRow (песочницы без ui-tab-quests.js,
    напр. CHAIN npc-hire) → ленивый typeof-guard в renderQuestsTab:
    console.error + строка «В работе» пропускается; questById → null →
    «Выполнено» рисует голый id (существующий фолбэк). Guard — ТОЛЬКО в
    момент вызова (не при загрузке) → errors.length === 0 на загрузке
    сохраняется во всех песочницах.
* Критично (000038-ловушка, a3): браузерная ветка НЕ создаёт/НЕ заменяет
  объект реестра — регистрация = push во внутренний массив СУЩЕСТВУЮЩЕГО
  Game.uiTabs; Object.assign-замена root.Game несёт ту же ССЫЛКУ на
  реестр. Новый объект реестра во вкладочном модуле = потеря регистраций.

## 4. Контракты (форма записи, ctx, реестр)

### 4.1 Форма записи вкладки (кандидат ТЗ сверен с существующими 6
### вкладками; ОТКЛОНЕНО зафиксировано)

```
{ column: 0 | 1,        // 0 — левый столбец, 1 — правый
  id: 'quests',         // уникальная строка (ключ get; фиксаторы:
                        //   character/inventory/settings | equipment/shop/quests)
  label: 'Квесты',      // подпись .cp-tab (побайтовые фиксаторы ui-panel)
  build(pane, ctx),     // ОДИН раз в buildPanel: скелет, тела — на
                        //   ctx.panel._* (имена фиксированы тестами)
  render?(ctx), }       // КАЖДЫЙ render(), в порядке РЕГИСТРАЦИИ,
                        //   скрытые pane тоже (quests/000100)
```
* `name` ОТКЛОНЕНО — конвенция 000096 `label` (подписи зафиксированы
  побайтовыми тестами).
* `render(state)` ОТКЛОНЕНО в пользу `render(ctx)` — архитектура 000096
  «build once + update in place» через panel._*; per-tab state-объекты =
  ре-архитектура, а не рефакторинг.
* `onKey?(code, state)` ОТКЛОНЕНО — по-вкладочных клавиш НЕТ: [I]/Esc —
  панельный уровень в ядре (toggle/attachEsc с гардами), переключение
  вкладок — только клик (.cp-tab в делегированном click). Нет
  потребителей.
* `isDefault?` ОТКЛОНЕНО — активная по умолчанию = ПЕРВАЯ вкладка
  столбца (порядок регистрации). Нет потребителей.
* `order` (явное поле сортировки) ОТКЛОНЕНО — порядок = ПОРЯДОК
  РЕГИСТРАЦИИ = порядок script-тегов (fix-ируется пином index-order):
  одно поле правды для порядка загрузки И порядка вкладок; simpler, чем
  sort (order, column).

### 4.2 Реестр Game.uiTabs (src/ui-tabs.js)

* `register(tab)` — валидация: tab-объект; id — непустая строка, УНИКАЛЬНА
  (дубликат → console.error + сохраняется ПЕРВАЯ — авторитетен порядок
  скриптов); label — непустая строка; column — строго 0 или 1; build —
  функция; render — опционально, если есть — функция. Любое нарушение →
  console.error + skip (игнор записи). НИКОГДА не бросает.
* `get(id)` → tab | null.
* `list()` → КОПИЯ массива в порядке регистрации (мутация возвращённого
  не влияет на реестр — фиксатор тестом).
* node-ветка — тот же экземпляр (тестируется в node).

### 4.3 ctx (контракт ядро → вкладка), строится ОДИН раз в buildPanel

```
ctx = {
  panel,            // корневой .char-panel; тела — на panel._title/_stats/
                    //   _invBody/_equipBody/_quickBody/_shopSec/_shopBody/
                    //   _questsBody (имена НЕ менять — прямые доступы тестов)
  el,               // el(tag, cls, text) — DOM-фабрика ядра (НЕ дублировать)
  itemRow,          // строка предмета с кнопками+tip (000097) — из ядра
  itemTipText,      // текст тултипа предмета (000097) — из ядра
  get character(),  // ЖИВОЕ (closure-переменная ядра; может быть null в
                    //   build — buildPanel до проверки character: fallback ''
  get shop(),       // ЖИВОЕ, null если нет (setShop каждый кадр, L1695 main.js)
  get quests(),     // ЖИВОЕ { npcs, book } (оба null или оба заданы; day НЕ
                    //   передаётся — в рендере не используется, 000100)
}
```
* itemRow/itemTipText ОСТАЮТСЯ в ядре (не в ui-tab-inventory.js) и идут
  через ctx: общий механизм строк доступен ЛЮБОЙ вкладке (в т.ч. будущим),
  как el; doItemAction (обработчик кнопок data-act) — тоже ядро.
* flashNotice в ctx НЕ идёт (вкладки не используют; только ядро).
* ТОЧНОЕ воспроизведение старых проверок (byte-level): `!questBook` ≡
  `!ctx.quests().book`; `questNpcs || []` ≡ `(ctx.quests().npcs || [])`;
  `G.refreshBringItems && questNpcs` — порядок условий сохранить
  (refreshBringItems вызывается ОДИН раз за render — в хуке quests).
* Модули вкладок БЕЗСОСТОЯТЕЛЬНЫ (никаких module-level shop/questNpcs):
  живое состояние — closure ядра, чтение — через getters ctx.

### 4.4 Порядок рендера и DOM

* Рендер-цикл ядра: `for (const t of tabs) if (typeof t.render === 'function')
  t.render(ctx)` — tabs зафиксированы при buildPanel (копия list()).
  Порядок хуков = порядок регистрации: character → inventory → equipment →
  settings (нет render) → shop → quests.
* Старый порядок записи DOM (character → equip → quick → inv → shop →
  quests) отличается (inv раньше equip), НО тела НЕЗАВИСИМЫ (каждый хук
  пишет только в СВОИ panel._*; кросс-чтений тел нет) → ФИНАЛЬНЫЙ DOM
  побайтово тот же; фиксаторы — существующие .cp-* ассерты.
* shop-хук: `if (!ctx.shop()) { panel._shopSec.style.display = 'none';
  return; }` — ранний return прежнего renderItems переехал в хук ЦЕЛИКОМ
  (инвентарь/снаряжение рендерятся независимо, как и сейчас).
* Список вкладок в render НЕ перечитывается (копия с buildPanel):
  саморегистрация действует при ЗАГРУЗКЕ страницы (все реальные вкладки —
  до buildPanel); поздняя регистрация (тестовая) — до ПЕРВОГО toggle
  (buildPanel ленивый) → успевает в анти-прецедент-тесте.
