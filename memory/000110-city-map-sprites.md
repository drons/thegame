## 1. Решение по спрайтам

* **Каталог — `assets/sprites/cities/` (новый), ровно 4 файла**:
  `city_51.svg` (хутор 1×1), `city_52.svg` (деревня 2×2),
  `city_53.svg` (город 5×5), `city_54.svg` (столица 7×7).
  Почему отдельный каталог, а не `sprites/buildings/`: город НЕ слот
  (000103 — свой канал, type = BUILDING_TYPES.NONE); отдельный каталог
  оставляет filter `buildingDraws` (префикс `assets/sprites/buildings/`)
  и все byte-level-пины 000042 нетронутыми. Почему имена `city_<id>.svg`:
  привязка к id каталога (51..54, 000102) нечувствительна к переименованию
  типа.
* **Вариант «стена footprint'а» — ОТДЕЛЬНОГО файла НЕТ** (решение по
  опции a3 §5 «5 или 8 файлов» — 4). Стена врисована в каждый SVG по краю
  viewBox (периметральная полоса). Почему: footprint рисуется ОДНИМ
  w×h-прямоугольником от якоря (механизм 000042); пути «стена на каждый
  тайл» в main.js нет и не добавляется (инвариант 000042: «одна
  постройка — один прямоугольник», порядок слоёв).
* **viewBox = 64w × 64w, где w — ширина из каталога**: 51 → `0 0 64 64`,
  52 → `0 0 128 128`, 53 → `0 0 320 320`, 54 → `0 0 448 448`. Почему:
  64 art-px на тайл = 1:1-соответствие тайлам при растяжке до w·zoom;
  единый 64×64 на 7×7 столичный footprint смазал бы арт в 7 раз.
  svg.test.js принимает любой viewBox из 4 чисел.
* **src/sprites.js** (UMD; node-require — только map.js/
  mob-groups-data.js/visuals-data.js, buildings.js НЕ требуется):
  * `CITY_SPRITES` — литерал `{51: 'assets/sprites/cities/city_51.svg',
    52: '…city_52.svg', 53: '…city_53.svg', 54: '…city_54.svg'}` —
    паттерн BUILDING_SPRITES/COMBAT_BG_DUNGEON (синхрон литерала с
    каталогом закрывает SP-C2; вставка после BUILDING_SPRITES, ~L246).
  * `citySprite(buildingId)` — чистая: `Number.isInteger(buildingId)` →
    `CITY_SPRITES[buildingId] || null` (вставка рядом с buildingSprite,
    ~L511). NONE/нецелое/неизвестное/слот-ид → null.
  * `allAssetPaths()`: +`paths.push(...Object.values(CITY_SPRITES))`
    (~L645, после строки BUILDING_SPRITES) — без неё загрузчик main.js
    не поставит SVG в очередь.
  * Экспорт: `CITY_SPRITES` (строка данных ~L781) и `citySprite`
    (строка функций ~L795).
* **Формат SVG**: статичные; корень `<svg xmlns="…" viewBox="…">`;
  прозрачный фон (без «небесного» background-rect; арт — стены +
  крыши, он и покрывает footprint); БЕЗ SMIL/DOCTYPE/CDATA/`&`/пустых
  атрибутов/внешних ссылок (href/foreignObject/text) — строгий парсер
  tests/svg.test.js (000120). Палитра — та же семья, что 13 спрaйтов
  построек: камень #8a8494/#7a7484/#6a6472, roofs #96793f-тоны,
  мох #4f7a3a, тёмный портал ворот #3a3542 (эталон —
  assets/sprites/buildings/rune_stone.svg, cave_entrance.svg).
* **Композиция каждого SVG** (вид «крепость на w тайлах», фронтальный):
  * периметральная стена — полоса у КРАЕВ viewBox (толщина 14/18/22 px
    для 52/53/54; у 51 вся плитка = сторожевая башня-воротца);
  * ворота — тёмный проём с перемычкой на позиции каталожного входа:
    `x_art = (вход[0] + 0.5)·64` на нижней кромке (у всех 4 типов вход
    на последней строке каталога): 51 (0,0) → центр единственной
    плитки (32,32); 52 (1,1) → x=96; 53 (2,4) → x=160; 54 (3,6) → x=224;
  * внутренности различают типы по масштабу: 51 — одна хижина;
    52 — 2-3 дома; 53 — ряд домов + шпиль церкви; 54 — замок/донжон +
    2 башни + ряды домов; угловые башни у 53/54.
* **Порядок (svg-гейт ОБЯЗАТЕЛЕН ДО каталога)**: (1) SVG созданы
  (вне assets/) → (2) прогон через парсер svg.test.js → (3) пин
  `EXPECTED_SVG_BY_DIR` + `'sprites/cities': 4` → (4) SVG в
  assets/sprites/cities/ → (5) код → (6) npm test.
* **tests/svg.test.js (единственная санкционированная правка
  существующего теста)**: `EXPECTED_SVG_BY_DIR` (L435) + строка
  `'sprites/cities': 4` — строгий счётчик 291 → 295; сообщение об
  ошибке самого теста предписывает эту правку (семантика — обход/
  валидность — не меняется). Обновить также счётчики в комментарии
  шапки файла (технич.).
