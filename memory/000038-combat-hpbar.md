# 000038 — Полоска HP героя в бою: единый источник цветов/порогов

Полоска здоровья героя на экране боя. Подзадача 000030, направление 7.

## Чистая функция (src/sprites.js)

`hpBarColor(frac) → css-цвет` + константа `HP_BAR_COLORS`.
Экспортировано в UMD-блок (в браузере — `Game.hpBarColor`).

Пороги (зафиксированы в комментарии кода и тесте):
  frac >= 0.5 → зелёный (#6fdc6f)
  frac >= 0.2 → жёлтый  (#e0b13c)
  иначе       → красный (#d9483b)

Границы «включены сверху»: ровно 0.5 — зелёный, ровно 0.2 — жёлтый.
(ТЗ «>50%» / «20–50%» читаем как включительные диапазоны 50–100 и 20–50.)

Colors — из существующей палитры (новых не введено):
  #6fdc6f — полоса HP мобов (combat-ui.js)
  #e0b13c — ROLE_COLORS.swarm (combat-ui.js) / dungeon-ui.js
  #d9483b — ROLE_COLORS.melee (combat-ui.js) / dungeon-ui.js

Clamp: frac вне [0,1] → [0,1] (±Infinity → 1/0); NaN/нечисла → 0
(красный). Рендер не падает ни при каких аргументах.

## UI (src/combat-ui.js)

- DOM-полоса `.combat-hpbar` — ВТОРОЙ элемент `.combat-side`: после
  `.combat-turnorder` (000036), ПЕРЕД `.combat-state`.
  Заполнение: width = clamp(hp/maxHP)·100%, background = hpBarColor;
  текст `HP ${hp}/${maxHP}` всегда виден.
- maxHP = `Game.derived(c.player).maxHP` (те же источники, что в
  .combat-state). Новых полей в ядре нет.
- Canvas-миниполоса 4px над ромбом (паттерн мобов: дорожка #3a0d0d +
  заполнение hpBarColor). Рисуется ПОСЛЕ героя → «поверх любого вида
  героя» (совместимость с 000047 — спрайт).
- Обновление ТОЛЬКО в render(): один блок `p/d/hpFrac/hpColor` на
  троих потребителей (canvas, stateEl, DOM). Никаких отдельных
  слушателей/timers. rAF-цикл (000047) обновит тем же render().
- finish() обнуляет hpbarEl/hpbarFillEl/hpbarTextEl.

## Порядок загрузки (ВАЖНО для 000047 и будущих полос)

Каждый UMD-модуль ЗАМЕНЯЕТ объект Game:
`root.Game = Object.assign({}, root.Game, factory(...))`. Модули с
`const G = globalThis.Game` (combat-ui.js, dungeon-ui.js, ui.js,
main.js) снимают его ОДИН раз при загрузке — функция из скрипта,
загружающегося ПОЗЖЕ, через этот G недоступна НИКОГДА. Ленивый вызов
«после загрузки всех скриптов» этого НЕ решает: G — ссылка на старый
объект (ревью 000038: в исходной версии sprites.js стоял ПОСЛЕ
combat-ui.js, `G.hpBarColor` был всегда undefined, и полоса героя —
DOM и canvas-миниполоса — ВСЕГДА рисовалась фолбэком `'#6fdc6f'`;
пороговые цвета не срабатывали никогда. Подтверждено vm-симуляцией
цепочки index.html).

Решение (паттерн задачи 000018): в index.html `src/sprites.js`
грузится ДО `src/combat-ui.js`; пара закреплена тестом
tests/index-order.test.js. Правило для будущих полос/функций:
модуль, ЧЬЯ функция нужна другому UI-модулю через захваченный G,
должен грузиться РАНЬШЕ него, а пара — фиксироваться в
tests/index-order.test.js (или же чтение из globalThis.Game лениво —
но в проекте принят первый вариант).

Фолбэк `'#6fdc6f'` в render() combat-ui.js остался только на случай
ОТСУТСТВИЯ sprites.js вовсе (напр. vm-песочница node) — рендер не
падает (стиль деградации). tests/combat-ui.test.js покрывает оба
пути: цепочка в порядке index.html (sprites.js ДО combat-ui.js) →
красный `#d9483b` при frac < 0.2; цепочка без sprites.js → фолбэк.

## MP-полоса — НЕ делалась (решение)

Задача про HP. MP в .combat-state остаётся текстом («MP x/y» в строке
stateEl). Если понадобится — отдельная задача с тем же паттерном
(синяя полоса рядом). hpBarColor для MP НЕ использовать: у MP порогов
нет (нужна своя функция).
