  минимум поверхности, фикстуры node-тестов читают live.

  дословно (соль 3-й аргумент hash2, >>> 0 дословно, текст-пин).

### Финальные решения стадии Проектирование (новые)
* **6. FP-семантика pickRarityTier** — последовательное вычитание по
  ЗАПИНЕННОЙ таблице, строгое `r < acc`, fallback = последний тир:
  ```
  r < 0.5                  → common
  0.5 ≤ r < 0.8            → rare
  0.8 ≤ r < 0.9500000000000001 → epic
  … ≤ r < 0.9990000000000001   → legendary
  r ≥ 0.9990000000000001  → impossible (включая 1.0)
  ```
  Почему: единственный источник данных = таблица RARITY (EQ1);
  ОДНА чистая функция для ОБЕХИХ потребителей (единая FP-граница);
  вероятности совпадают с ТЗ 50/30/15/4.9/0.1 с точностью до FP-
  округления границ (≤1e-15).
* **7. ПРАВКА ТРЕХ АНАЛИЗОВ: 0.999 → legendary, НЕ impossible.**
  a1/a3/arch утверждали «0.999→impossible» (в т.ч. «проверено
  node-пробой») — ЛОЖЬ: acc(legendary) = 0.5+0.3+0.15+0.049 =
  0.9990000000000001 > 0.999, значит 0.999 < acc → legendary.
  Проверено node-пробой (эта станция): 0.25→common, 0.5→rare,
  0.65→rare, 0.8→epic, 0.875→epic, 0.95→epic, 0.9500000000000001→
  legendary, 0.9745→legendary, **0.999→legendary**,
  0.9990000000000001→impossible, 0.9995→impossible, 1→impossible;
  сумма chances РОВНО 1.0 в FP. E3-пин — ЭТИ значения (чистые
  литералы + точные acc-значения, фиксирующие строгое `r < acc`).
  Тест, запинаящий 0.999→impossible, покраснел бы на зелёной стадии
  или заставил бы «исправить» реализацию под неверный пин.
* **10. Триггер сундука — ЯВНЫЙ `slot` ТОЛЬКО** (`it.slot !==
  undefined`), НЕ `slot || rarity` как в черновике arch.
  Почему: ТЗ п.2 дословно «предмет с `slot`»; валидатор .01 допускает
  rarity БЕЗ slot (у weapon/armor slot — ОПЦИОНАЛЕН, items.js:248
  требует slot только для shield/artifact/tool/ring); риск-дизайн
  a3 §2: legacy (10 weapon/armor без slot) НИКОГДА не ре-роллятся —
  супер-триггер нарушил бы это в момент появления rarity без slot.
* **13. Позиция сундучного блока — ПОСЛЕ блока залежей, ПЕРЕД return**
  generateDungeonContents. Почему: явный «ПРАВИЛО ДЛЯ БУДУЩЕГО»
  000157.02 §4.2 («новые механики контента получают СВОИ потоки
  ПОСЛЕ залежей») + рекомендация a1; функционально эквивалентно
  arch-варианту «между циклом сундуков и залежами» (блок не трогает
  главный rng/occupied/spots — только ch.item in-place), но
  противоречило бы доменной группе; позиция ЗАПИНЕНА (перенос =
  осознанный ре-пин визуального контракта, без дельты goldens).

## 3. Контракты и границы

### 3.1 src/loot-equip-data.js (Game.LootEquipData)
Форма — UMD data-модуль по паттерну mob-groups-data.js:
```
node:    module.exports = factory()
browser: root.Game = Object.assign({}, root.Game, { LootEquipData: factory() })
```
factory() — чистая (нет console.*, нет require-других-модулей,
нет root-ссылок на load — LOC-11: vm-сэндбокс без console падает).

Экспорт:
```
RARITY        — [{id:'common',chance:0.5},{id:'rare',chance:0.3},
                 {id:'epic',chance:0.15},{id:'legendary',chance:0.049},
                 {id:'impossible',chance:0.001}]   // сумма === 1.0 в FP
EQUIP_POOLS   — {common:[],rare:[],epic:[],legendary:[],impossible:[]}
pickRarityTier(rngFn) — 1 вызов rngFn(); acc-накопление по RARITY,
                 строгое `r < acc`; fallback = последний тир
                 (impossible) — никогда не undefined
```
* RARITY ids === Object.values(I.ITEM_RARITIES) (пinned EQ1/CH4).
* Порядок RARITY = канонический (common→impossible); порядок
  ОБЯЗАТЕЛЕН — acc-накопление зависит от него (EQ1 пин массива
  целиком).
* EQUIP_POOLS — ОДИН ГЛОБАЛЬНЫЙ пул по тирам; значения = id-строки
  предметов из items-data; редкость предмета = КЛЮЧ массива (в
  рантайме каталог НЕ читается).
* .05: ВСЕ 5 массивов ПУСТЫЕ. Волны .08–.15 добавляют id в
  каталожном порядке (интерфейс §6).
* Целостность (EQ2/CH4): каждый id ∈ items-data; у предмета явный
  slot И явная rarity; catalog-rarity === ключ тира; порядок в
  массиве = каталожный (свойство, не обязательство рантайма —
  рантайм по порядку не смотрит, но пин ловит регресс волн).

## 7. Подводные камни

1. **FP-границы — главная ловушка.** 0.95 ≠ 0.5+0.3+0.15 в FP
   (=0.9500000000000001); 0.999 < 0.9990000000000001 → 0.999
   legendary, НЕ impossible (все три анализа ошиблись — решение 7).
   Пины E3 — точные acc-значения (0.9500000000000001,
   0.9990000000000001), а не «красивые» 0.95/0.999 — только так
   фиксируется строгое `r < acc`. Не «чинить» 0.95 через EPSILON
   — таблица запинена, FP-хвост — часть контракта.
2. **Порядок вызовов = контракт.** Экипировочный ролл = ПОСЛЕ
   редкого (combat) / ПОСЛЕ залежей (dungeon, СВОЙ поток).
   Перестановка = тихий сдвиг всего main-stream (N5/D-BOSS-2
   goldens).
3. **eqTotal > 0 guard ДО ЛЮБОГО rng.** Пул всегда пуст до волн;
  guard — единственное, что держит бит-в-бит весь пре-волновый
  период (и все subset-цепочки).
4. **Замена ch.item — in-place, без новых ключей.** Новый ключ
   (ch.eq, ch.rarity) = слом D-BOSS-3 deepStrictEqual + save.js
   serializer + 100%-re-сериализация сейвов. Редкость предмета
   сундука НЕ храним — определяется каталогом в UI/инвентаре
   (000230.02/01).
5. **Соль 0x0E5C = ОРЕ-7.** Смена = репин ВСЕЙ зоны сундуков
  (все CH-goldens + D-BOSS-2-совместимые пины). Текст-пин литерала
  в CH1 (паттерн STAIRS_SALT-пина 000157.02).
6. **Red-фаза: require data-модуля ТОЛЬКО в теле dungeon-тестов.**
  В шапке файла = MODULE_NOT_FOUND на load = 73 fall-а вместо 4.
  В combat.test.js — только +имена в деструкте (undefined =
  осмысленный red без load-ошибки).
7. **Fixtures: in-place мутация + restore в finally ВНУТРИ теста.**

  контаминации), но внутри файла тесты последовательны — утечка
  фикстуры = fall следующих тестов того же файла. Замена объекта
