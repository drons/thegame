## 7. Верификация референс-плана пользователя (автотайлинг, «вариант A — границу рисует стена»)

**Ключевые расхождения с кодом:**
1. **Значения клеток инвертированы**: в плане «0=пол, 1=стена», в коде `CELL_WALL = 0`, `CELL_FLOOR = 1` (`dungeon.js:62-63`, `cities.js:49-50`). Бит маски «сосед — пол» = `cells[idx] === 1`. Буквальный перенос формулы плана даст инвертированную маску.
2. **Масштаб «16 спрайтов» vs 5 стилей стен подземелья**: у каждого из 5 типов — свой набор wall-видов (cave: rock+stalactite; crypt: column+rock; ruins: column; drowned: rock; abyss: stalactite+rock), плюс город — 6-й стиль. План не учитывает множественность: минимум 16 (город) + 16 универсальных для подземелий (или строго 5×16 + 16 = 80).
3. **Соседство маски**: текущий фасад — **8-соседство** (диагональный floor уже «фасад» и рисуется, `dungeon.js:626-644`, пин 000070); маска плана — 4-соседство → клетка с только диагональным полом получит mask 0 → меняется набор рисуемых клеток в подземельях (в городах этот случай невозможен: layout — прямоугольник, у периметрных wall-клеток максимум один ортогональный floor-сосед; реально используются только маски {0,1,2,4,8}).
4. **Атлас**: прецедента атласов нет (grep 0); лоадер `createSpriteLoader` (`sprites.js:1172+`) кэширует целое изображение на путь, все `drawImage` — 4/5 аргументов. 16 отдельных 64×64 SVG ложатся в существующий механизм без изменений лоадера (прецеденты: 15 floor, 6 walls); атлас 4×4 возможен через 9-аргументный drawImage, но это новый паттерн + новые тесты. Обязательное: пути в `allAssetPaths()` (`sprites.js:1087+` — единственный pre-лоад) + `EXPECTED_SVG_BY_DIR` в tests/svg.test.js + XML-схема.
5. **Двери/здания — overlay, не клетки**: дверь = FLOOR-клетка + спрайт поверх (после слоя стен, `dungeon-ui.js:653-718`); постройки/сундуки/мобы/залежи — спрайты поверх FLOOR, `cells` **нигде не мутируется во время визита** (layout иммутабилен; `generateCityContents` копирует массив `cities.js:291`; merge построенных зданий пишет только contents — `main.js:2622+`). → Маска считается по `cells[]` без учёта overlay — «отдельные спрайты поверх пола, маску не трогают» ложится как есть. Стена над дверью города получит «грань сверху» (дверь — FLOOR) — визуально корректно.
6. **Динамические изменения тайлов отсутствуют** — пункт 7 плана (пересчёт 3×3) не применим: нет открытия дверей (выход — [E] на FLOOR-клетке, 000177), нет разрушения/постеления пола; рендер и так перерисовывает весь видимый диапазон **каждый кадр** (`dungeon-ui.js:568-597`, без dirty-трекинга). Маска: либо чистая функция на клетку на кадр (4 чтения + bounds — пренебрежимо), либо одноразовая предвычисленная сетка на layout/этаж (чисто, 0 RNG — детерминизм не ломается). **Осторожно**: форма city-layout пинана «ровно 7 полей» (`cities.test.js:274-283`) — новое поле в layout сломает пин; маску лучше держать на стороне оверлея/чистой функцией.
7. **Fog of war**: стеновой слой подземелья под гейтом маски тумана (`dungeon-ui.js:641, 572`) — автотайл-стены обязаны пройти тот же гейт (город — без тумана).
8. **Вариант A vs B для наших ассетов**: A ложится лучше — в городе стены уже отдельный рисуемый слой (заменяем fillRect на спрайт, пол может остаться плоским цветом), в подземелье концепция фасадных объектов уже существует (заменяем kind_выбор на mask-индекс). B потребовал бы 16 floor-спрайтов на каждый из 5 dungeon-типов + город при уже существующем 15-файловом floor-наборе (дungeonFloorFrame пинан) — дороже и с большими ре-пинами.
