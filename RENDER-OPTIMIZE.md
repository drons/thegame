## 2. Горячие места текущего цикла (по коду, steady state, каждый rAF-кадр)

Цикл: `frame()` main.js:4051 → unconditional `requestAnimationFrame(frame)` :4223;
body: tryMove → updateCamera → gated resize → buildFrame → drawSprites → renderHud.

1. **Legacy-гейт XOR каждый кадр по всем frameTiles** (main.js:3636): при z=4 —
   131k вызовов `tileFrameImg` + `brightness()` на кадр, даже когда все ассеты
   ready и вершин 0. Доминирующий CPU-цикл steady-state.
2. **4 прохода по frameTiles каждый кадр** (:3828 текстуры/вода/декор/лут,
   :3882 якоря построек через Set, :3930 агро-окружности, :3960 мобы) — полный
   скан всех видимых тайлов ради горстки объектов; худший случай ~5×131k
   итераций/кадр.
3. **Шторм re-bake при колесе зума**: guard чанка требует точного совпадения
   зума (:3804, `|zoom−zoom| ≤ 1e-6`) → каждый шаг колеса меняет bucket →
   полный re-bake всех видимых чанков на main thread (527 × 256 drawImage ≈
   135k на шаг) — главный источник «неплавного зума».
4. **Miss-кадр pan при низком зуме**: `tileCache` cap 65536 (map.js:1203) при
   N=131k трэшит FIFO → ~65k регенераций `tileAt` (fbm/noise) на пересборку,
   синхронно.
5. **Подземелье при ≤1024 клеток**: per-cell пол/стены каждый кадр
   (dungeon-ui.js:737-803) + fog-fill по клеткам; типичный вьюпорт не попадает
   под чанковый гейт (000263 §3.1).
6. **Кадровые аллокации**: `new Float32Array(verts)` + `bufferData` каждый кадр
   (:3672-3673, даже при 0 вершин); `worldAnchoredTileEdges` edge-массивы
   каждый кадр (~1k элементов при z=4); `clearRect` обоих canvas каждый кадр.
7. Нет idle-ветки: рендер unconditional, CPU-стоимость steady кадра постоянна
   независимо от того, изменилась ли сцена.

## 3. Цикл maplibre (факты по клону 6.17.0)

### 3.1 Планирование кадра — рендер только на dirty
- Постоянного rAF-цикла нет: `triggerRepaint()` → `browser.frame` с дедупом по
  `_frameRequest` (ui/map.ts:4636-4654; util/browser.ts:23-35) — много вызовов
  в один тик дают один кадр.
- Тело `_render`: `style.update` только при `_styleDirty` (ui/map.ts:4459-4480);
  update тайловых менеджеров только при `_sourcesDirty` (:4488-4491); placement
  (:4503); painter.render (:4509). Если после кадра nothing dirty и не
  `_repaint` — следующий кадр НЕ планируется, fires `idle` (:4552-4557) →
  CPU в idle = 0.
- Pan/zoom: движение камеры через `camera_movement_scheduler` + task queue
  (ui/camera_movement_scheduler.ts:82-85,219), `_update()` ставит
  `_sourcesDirty` на каждый кадр движения (:4404-4424) → кадры есть только
  пока движение идёт.
- Continuous-анимации: style transitions → `_styleDirty` (:4536-4538); symbol
  fade держит кадры ещё fadeDuration после commit (symbol/placement.ts:1330-1342);
  raster fade — `hasTransition` тайл-менеджера (tile/tile_manager.ts:986-992).

### 3.2 Геометрия аплоадится один раз и живёт на GPU
- Bucket строится в worker-потоке, сериализуется, на main — WebGL-буферы
  (data/bucket.ts:107-113); shared между слоями с одинаковым layout (:128-131).
- `tile.upload` только при `uploadPending` (tile/tile.ts:378-382, флаг
  uploaded symbol_bucket.ts:619-630), вызывается из tile_manager.prepare
  (:227-235), после загрузки НИКОГДА не ре-аплоадится; `bucket.update` —
  только feature-state/images (tile.ts:539-560), не по зуму.
- Переиспользование на всех кадрах/панорамах того же зума: vertex/index буферы
  неизменны; на кадр — `program.draw` с identity-кэшем VAO на сегмент+слой
  (webgl/program.ts:254-267); uniforms ставятся каждый draw (:231-239).

### 3.3 Зум = матрица + async новые тайлы (аналог «overscale»)
- `reparseOverscaled=true` по дефолту (source/vector_tile_source.ts:111): worker
  режет maxzoom-тайл под целевой (vector_tile_overzoomed.ts:72-109), результат
  кэшируется по паре (max,target) (vector_tile_worker_source.ts:182-209);
  CPU-работа — в worker (async, вне main-кадра), GPU-буферы нового тайла —
  upload один раз. На main при зуме пересчитывается только projection-матрица
  на тайл (webgl/projection_uniform_buffer.ts:34-47, кэш по tileID внутри
  кадра, освобождение в начале кадра :50-53; painter.ts:253).
- Тайлы вне вьюпорта НЕ выбрасываются: LRU `_outOfViewCache` держит GPU-буферы
  и возвращает при обратном зуме (tile_manager.ts:737-762,824-844), размер =
  tilesInView × 5 зум-уровней (:462-473, util/config.ts:38); переполнение →
  `_unloadTile` (:211-213) → удаление буферов/атласов (tile.ts:354-370),
  raster-текстура — в пул.

### 3.4 Culling — DFS квад-дерево, пересчёт на change
- `coveringTiles`: DFS квад-дерево с frustum-AABB тестом кандидата
  (geo/projection/covering_tiles.ts:286-398; isTileVisible :90-106;
  zoom-эвристика под pitch :129-161). Пересчёт — только при `_sourcesDirty`
  (pan/zoom/load), НЕ каждый кадр в idle.

### 3.5 Raster и атласы
- Raster-текстура аплоадится один раз с mipmap (raster_tile_source.ts:232-241),
  пул переиспользования 50/размер (render/painter.ts:455-472), unload — в пул
  (:261-265). 1 draw call на тайл (webgl/draw/draw_raster.ts:104-144);
  tileSize=512 (:85) → типичный 1920×1080 pitch 0 ≈ 12 тайлов.
- Glyph/icon атласы — НА ТАЙЛ, pack в worker (render/glyph_atlas.ts:32-80),
  upload один раз (tile.ts:385-394); dirty images патчат атлас частично только
  при dirty (tile.ts:396-401 → render/image_atlas.ts:155-192). Symbols:
  инстансинга нет, drawElements на сегмент на тайл, halo 2-pass
  (webgl/draw/draw_symbol.ts:470-477,486-493,516-520).

### 3.6 Painter и контекст
- Программы кэшированы по (variant, configuration) и компилятся один раз
  (webgl/program_cache.ts:34-35); depth/stencil/color/cull state — кэшированные
  обёртки (program.ts:212-215). Frame-UBO обновляется 1 раз на кадр
  (painter.ts:250). Пер-тайл stencil-клиппинг: 1 draw на тайл на клиппинг-слой
  (painter.ts:330 → frame_render_context.ts:247-262).
- antialias=false (ui/map.ts:522), webgl2 stencil:true (:4244-4259);
  canvas = CSS × pixelRatio с clamp по maxCanvasSize (:1658-1670,1685-1703;
  painter.resize painter.ts:134-138).

### 3.7 CPU на кадр (итог)
- idle: 0 кадров, 0 CPU.
- steady (без движения): полный render ≈ tiles×layers×2 draw calls, без
  uploads, без CPU-циклов по тайлам.
- pan: coveringTiles + re-projection symbol placement с ре-аплоадом
  dynamic/opacity буферов (symbol/projection.ts:220-333, placement.ts:1288-1292)
  — самая дорогая часть pan в maplibre; геометрия тайлов НЕ перестраивается.
- zoom: как pan + async loads/slices в worker + один upload новых overzoom-тайлов;
  GPU-геометрия не re-bake'ится пер-кадром.

## 4. Ключевые отличия от нашего цикла

| аспект | maplibre | мы |
|---|---|---|
| планирование | кадр только на dirty; idle = 0 кадров | unconditional rAF каждый tick (main.js:4051→4223) |
| where per-tile CPU | один раз при загрузке тайла (worker) + GPU upload | повторяется каждый кадр: legacy-гейт + 4 прохода по frameTiles (худший ~650k итераций/кадр) |
| zoom | projection-матрица + async worker-тайлы + out-of-view GPU-кэш; геометрия не перестраивается | синхронный re-bake всех видимых чанков на каждый шаг колеса (~135k drawImage) из-за гарда точного зума |
| pan miss-кадр | bounded: async upload queue, генерация в worker | 131k look-up'ов + ~65k регенераций tileAt на main thread (FIFO cap 65536) |
| draw unit | GPU draw call (тайл×слой, ~tiles×layers×2 на кадр) | Canvas2D drawImage на тайл/чанк/сущность |
| ресурсы вне вью | держатся на GPU (LRU tilesInView×5), возврат при обратном зуме | CPU-canvas LRU 16MP; при вытеснении — полный re-bake |
| аллокации на кадр | frame-UBO 1 раз, projection-UBO кэш по tileID | новый Float32Array каждый кадр, edge-массивы каждый кадр |
| HiDPI | canvas CSS×pixelRatio (clamp) | CSS px → размытие на HiDPI |

## 5. Применимые подходы (по порядку цена/эффект, с контрактными рисками)

### A. Гасить legacy-гейт в steady state (дёшево, огромный выигрыш)
При `spriteLoader.readyCount() === totalCount()` (API есть, sprites.js:1267)
XOR-гейт 000176 детерминированно даёт 0 вершин → пропускать цикл main.js:3636
полностью (и сбор brightness). Убирает доминирующие 131k итераций/кадр.
Риски: пины RM-3/RM-10 (steady 0 вершин) валидны; RM-4/RM-8 (частичная
загрузка) требуют, чтобы гейт работал при readyCount < totalCount — новый
пин «гейт возвращается при частичной загрузке»; readiness-канал readyCount
монотонен (000263 §3.8). bufferData на кадр остаётся (DYNAMIC-семантика,
RM-6). Коммит-контракт: CHANGELOG не трогать (рендер-визуал не меняется).

### B. Subset-списки по слоям вместо полных сканов (аналог bucket, CPU-версия)
При пересборке frameTiles строить субсписки: waterTiles, decorCandidates,
lootCandidates, anchors, mobGroups. На хите iterate субсписки (live-фильтры
collectedLoot/defeatedAt/groupVisible сохраняются в петле — дёшевы).
Порядок row-major в субсписке → draw бит-в-бит (пины CC-2 z-порядка, LM/000042
держатся). Инвалидация: сбор лута (collect), смена дня (defeatedAt), respawn —
bump версии ключа по паттерну `bumpWorldVersion` (000276 §3-контракт).
Эффект: худший steady кадр с 5 полных сканов до 1 скан (до A — 2) + горстки.

### C. Поднять cap tileCache (map.js:1203, 65536) под размер вьюпорта
Худший case N=131k сейчас трэшит FIFO → каждая miss-пересборка содержит ~65k
регенераций tileAt. Адативный/поднятый cap делает pan-кадры чисто lookup'ами.
Побочка: FIFO eviction-порядок меняется — тайлы чистые (tileAt детерминирован),
содержимое идентично; изолированные tileCache-тесты (map.test.js) и
tileCache-в-frame() пинов нет (000276 §7). Быстрый win против pan-jank при
низком зуме. Память: 131k тайл-объектов ≈ несколько MB — приемлемо.

### D. Плавный зум — «bake на покое» (аналог overscale)
Bake чанка один раз на канонический zoom бакета; во время жеста колеса — блит
ближайшего бакета со scale; после остановки колеса (idle N мс) — точный re-bake
на текущий zoom → пиксель-перфект восстанавливается на покое. Единственный
подход, дающий maplibre-подобный smooth zoom, НО ломает «результат идентичен»
в переходном состоянии (blur внутри чанка при scale, соседи одного бакета —
без шва между чанками). Требует РЕШЕНИЯ пользователя (пиксель-перфект vs
плавность в жесте), квалификатора в spec/world-map.md, ре-пинов CC-4 и
spec-wording. Альтернатив без потери пиксель-перфекта нет (000263 §13 гард
1e-6 написан именно против швов).

### E. Idle-skip — рендер только на dirty
Флаги dirty (камера/hero-glide/wander мобов/видимая вода/day change/оверлеи/
building-anim 000224) гасят ТЕЛО рендера; rAF-цепь остаётся unconditional
(контракт watchdog 000170 D3: reschedule в finally ВСЕГДА). Риск: e2e-харнесы
pumping'ом кадров ассертят draw-вызовы на кадр — idle-ветка должна быть
принудительно «dirty» в тестах или отдельный forced-render хук. Кандидат с
осторожной проводкой; самый большой win по idle-CPU, но и самый контрактный.

### F. GPU для статичного слоя (большой build)
Запечённый чанк-canvas → WebGL-текстура (texImage2D 1 раз на bake, пул по
образу painter.ts:455-472), все видимые чанки — один textured pass на #game
под 2D-слоем (квады чанков — пересчёт блит-прямоугольников, ~527 квадов/кадр,
дешёвый). Далее — entities (мобы/постройки/герой/лут) в texture atlas одним
инстанс-проходом (documented-кандидат 000289 §7 «гибридный WebGL, >500
спрайтов»). Снимает 527 Canvas2D drawImage/кадр и разгружает #sprites до
динамических слоёв. Строить только после A+B+C и профайлинга — возможно,
Canvas2D-блитов достаточно на рабочих разрешениях.

### G. Мелочи
- Переиспользовать Float32Array в buildFrame (skip аллокацию при 0 вершин или
  bufferSubData в capacity-буфер) — мелкий GC-win, пины RM-6 bufferData-вызова
  сохранить.
- Fog подземелья: FOG_DIM per-cell fillRect → один квад с explored-mask
  текстурой (upload на изменение explored — монотонно, 000263 §3.5) — кандидат
  000263 §9.
- DPR-aware canvas (maplibre CSS×pixelRatio с clamp): у нас HiDPI-размытие;
  снап-сетка (000215/000228) потребует пересмотра spec и TS-пинов — отдельное
  решение.

## 5.1 Оценки подходов по трём критериям (шкала 1..10)

Эффект = потенциал роста производительности рендера и плавности анимаций.
Простота = трудозатраты реализации (10 = тривиально). Риск сломать =
вероятность регрессии существующих контрактов/пинов/визуала (10 = ломает
многое).

Fog-маска подземелья текстурой | 5 — до 3969 fog-fillRect/кадр в подземелье на низком зуме (кандидат 000263 §9) | 5 — upload маски на изменение explored (монотонно), один квад поверх мобов до игрока | 4 — затемнение обязано быть бит-в-бит (пины dungeon-vision/MOBV); порядок слоёв фиксирован — квад строго между мобами и игроком |
| G3. DPR-aware canvas | 3 — резкость на HiDPI (качество, не скорость) | 4 — resize × pixelRatio с clamp (паттерн maplibre ui/map.ts:1658-1670) | 6 — снап-сетки 000215/000228 и TS-пины требуют пересмотра spec (целые ряды при DPR) — отдельное решение |

Сводка: максимум эффекта при минимальной цене — **A** (высокий эффект, почти
тривиально, почти без риска) и **C** (дешёвая константа против pan-jank);
**B** — следующий по соотношению. Решающий по плавности зума — **D**, но он
единственный с сознательной визуальной регрессией в переходном состоянии
(нужно решение). **F** — потолок архитектуры при самой низкой простоте и
среднем риске; строить только после A/B/C + профайлинга. **E** — самый
контрактно-опасный среди «чистых» оптимизаций.

## 5.2 Плавность движения персонажа (основной игровой сценарий)

Механика движения (по коду): шаг героя = пересечение тайла + глейд
(renderPos prev→next, 000033), камера следует за глейдом. Каждый пересечения
тайла сдвигает `visibleTileRange` на строку/столбец → **frameTiles miss на
каждом пересечении** (между пересечениями — hit); мирные чанки при движении НЕ
ре-бейкаются (камера не в ключе, мир-якорная сетка, 000263 §3.3), только
блит-ряды пересчитываются на кадр. В подземелье камера cam-anchored и сетка
сдвигается на каждый px-шап снапа → чанки ре-бейкаются на шап (000263 §3.4) —
поэтому пер-cell путь при ≤1024 клеток и есть путь движения.

Стоимость movement-кадра (пересечение тайла): miss-пересборка (131k look-up +
~65k регенераций FIFO) + legacy-гейт в том же цикле + 4 полных скана + аллокация
Float32Array — именно этот «шип» на каждое пересечение тайла и есть jank при
ходьбе между плавными hit-кадрами глейда.

| подход | Эффект на плавность движения | Комментарий |
|---|---|---|
| A. Skip legacy-гейта | 10 — гейт выполняется и на hit, и на miss (внутри rebuild-цикла, main.js:3636/3645); при всех ready его вывод пуст, значит пропуск снимает 131k+ вызовов tileFrameImg/brightness с КАЖДОГО movement-кадра — движение болит именно на miss-кадрах | простота/риск — как §5.1 |
| C. Cap tileCache | 10 — движение = miss на каждом пересечении тайла; cap убирает FIFO-регенерации ~65k tileAt в пересборке — главный анти-jank ходьбы на низком зуме | простота/риск — как §5.1 |
| B. Subset-списки | 8 — на каждом movement-кадре полностью сканируются якоря построек, агро-окружности, мобы, лут (:3882/:3930/:3960) — subсписки снимают эти сканы между пересечениями и на них самих | простота/риск — как §5.1 |
| G1. Реюз Float32Array | 4 — аллокация массива каждый кадр глейда → GC-паузы = периодические микродрыги при ходьбе (в §5.1 оценка 2 — для движения выше) | |
| G2. Fog-маска текстурой | 6 — ходьба в подземелье: fog-fill по клеткам каждый кадр (до ~3969 fillRect на ABYSS@низком зуме) + пер-cell пол/стены остаются (чанки при движении ре-бейкаются на px-шап — см. анти-паттерн ниже) | |
| F. GPU-статика + atlas | 9 — потолок: movement-кадр = несколько draw call вместо 527 блитов + entity-сканов; ставить после профайлинга A/B/C | простота/риск — как §5.1 |
| D. Bake на покое | 2 — колесо в игре почти не используется; при движении зум постоянен → бакет не меняется → re-bake-шторм не на пути движения; остаётся для редкого wheel-сценария | |
| E. Idle-skip | 2 — движение = всегда dirty; idle-ветка не помогает ходьбе, только статичным сценам | |
| G3. DPR | 2 — резкость визуала при ходьбе на HiDPI, на скорость движения не влияет | |

Анти-паттерн для движения: НЕ понижать DUNGEON_CHUNK_MIN_CELLS (1024) ради
подземельной ходьбы — cam-anchored сетка чанков сдвигается на каждый px-шап
камеры глейда → ре-бейк задетых чанков на каждом шапе = шторм вместо плавности
(000263 §3.4; гейт 1024 оставлен именно потому, что при полном вхождении сетки
камера закреплена и ре-бейков 0). Плавность подземелья при движении — через G2
(fog-маска) и, при профайлинге, через F.

Сводка по движению: **максимально плавную ходьбу дают A + C + B** (+G1/G2
убирают GC-микродрыги и fog-скан в подземелье); архитектурный потолок — F. D и
E движению не помогают.

## 6. Что копировать не стоит

Векторные тайлы и worker-реparse/overscale-механику (мир процедурный, тайлы —
спрайты, не vector features), квад-дерево coveringTiles (наш диапазон —
прямоугольник visibleTileRange, O(1)), глифный атлас и symbol placement/fade
(нет текста на карте), per-tile stencil-клиппинг, инстансинг символов (в
maplibre его нет), antialias:false (Canvas2D-слой — свои semantics),
fade-переходы тайлов.

## 7. Рекомендуемый порядок

1. A (skip гейта в steady) + C (cap tileCache) — дешёвые, без контрактных
   compromises; A убирает главный steady-цикл, C — pan-jank при низком зуме.
2. B (subset-списки) — умеренный build, снимает 4 полных скана/кадр.
3. D (bake на покое) — требует решения о пиксель-перфекте в переходном
   состоянии; после решения — biggest smoothness win для зума.
4. E (idle-skip) — после A+B, с профайлингом и аккуратной проводкой тестов.
5. F/G — после профайлинга; F только если Canvas2D-блиты не тянут рабочие
   разрешения.

Ожидание после 1+2: steady худший кадр — без полных сканов (вода per-tile +
блиты + entities), панорама — lookup-пересборки без регенераций; «плавность»
в уровне maplibre для pan/steady, для zoom — только после D.

Основной игровой сценарий — движение персонажа (§5.2): приоритет A + C + B
(каждое пересечение тайла = miss-кадр; D/E движению не помогают), затем G1/G2,
потом F по профайлингу.

Оформление по workflow (CLAUDE.md): каждая правка — отдельная задача
`tasks/pending`, свой worktree, красные тесты, один коммит, мерж в master;
для D/E — решение пользователя до реализации; CHANGELOG — только если
user-visible (D меняет переходный визуал → буллет по дате мержа).
